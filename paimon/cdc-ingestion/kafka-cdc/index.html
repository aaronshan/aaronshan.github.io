Kafka CDC

准备 Kafka Bundled Jar​

flink-sql-connector-kafka-*.jar

支持的格式​

Flink 提供了多种 Kafka CDC 格式:Canal Json、Debezium Json、Debezium Avro、Ogg Json、Maxwell Json 和普通 Json。 如果 Kafka Topic 中的消息是使用变更数据捕获(CDC)工具从另一个数据库捕获的变更事件,那么你可以使用 Paimon Kafka CDC,将解析出的 INSERT、UPDATE、DELETE 消息写入 Paimon 表。

格式是否支持
Canal CDCTrue
Debezium CDCTrue
Maxwell CDCTrue
OGG CDCTrue
JSONTrue
aws-dms-jsonTrue
debezium-bsonTrue
信息

JSON 数据源可能会缺失部分信息。例如,Ogg 和 Maxwell 格式标准不包含字段 类型;当你将 JSON 数据源写入 Flink Kafka sink 时,只会保留数据和行类型,其他信息会被丢弃。 同步作业会尽最大努力按如下方式处理该问题:

  1. 通常,debezium-json 包含 'schema' 字段,Paimon 会从中获取数据类型。请确保你的 debezium json 包含该字段,否则 Paimon 会使用 'STRING' 类型。
  2. 如果缺失字段类型,Paimon 默认使用 'STRING' 类型。
  3. 如果缺失数据库名或表名,则无法执行数据库同步,但仍可执行表同步。
  4. 如果缺失主键,作业可能会创建无主键表。在表同步时,你可以在提交作业时指定主键。

同步表​

通过在 Flink DataStream 作业中使用 KafkaSyncTableAction,或直接通过 flink run,用户可以将 Kafka 某个 Topic 中的一张或多张表同步到一个 Paimon 表中。

如需通过 flink run 使用该功能,执行以下 shell 命令。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    kafka_sync_table \
    --warehouse <warehouse-path> \
    --database <database-name> \
    --table <table-name> \
    [--partition_keys <partition_keys>] \
    [--primary_keys <primary-keys>] \
    [--type_mapping to-string] \
    [--computed_column <'column-name=expr-name(args[, ...])'> [--computed_column ...]] \
    [--metadata_column <metadata-column> [--metadata_column ...]] \
    [--metadata_column_prefix <metadata-column-prefix>] \
    [--kafka_conf <kafka-source-conf> [--kafka_conf <kafka-source-conf> ...]] \
    [--catalog_conf <paimon-catalog-conf> [--catalog_conf <paimon-catalog-conf> ...]] \
    [--table_conf <paimon-table-sink-conf> [--table_conf <paimon-table-sink-conf> ...]]

Configuration Description
--warehouse
 The path to Paimon warehouse.
--database
 The database name in Paimon catalog.
--table
 The Paimon table name.
--partition_keys
 The partition keys for Paimon table. If there are multiple partition keys, connect them with comma, for example "dt,hh,mm".
--primary_keys
 The primary keys for Paimon table. If there are multiple primary keys, connect them with comma, for example "buyer_id,seller_id".
--type_mapping
 It is used to specify how to map MySQL data type to Paimon type.
Supported options:
  • "tinyint1-not-bool": maps MySQL TINYINT(1) to TINYINT instead of BOOLEAN.
  • "to-nullable": ignores all NOT NULL constraints (except for primary keys). This is used to solve the problem that Flink cannot accept the MySQL 'ALTER TABLE ADD COLUMN column type NOT NULL DEFAULT x' operation.
  • "to-string": maps all MySQL types to STRING.
  • "char-to-string": maps MySQL CHAR(length)/VARCHAR(length) types to STRING.
  • "longtext-to-bytes": maps MySQL LONGTEXT types to BYTES.
  • "bigint-unsigned-to-bigint": maps MySQL BIGINT UNSIGNED, BIGINT UNSIGNED ZEROFILL, SERIAL to BIGINT. You should ensure overflow won't occur when using this option.
  • "decimal-no-change": Ignore decimal type change.
--sync_primary_keys_from_source_schema
 This is used to specify if primary keys from source should be used in paimon schema if primary keys using --primary_keys are not specified. The default is true.
--computed_column
 The definitions of computed columns. The argument field is from Kafka topic's table field name. See here for a complete list of configurations.
--metadata_column
 --metadata_column is used to specify which metadata columns to include in the output schema of the connector. Metadata columns provide additional information related to the source data. Available values are topic, partition, offset, timestamp and timestamp_type (one of 'NoTimestampType', 'CreateTime' or 'LogAppendTime').
--metadata_column_prefix
 --metadata_column_prefix is optionally used to set a prefix for metadata columns in the Paimon table to avoid conflicts with existing attributes. For example, with prefix "__kafka_", the metadata column "topic" will be stored as "__kafka_topic" field.
--kafka_conf
 The configuration for Flink Kafka sources. Each configuration should be specified in the format `key=value`. `properties.bootstrap.servers`, `topic/topic-pattern`, `properties.group.id`, and `value.format` are required configurations, others are optional.See its document for a complete list of configurations.
--catalog_conf
 The configuration for Paimon catalog. Each configuration should be specified in the format "key=value". See here for a complete list of catalog configurations.
--table_conf
 The configuration for Paimon table sink. Each configuration should be specified in the format "key=value". See here for a complete list of table configurations.

如果你指定的 Paimon 表不存在,该 action 会自动创建这张表。其 Schema 将从指定的 Kafka Topic 中所有表推导而来,即从 Topic 中获取最早的非 DDL 数据并解析出 Schema。如果 Paimon 表已存在,则会将其 Schema 与指定的 Kafka Topic 中所有表的 Schema 进行对比。

示例 1:

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --partition_keys pt \
    --primary_keys pt,uid \
    --computed_column '_year=year(age)' \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=order \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=canal-json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf bucket=4 \
    --table_conf changelog-producer=input \
    --table_conf sink.parallelism=4

如果在启动同步作业时 Kafka Topic 中没有消息,你必须在提交作业前手动创建表。你可以只定义分区键和主键, 其余列将由同步作业自动添加。

注意:在这种情况下你不应使用 --partition_keys 或 --primary_keys,因为这些键在建表时已定义, 无法修改。此外,如果你指定了计算列,还应该定义计算列所使用的所有参数列。

示例 2: 如果你想同步一张主键为 'id INT' 的表,并希望计算分区键 'part=date_format(create_time,yyyy-MM-dd)', 你可以先创建这样一张表(其他列可以省略):

CREATE TABLE test_db.test_table (
    id INT,                 -- primary key
    create_time TIMESTAMP,  -- the argument of computed column part
    part STRING,            -- partition key
    PRIMARY KEY (id, part) NOT ENFORCED
) PARTITIONED BY (part);

然后提交同步作业:

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --computed_column 'part=date_format(create_time,yyyy-MM-dd)' \
    ... (other conf)

示例 3: 对于某些追加型数据(如日志数据),可以将其视为只有 INSERT 操作类型的特殊 CDC 数据,因此你可以使用 'format=json' 将这类数据同步到 Paimon 表。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --partition_keys pt \
    --computed_column 'pt=date_format(event_tm, yyyyMMdd)' \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=test_log \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf sink.parallelism=4

同步数据库​

通过在 Flink DataStream 作业中使用 KafkaSyncDatabaseAction,或直接通过 flink run,用户可以将多个 Topic 或一个 Topic 同步到一个 Paimon 数据库中。

如需通过 flink run 使用该功能,执行以下 shell 命令。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    kafka_sync_database \
    --warehouse <warehouse-path> \
    --database <database-name> \
    [--table_mapping <table-name>=<paimon-table-name1> [--table_mapping <table-name2>=<paimon-table-name2> ...]] \
    [--table_prefix <paimon-table-prefix>] \
    [--table_suffix <paimon-table-suffix>] \
    [--table_prefix_db <db-name1>=<table-prefix1> [--table_prefix_db <db-name2>=<table-prefix2> ...]] \
    [--table_suffix_db <db-name1>=<table-suffix1> [--table_suffix_db <db-name2>=<table-suffix2> ...]] \
    [--including_tables <table-name|name-regular-expr>] \
    [--excluding_tables <table-name|name-regular-expr>] \
    [--including_dbs <database-name|name-regular-expr>] \
    [--excluding_dbs <database-name|name-regular-expr>] \
    [--type_mapping to-string] \
    [--partition_keys <partition_keys>] \
    [--primary_keys <primary-keys>] \
    [--computed_column <'column-name=expr-name(args[, ...])'> [--computed_column ...]] \
    [--metadata_column <metadata-column> [--metadata_column ...]] \
    [--metadata_column_prefix <metadata-column-prefix>] \
    [--kafka_conf <kafka-source-conf> [--kafka_conf <kafka-source-conf> ...]] \
    [--catalog_conf <paimon-catalog-conf> [--catalog_conf <paimon-catalog-conf> ...]] \
    [--table_conf <paimon-table-sink-conf> [--table_conf <paimon-table-sink-conf> ...]]

    该 action 会为所有表构建一个单一的合并 sink。对于每个待同步的 Kafka Topic 中的表,如果 对应的 Paimon 表不存在,该 action 会自动创建这张表,其 Schema 将从指定的 Kafka Topic 中所有表推导 而来。如果 Paimon 表已存在且其 Schema 与从 Kafka 记录解析出的 Schema 不同,该 action 会尝试执行 Schema 演进。

    示例

    从单个 Kafka Topic 同步到 Paimon 数据库。

    <FLINK_HOME>/bin/flink run \
        /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
        kafka_sync_database \
        --warehouse hdfs:///path/to/warehouse \
        --database test_db \
        --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
        --kafka_conf topic=order \
        --kafka_conf properties.group.id=123456 \
        --kafka_conf value.format=canal-json \
        --catalog_conf metastore=hive \
        --catalog_conf uri=thrift://hive-metastore:9083 \
        --table_conf bucket=4 \
        --table_conf changelog-producer=input \
        --table_conf sink.parallelism=4 \
        --computed_column 'pt=date_format(event_tm, yyyyMMdd)'

    从多个 Kafka Topic 同步到 Paimon 数据库。

    <FLINK_HOME>/bin/flink run \
        /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
        kafka_sync_database \
        --warehouse hdfs:///path/to/warehouse \
        --database test_db \
        --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
        --kafka_conf topic=order\;logistic_order\;user \
        --kafka_conf properties.group.id=123456 \
        --kafka_conf value.format=canal-json \
        --catalog_conf metastore=hive \

    Debezium-bson​

    debezium-bson 格式是 Kafka CDC 支持的格式之一。 它是通过 debezium 采集 mongodb 得到的格式,与 debezium-json 格式类似。 然而,MongoDB 没有固定的 Schema,每个文档的字段类型可能不同,因此 JSON 中的 before/after 字段 都是字符串类型,而 debezium-json 格式要求 JSON 对象类型。

    MongoDB BSON Jar 可以从 Maven 仓库 下载。

    bson-*.jar
    信息

    debezium bson 格式要求 insert/update/delete 事件消息包含完整文档,并包含一个表示变更前文档状态的字段。 这需要将 debezium 的 capture.mode 设置为 change_streams_update_full_with_pre_image,并将 capture.mode.full.update.type 设置为 post_image。 在 MongoDB 6.0 之前的版本中,无法获取 'Update Before' 信息,因此使用 Kafka Key 中的 id 字段作为 'Update Before' 信息。

    下面是一个从 Mongodb customers 集合捕获的更新操作的 JSON 格式简单示例:

    {
      "schema": {
        "type": "struct",
        "fields": [
          {
            "type": "string",
            "optional": true,
            "name": "io.debezium.data.Json",
            "version": 1,
            "field": "before"
          },
          {
            "type": "string",
            "optional": true,
            "name": "io.debezium.data.Json",
            "version": 1,
            "field": "after"
          },
          ...
        ]
      },
      "payload": {
        "before": "{\"_id\": {\"$oid\" : \"596e275826f08b2730779e1f\"}, \"name\" : \"Anne\", \"create_time\" : {\"$numberLong\" : \"1558965506000\"}, \"tags\":[\"success\"]}",
        "after": "{\"_id\": {\"$oid\" : \"596e275826f08b2730779e1f\"}, \"name\" : \"Anne\", \"create_time\" : {\"$numberLong\" : \"1558965506000\"}, \"tags\":[\"passion\",\"success\"]}",
        "source": {
          "db": "inventory",
          "rs": "rs0",
          "collection": "customers",
          ...
        },
        "op": "u",
        "ts_ms": 1558965515240,
        "ts_us": 1558965515240142,
        "ts_ns": 1558965515240142879
      }
    }

    这个来自 MongoDB customers 集合的文档有 4 个字段:_id 是 BSON ObjectID,name 是字符串, create_time 是长整型,tags 是字符串数组。以下是 debezium-bson 格式的处理结果:

    文档 Schema:

    字段名字段类型键
    _idSTRING主键
    nameSTRING
    create_timeSTRING
    tagsSTRING

    记录:

    RowKind_idnamecreate_timetags
    -U596e275826f08b2730779e1fAnne1558965506000["success"]
    +U596e275826f08b2730779e1fAnne1558965506000["passion","success"]

    由于事件消息的 schema 字段没有文档的字段信息,debezium-bson 格式不要求事件消息携带 schema 信息。具体操作如下:

    • 将事件消息的 before/after 字段解析为 BSONDocument。
    • 递归遍历 BSONDocument 的所有字段,并将 BsonValue 转换为 Java Object。
    • before/after 的所有顶层字段都转换为字符串类型,_id 固定为主键。
    • 如果 before/after 的顶层字段是基本类型(如 Integer/Long 等),直接转换为字符串;否则,转换为 JSON 字符串。
