BLOB 存储

Primary Key 表可以将顶层 BLOB、ARRAY<BLOB> 和 MAP<K, BLOB> 载荷存储在表管理的文件中。 与 Append 表使用的按位置寻址的 BLOB 文件不同,受管 BLOB 载荷拥有稳定的描述符。MergeTree 排序、去重和 Compaction 因此可以重排或删除行,而无需重写仍然存活的载荷字节。

该模式存储:

  • 每个标量值、非 null 数组元素或非 null map 值对应的序列化 BlobDescriptor;
  • 存放在不可变的 .managed.blob 数据包中的载荷;
  • 每个数据文件对应一个 .blobref sidecar 文件,记录该数据文件所引用的确切的受管数据包。

关于通用的 BLOB 概念和读取选项,请参见 BLOB 存储。

仅追加(append-only)的 video-frame-field 模式刻意与 Primary Key 表的受管 BLOB 存储保持分离。它写入自包含的 .video 数据包,包含完整编码的视频和内嵌的 帧序列索引,Primary Key 表不支持该模式。启用它不会改变 .managed.blob 数据包、.blobref 的所有权及其垃圾回收行为。

创建表​

使用 blob-field 标记需要将其载荷存入受管 BLOB 文件的标量、数组或 map 字段。 blob-descriptor-field 和 blob-view-field 是内联形式:它们序列化后的描述符或视图元数据保留在 普通数据文件中,不会被物化到受管 BLOB 文件中。

下面的示例同时接收一个标量值和一个有序的值数组:

CREATE TABLE media (
    id BIGINT,
    name STRING,
    content BYTES COMMENT '__BLOB_FIELD; media content',
    attachments ARRAY<BYTES> COMMENT '__BLOB_FIELD; related files',
    renditions MAP<STRING, BYTES> COMMENT '__BLOB_FIELD; named renditions',
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'merge-engine' = 'deduplicate',
    'changelog-producer' = 'none',
    'blob.target-file-size' = '128 mb'
);

INSERT INTO media VALUES
    (1, 'logo', X'89504E470D0A1A0A', ARRAY[X'25504446', NULL], MAP['thumbnail', X'89504E47']);

对于 Primary Key 表,blob-field 中每个非 null 的 Blob 值在进入 MergeTree 排序缓冲区之前都会被外置。无论值底层的表示形式如何,其载荷都会被复制到一个新的表管理的 BLOB 数据包中。 默认情况下读取返回载荷字节;也可以借助已有的 blob-as-descriptor 读取选项改为返回描述符。 blob-descriptor-field 会被内联写入普通数据文件,不参与受管存储及其 引用 sidecar 文件。

当基于描述符的 BLOB 被复制到另一张表时,目标表通常会基于自身的 catalog 上下文重建一个 FileIO。对于受管的 blob-field,这是一个复制流程:目标表会把载荷写入自己的 BLOB 存储, 而不会保留源描述符。如果源表使用表级凭证,请在目标表上配置 blob-descriptor.source-table,以便使用源表的 FileIO 来物化载荷:

ALTER TABLE media_copy SET TBLPROPERTIES (
    'blob-descriptor.source-table' = 'db.media$branch_rt'
);

使用 blob-descriptor-field 保留字面量描述符,或使用 blob-view-field 保留对上游行的逻辑、免复制的引用。 当源存储可以通过静态配置访问时,其他 blob-descriptor.* 文件系统选项仍然足够; source-table 用于表级 FileIO 凭证的场景。

源表必须与目标表属于同一个 catalog。支持 branch 后缀。没有 catalog 加载器的目标表 (包括 REST catalog 中的 external 表)不受支持。设置该选项后,它优先于其他 blob-descriptor.* 选项;如需切换回基于描述符的文件系统配置,请先移除该选项。

ARRAY<BLOB> 逐元素外置。每个非 null 的 Blob 元素都会被复制到受管存储,同时 数组顺序、null 数组以及 null 元素都会被保留。空数组不写入任何载荷。ARRAY<BLOB> 使用 blob-field;blob-descriptor-field 和 blob-view-field 仍然只支持标量声明。

MAP<K, BLOB> 逐值外置。键保留在普通数据文件中,每个非 null 值都会被替换为 指向受管存储的描述符。null map、空 map 以及 null 值都会被保留。支持的键类型包括 整数家族、BOOLEAN、DECIMAL、DATE、TIME、BINARY、VARBINARY(BYTES)、CHAR 和 VARCHAR; blob-descriptor-field 和 blob-view-field 仍然只支持标量声明。

blob.target-file-size 控制写入器何时滚动到新的受管载荷数据包。一个数据包可以包含 多行的载荷,行描述符记录其 URI、偏移量和长度。

备注

在 Append 表上,blob-descriptor-field 是仅描述符的存储方式,非 null 值必须提供描述符。 Append 表的 blob-field 存储仍需要启用 row tracking 和 data evolution。本文描述的 受管原始字节外置方式是受支持的 Primary Key 表所特有的。

要求与限制​

Primary Key 表的受管 BLOB 存储有以下要求:

项目要求
受管 BLOB 声明BLOB、ARRAY<BLOB> 和 MAP<K, BLOB> 使用 blob-field;blob-descriptor-field 保持内联
Merge Enginededuplicate、partial-update 或 first-row
Changelog Producer仅支持 none
键的用途受管 BLOB 列不能作为主键、分区键、bucket 键或 sequence 键
外部数据路径不支持 data-file.external-paths
PK clustering override不支持 pk-clustering-override

该 Primary Key 模式不要求启用 row-tracking.enabled 和 data-evolution.enabled。

Partial-update 与 BLOB 字段​

Primary Key 表可以在 merge-engine=partial-update 下结合标量 blob-descriptor-field、 受管的 blob-field(BLOB、ARRAY<BLOB> 或 MAP<K, BLOB>)以及标量 blob-view-field 使用:

模式Partial-updateChangelog说明
标量 blob-descriptor-field支持与其他 PU 表相同描述符字节内联存储
blob-field(受管的标量、数组或 map)支持仅 changelog-producer=none载荷存放在 .managed.blob
标量 blob-view-field支持与其他 PU 表相同读取时通过 catalog 解析
ARRAY / MAP 描述符或视图不支持—仅支持标量

fields.<ordering-field[,ordering-field...]>.sequence-group 左侧的 排序字段不能包含 BLOB 值。这包括任何存储模式下的 BLOB、ARRAY<BLOB> 和 MAP<K, BLOB> 字段。BLOB 字段可以出现在右侧,作为受 sequence group 保护的字段。

CREATE TABLE media_meta (
    id BIGINT,
    name STRING,
    content BYTES COMMENT '__BLOB_DESCRIPTOR_FIELD; external video',
    ts INT,
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'merge-engine' = 'partial-update',
    'fields.ts.sequence-group' = 'name,content'
);

对于受管 BLOB 列,请设置 changelog-producer=none(与 deduplicate 受管 BLOB 表相同)。 受管 BLOB 的 retract 记录不保留载荷值。因此,当受管 BLOB 字段被 sequence group 保护且需要处理 retract 记录时,它不能使用依赖原始 retract 载荷的聚合 函数。last_value 是支持的,因为它在 retract 时总是清空该字段;其他聚合函数要求配置 fields.<field-name>.ignore-retract=true。当 ignore-delete=true 或受管 BLOB 字段未被 sequence group 保护时,此限制不适用。

CREATE TABLE training_chunks (
    id BIGINT,
    name STRING,
    chunk BYTES COMMENT '__BLOB_FIELD; raw training block',
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'merge-engine' = 'partial-update',
    'changelog-producer' = 'none',
    'blob-field' = 'chunk'
);

非 null 值会更新对应的列;null 值不会更新字段(标准的 partial-update 语义)。在一个 sequence group 内,sequence 值为 null 会跳过整个组。不使用聚合函数时,一条 sequence 值更新或相等的记录会替换组内的所有字段,包括用 null 替换 BLOB 值; sequence 值更旧的记录会被忽略。使用聚合函数时,每条 sequence 值非 null 的记录 都会参与聚合或 retract,即使其 sequence 值更旧。例如,last_value 对 更新和更旧的 retract 记录都会清空该字段。

受管 BLOB 的 partial update 会将每个非 null 的标量 BLOB、数组元素或 map 值外置到一个 .managed.blob 数据包中。空集合以及只包含 null 值的集合不写入载荷。针对孤立数据包的 BLOB 垃圾回收尚未实现;在将来的收集器可用之前,反复更新可能留下无法访问的存储空间。

blob-view-field 列内联存储序列化的视图结构体。当 blob-view.resolve.enabled 为 true(默认值)时, 读取会通过 catalog 解析上游的 blob 字节。被 sys.blob_view(...) 使用的 Append 上游表必须启用 row-tracking.enabled 和 data-evolution.enabled。

First-row 与 BLOB 字段​

Primary Key 表可以在 merge-engine=first-row 下结合受管的 blob-field(BLOB、ARRAY<BLOB> 或 MAP<K, BLOB>)使用:

模式First-rowChangelog说明
blob-field(受管的标量、数组或 map)支持仅 changelog-producer=none保留第一条非 retract 行及其受管载荷

对于受管 BLOB 列,请设置 changelog-producer=none。first-row 通常也支持 lookup changelog producer,但受管 BLOB 存储要求使用 none。

first-row 为同一主键保留最早存活的行。因此,对同一个键的后续更新不会 替换已有的受管 BLOB 载荷。这与保留最新行的 deduplicate 不同。

默认情况下,first-row 不接收 DELETE 或 UPDATE_BEFORE 记录。如果你的 管道可能发出这类记录,请配置 ignore-delete=true。

CREATE TABLE training_chunks (
    id BIGINT,
    name STRING,
    chunk BYTES COMMENT '__BLOB_FIELD; raw training block',
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'merge-engine' = 'first-row',
    'changelog-producer' = 'none',
    'blob-field' = 'chunk'
);

受管 BLOB 的更新、删除与 Compaction​

每条进入的非 null 标量 BLOB、数组元素或 map 值,在应用合并规则之前都会被写为一个新的描述符和载荷。 因此,随后被 partial-update 或 sequence 规则丢弃的更新可能留下一个孤立的 载荷数据包。delete 记录不会写入新载荷。Merge Engine 在读取和 Compaction 期间确定逻辑上的 最终行。每个数据文件的 .blobref sidecar 记录该文件中非 retract 键值所引用的受管数据包, 在 Compaction 之前这可能包含中间态的 partial-update 载荷。

Compaction 会保留存活值的描述符,并基于 Compaction 结果创建新的 .blobref sidecar 文件。 它不会把被引用的载荷字节复制到新的 .managed.blob 数据包中。这使得普通 Compaction 的开销 与行元数据成正比,而非与 BLOB 大小成正比。

.blobref 文件通过 DataFileMeta.extraFiles 归属于其数据文件,因此它会跟随数据文件经历 snapshot、tag、branch、rollback、过期和删除等整个生命周期。共享的 .managed.blob 数据包刻意不作为 extra file,因为多个保留的数据文件可能引用同一个数据包。

垃圾回收​

对未被引用的 .managed.blob 数据包的垃圾回收尚未实现。因此,更新、删除、Compaction 或 不确定的写入器失败都可能留下不再被当前行可达的载荷数据包。

普通的孤儿文件清理器会刻意保留所有 .managed.blob 文件。这种防错行为可以避免它 删除仍然可从某个 snapshot、tag、branch 或其他保留根访问的载荷,但同时也意味着 在一个能够感知根节点的 BLOB 垃圾回收器可用之前,未使用的 BLOB 存储可能持续增长。

未来的收集器必须跨所有保留根计算可达性,并将缺失、损坏或不受支持的 .blobref sidecar 视为不可安全删除。空的、合法的 sidecar 与缺失的 sidecar 是不同的:它明确表示 该数据文件没有引用任何受管载荷数据包。

引用元数据​

BLOB 引用集合记录在由数据文件持有的 .blobref sidecar 中,而不是 IndexManifest 中。BLOB 可达性是单个数据文件的精确依赖,而 DataFileMeta.extraFiles 已经为此类元数据提供了所需的 生命周期。使用 IndexManifest 将需要引入新的 snapshot 级索引生命周期,这是一个 更大的兼容性变更。

每个 sidecar 都是不可变的、带版本、带校验和且确定性的。它只存储受管载荷的标识; 描述符和视图字段保持内联,不会被加入受管引用集合。受管数据包的标识由 描述符 URI 及其保留的 .managed.blob 后缀派生,因此即使 数据包与数据文件位于不同目录,引用仍然有效。
