创建发布版本

本指南面向 Apache Paimon 和 PyPaimon 的 Release Manager（RM）。它遵循 ASF 发布政策 和 ASF 发布分发政策。

注意

签名的源码归档包才是 Apache 正式发布物。Maven 和 PyPI 包属于便利性产物。最终发布必须使用社区投票 批准的源文件和 Java staging 仓库；投票通过后不得重新构建或替换它们。

发布模型​

Paimon 与 PyPaimon 的联合发布使用同一个共享版本号。 Maven 项目版本与 paimon-python/setup.py 中的版本必须一致。

交付物候选版本发布位置
Paimon 源码apache-paimon-PAIMON_VERSION-src.tgz、.asc、.sha512ASF distribution
Java 便利产物在 JDK 8、11、17 三条流水线中构建的 Maven 产物Apache Nexus staging，随后进入 Maven Central
PyPaimon 源码pypaimon-PAIMON_VERSION.tar.gz、.asc、.sha512ASF distribution
Python 便利包RC 版本为 pypaimon==PAIMON_VERSIONrcRC_NUMBERTestPyPI，随后正式版 pypaimon==PAIMON_VERSION 发布到 PyPI

一次联合发布投票同时覆盖两个签名源码候选包。本指南不定义独立的 PyPaimon 发布流程。 在单独发布 PyPaimon 之前，PMC 必须定义一套不依赖 Maven 版本或 Java 任务的纯 Python tag 与 工作流，并提供一个可独立完成构建和测试的签名源码包。

Java 构建矩阵​

三条 Java 流水线是不同的发布目标，而非可互换的构建 JDK：

JDKMaven profiles 及范围主要产物
8spark3,flink1 以及默认 reactorPaimon core、Flink 1.x、Spark 3.x、Hive、文件系统、bundles 及其他 Java 8 产物
11flink2 加上 paimon-icebergFlink 2.x、paimon-flink2-common 以及 Iceberg 集成
17spark4Spark 4.x 及其 Scala 2.13 公共产物

每条流水线必须使用对应的 JDK。全部用 JDK 17 构建并降低编译目标级别，并不能替代 JDK 8 和 JDK 11 流水线的运行。

GitHub Actions 发布工作流​

发布流程使用 Release 工作流， 从每一个签名 RC tag 打包 JDK 8、JDK 11、JDK 17 三条 Java 流水线以及 PyPaimon。 三条 Java 流水线的产物会合并成一个未签名的 Maven 仓库镜像。RM 下载该镜像、签名， 并将其暂存（stage）到 Nexus。RM 还从同一个 tag 在本地创建并签名两个 ASF 源码归档包。 RM 的 GPG 私钥绝不会存储在 GitHub Actions 中。

该工作流的约定如下：

任务必须满足的行为
校验要求 RC tag 命名为 release-PAIMON_VERSION-rcN，或正式 tag 命名为 release-PAIMON_VERSION，其中 PAIMON_VERSION 必须与根 Maven project.version 完全一致
Java 8使用 Temurin 8，将默认 reactor（Spark 3 和 Flink 1）部署到本地 Maven 仓库镜像
Java 11使用 Temurin 11，将 Flink 2 和 Iceberg 部署到本地 Maven 仓库镜像
Java 17使用 Temurin 17，将 Spark 4 部署到本地 Maven 仓库镜像
Java 仓库要求每一个启用 deploy 的 effective-POM 项目及其 POM、主 JAR、源码 JAR 齐全；Maven 生成的 Javadoc JAR 予以保留；合并三条流水线；拒绝坐标冲突；随后上传完整的未签名 Maven 仓库镜像、校验和、清单和日志
Python 打包构建并校验 PyPaimon 源码分发包和 universal wheel，然后作为工作流产物上传
Python 发布在 Python 打包通过后，将 RC 发布到 TestPyPI，或将正式 tag 发布到 PyPI，无需等待 Java 打包

打包之前，每条 Java 流水线都会在其完整的 reactor 范围内执行 Maven Enforcer 的 requireReleaseVersion 和 requireReleaseDeps 规则。后者包含传递依赖。任何残留的 -SNAPSHOT 项目、父 POM、直接依赖或传递依赖都是发布阻塞项。

Java 任务独立于公共校验任务和 Python 任务运行。它们使用 -Dgpg.skip=true，仅部署到 runner 本地的文件仓库，并且从不会获得 Nexus 凭据或 GPG 私钥。合并后的仓库镜像包含 POM、主产物、源码 JAR、Maven 生成的 Javadoc JAR 以及 Maven 生成的校验和。纯 Scala 和 wrapper 模块可能不会生成 Javadoc JAR。该镜像是 RM 本地签名和 Nexus staging 步骤的输入， 其本身并不是 ASF 发布物。Python RC 任务使用仓库 Actions secret 中的 TEST_PYPI_API_TOKEN 将 PAIMON_VERSIONrcRC_NUMBER 发布到 TestPyPI。正式版任务 使用仓库 Actions secret 中的 PYPI_API_TOKEN 发布到 PyPI。发布工作流只会将这两个 secret 传递给可复用的发布工作流。

RM 一次性配置​

在管理首个发布之前：

  1. 创建一个与你的 @apache.org 身份关联的至少 2048 位的 RSA GPG 密钥，并将其发布到 公共密钥服务器。ASF 发布分发政策 要求新产物使用 RSA 密钥；新生成的发布密钥请使用 RSA 4096。不要使用 DSA、ECDSA、 EdDSA 或 Ed25519 签署发布产物。
  2. 将公钥追加到 Paimon 的 KEYS 文件。绝不要移除验证旧版本发布 所需的密钥。
  3. 配置 Git 和本地 GPG，使用同一密钥为 tag 和 Maven 产物签名。
  4. 使用 RM 的 Apache Nexus 凭据配置本地 Maven server ID apache.releases.https。 不要将 GPG 密钥或 Nexus 凭据复制到 GitHub Actions。
  5. 记录 Paimon 的 Apache Nexus staging profile ID。本地仓库上传脚本会以 STAGING_PROFILE_ID 的形式要求提供它。
  6. 确认拥有 ASF distribution SVN 仓库、Apache Nexus、TestPyPI 和 PyPI 的访问权限。
  7. 确认仓库 Actions secrets TEST_PYPI_API_TOKEN 和 PYPI_API_TOKEN 已配置， 且不会将其值打印到 Actions 日志中。
gpg --with-subkey-fingerprint --list-secret-keys --keyid-format LONG
git config user.signingkey
svn --version

确认本次发布所配置的确切密钥或签名子钥报告为 rsa2048 或更高。不要根据同一 keyring 中的其他密钥推断合规性。

准备发布​

就发布达成一致​

在 dev@paimon.apache.org 上讨论发布事项，选定 RM，解决发布阻塞项，评审不兼容变更 和升级说明，并准备发布说明。评审将要切出候选版本的提交的 CI 状态；是否存在阻塞发布的 未解决失败由 RM 决定。

设置发布变量​

以 2.0.0 发布为例，Java 与 Python 版本保持一致：

PAIMON_VERSION="2.0.0"
DOC_VERSION="2.0"
RC_NUMBER="1"
RELEASE_BRANCH="release-2.0"

RC_REF="release-${PAIMON_VERSION}-rc${RC_NUMBER}"
RELEASE_TAG="release-${PAIMON_VERSION}"

在本地工作分支、tag、工作流入参、SVN 目录、投票邮件、Java 包清单以及文档 URL 中 都必须使用这些完全一致的值。

从干净的克隆开始​

git clone https://github.com/apache/paimon.git paimon-release
cd paimon-release
git checkout "${RELEASE_BRANCH}"
git pull --ff-only origin "${RELEASE_BRANCH}"
git status --short

最后一条命令必须没有任何输出。

创建本地 RC 分支并设置版本​

使用现有的辅助脚本创建本地 RC 工作分支：

RELEASE_VERSION="${PAIMON_VERSION}" \
RELEASE_CANDIDATE="${RC_NUMBER}" \
  ./tools/releasing/create_release_branch.sh

这会创建本地分支 release-PAIMON_VERSION-rcRC_NUMBER。它仅用于准备候选提交， 不要将该分支推送到远端。

远端发布分支不会被 RC 冻结。它可以继续接收用于后续 RC 或维护版本的修复，其头部 无需与已发布的 RC tag 保持一致。如果后续分支变更必须纳入当前正在投票的发布， 请基于更新后的分支状态创建一个新的 RC；绝不要移动或替换已有的 RC tag。

将所有 Maven 模块的版本从 PAIMON_VERSION-SNAPSHOT 改为 PAIMON_VERSION。辅助脚本会提交 Maven 版本变更：

NEW_VERSION="${PAIMON_VERSION}" \
  ./tools/releasing/update_branch_version.sh

将 paimon-python/setup.py 中的 VERSION 设为最终的 PAIMON_VERSION，不带 .dev 或 RC 后缀。发布工作流会通过追加 rcRC_NUMBER 导出 TestPyPI 版本；源码候选包则保留最终版本。

检查并提交 Python 版本、依赖声明、发布说明、LICENSE、NOTICE 以及任何生成的 法律文件。然后确认候选版本不包含任何 snapshot 或开发版本：

mvn -q -DforceStdout help:evaluate -Dexpression=project.version
python3 paimon-python/setup.py --version
rg --glob 'pom.xml' "<version>${PAIMON_VERSION}-SNAPSHOT</version>"
rg '^VERSION = ".*\.dev' paimon-python/setup.py
git status --short

前两条命令必须打印出预期的发布版本，两条 rg 命令必须找不到任何发布版本标记， 且工作区必须是干净的。

签名并推送 RC tag​

签名 tag 是唯一发布到远端的 RC ref。不要推送同名的本地 RC 分支。推送时使用显式的 tag ref：

git tag -s "${RC_REF}" \
  -m "Apache Paimon ${PAIMON_VERSION} and PyPaimon ${PAIMON_VERSION} RC${RC_NUMBER}"
git tag -v "${RC_REF}"

git push origin \
  "refs/tags/${RC_REF}:refs/tags/${RC_REF}"

推送签名 tag 会从完全相同的提交启动全部三条 Java 打包流水线。Python 发布在公共校验 和 Python 打包成功后立即开始；不会等待 Java 打包。请记录：

  • 工作流运行 URL 和 head_sha；
  • java-release-repository 产物名称、清单和 SHA-512 校验和；
  • TestPyPI 项目/版本 URL。

无关的 CI 状态不是自动的发布门槛；某个失败是否阻塞候选版本由 RM 决定。三条 Java 打包流水线和仓库合并必须成功，其仓库镜像才能被签名和暂存。

在本地签名并暂存 Java 便利产物​

在干净的克隆中检出确切的签名 RC tag。使用 RM 机器上的本地 GPG 密钥和 Maven 凭据； 不要把私钥下载到 CI runner 中。使用 Maven 3.8.8，与 Release 工作流一致。当本地 GPG agent 需要终端访问时，导出 GPG_TTY：

git checkout --detach "refs/tags/${RC_REF}"
export GPG_TTY="$(tty)"

gpg --list-secret-keys --keyid-format LONG
mvn -q -DforceStdout help:evaluate -Dexpression=project.version

从已记录的工作流运行中下载合并后的仓库镜像。使用 GitHub CLI 时，将 RUN_ID 设为 工作流 URL 中的数字运行 ID：

RUN_ID="<GITHUB_WORKFLOW_RUN_ID>"
JAVA_REPOSITORY_ARCHIVE="paimon-${PAIMON_VERSION}-maven-repository.tar.gz"

gh run download "${RUN_ID}" \
  --name java-release-repository \
  --dir java-release-repository

签名前先校验归档包以及仓库镜像中的每一个文件：

(
  cd java-release-repository
  sha512sum -c "${JAVA_REPOSITORY_ARCHIVE}.sha512"
)

mkdir paimon-maven-repository
tar -xzf "java-release-repository/${JAVA_REPOSITORY_ARCHIVE}" \
  -C paimon-maven-repository
(
  cd paimon-maven-repository
  sha512sum -c \
    ../java-release-repository/paimon-maven-repository-sha512.txt
)

grep -Fx "version=${PAIMON_VERSION}" \
  java-release-repository/paimon-maven-repository-manifest.txt
grep -Fx "tag=${RC_REF}" \
  java-release-repository/paimon-maven-repository-manifest.txt
grep -Fx "commit=$(git rev-parse HEAD)" \
  java-release-repository/paimon-maven-repository-manifest.txt

在 macOS 上，将 sha512sum 替换为 shasum -a 512。使用 RM 的本地密钥为解压后仓库中的 每一个 JAR 和 POM 签名。当默认 GPG 密钥就是发布密钥时，GPG_KEY_ID 可选：

REPOSITORY_DIRECTORY="${PWD}/paimon-maven-repository" \
GPG_KEY_ID="<RELEASE_GPG_KEY_ID>" \
  ./tools/releasing/sign_maven_repository.sh

使用 Nexus Staging Maven Plugin 上传完整的签名镜像：

REPOSITORY_DIRECTORY="${PWD}/paimon-maven-repository" \
STAGING_PROFILE_ID="<PAIMON_STAGING_PROFILE_ID>" \
  ./tools/releasing/deploy_maven_repository.sh

上传插件会创建一个 staging 仓库，并在完整上传后将其关闭（close）。脚本显式禁用了自动 release。若发生传输失败，它会丢弃不完整的 staging 仓库，因此重试时可以从干净状态开始， 而不会把坐标拆散到多个仓库中。若关闭规则（close-rule）校验失败，脚本会保留该仓库以供 检查。请记录唯一的 orgapachepaimon-XXXX 仓库 ID。如果关闭失败，检查并丢弃该仓库， 修正原因后重新上传干净的签名镜像。只有在成功关闭一个 staging 仓库之后才能发起投票。 投票通过之前不要 release 它。

如果签名过程被中断，丢弃已解压的仓库，重新解压已校验的归档后再重试。如果上传过程被 中断，先在 Nexus 中确认插件已丢弃不完整的 staging 仓库；必要时手动丢弃，然后使用 没改动过的签名仓库镜像重新运行上传。

暂存源码候选包​

在一个全新克隆中，从确切的签名 tag 在本地创建两个源码候选包。Paimon 的辅助脚本会创建、 签名主源码归档包并生成校验和，同时拒绝不安全的归档路径和 macOS 隐藏的 AppleDouble 元数据。PyPaimon 源码分发包单独构建，并使用同一个 RM 密钥签名：

git checkout --detach "refs/tags/${RC_REF}"

RELEASE_VERSION="${PAIMON_VERSION}" \
  ./tools/releasing/create_source_release.sh

cd paimon-python
python3 setup.py sdist
gpg --armor --detach-sig \
  "dist/pypaimon-${PAIMON_VERSION}.tar.gz"

(
  cd dist
  if command -v sha512sum >/dev/null 2>&1; then
    sha512sum "pypaimon-${PAIMON_VERSION}.tar.gz" \
      > "pypaimon-${PAIMON_VERSION}.tar.gz.sha512"
  else
    shasum -a 512 "pypaimon-${PAIMON_VERSION}.tar.gz" \
      > "pypaimon-${PAIMON_VERSION}.tar.gz.sha512"
  fi
)

cp "dist/pypaimon-${PAIMON_VERSION}.tar.gz"* ../release/
cd ..

上传到 ASF dist dev 之前，先在本地校验两个签名和校验和文件。

svn checkout --depth=immediates \
  https://dist.apache.org/repos/dist/dev/paimon/ paimon-dist-dev

mkdir "paimon-dist-dev/paimon-${PAIMON_VERSION}-rc${RC_NUMBER}"
cp "release/apache-paimon-${PAIMON_VERSION}-src.tgz"* \
  "paimon-dist-dev/paimon-${PAIMON_VERSION}-rc${RC_NUMBER}/"

mkdir "paimon-dist-dev/pypaimon-${PAIMON_VERSION}-rc${RC_NUMBER}"
cp "release/pypaimon-${PAIMON_VERSION}.tar.gz"* \
  "paimon-dist-dev/pypaimon-${PAIMON_VERSION}-rc${RC_NUMBER}/"

svn add \
  "paimon-dist-dev/paimon-${PAIMON_VERSION}-rc${RC_NUMBER}" \
  "paimon-dist-dev/pypaimon-${PAIMON_VERSION}-rc${RC_NUMBER}"
svn commit -m \
  "Stage Paimon ${PAIMON_VERSION} and PyPaimon ${PAIMON_VERSION} RC${RC_NUMBER}" \
  paimon-dist-dev

绝不要覆盖已有的 RC 目录。在本发布流程中，TestPyPI 版本同样是不可变的：工作流会在 上传前检查版本是否已存在，存在则失败而不是跳过文件。上传器也会拒绝重复文件，以覆盖 检查之后发生的竞态。只要有任何字节发生变化，就使用新的 RC 编号创建新的 RC。

发起投票​

向 dev@paimon.apache.org 发送纯文本投票邮件。投票至少开放 72 小时。投票必须获得 至少三张具有约束力的 +1 票，且具有约束力的 +1 票数必须多于具有约束力的 -1 票数。

Subject: [VOTE] Release Apache Paimon ${PAIMON_VERSION} and PyPaimon ${PAIMON_VERSION} (RC${RC_NUMBER})

Hi everyone,

Please review and vote on Apache Paimon ${PAIMON_VERSION} and
PyPaimon ${PAIMON_VERSION}, release candidate ${RC_NUMBER}.

[ ] +1 Approve
[ ]  0 No opinion
[ ] -1 Do not approve (please explain)

Paimon source candidate:
https://dist.apache.org/repos/dist/dev/paimon/paimon-${PAIMON_VERSION}-rc${RC_NUMBER}/

PyPaimon source candidate:
https://dist.apache.org/repos/dist/dev/paimon/pypaimon-${PAIMON_VERSION}-rc${RC_NUMBER}/

Signed Git tag:
release-${PAIMON_VERSION}-rc${RC_NUMBER}

Commit:
https://github.com/apache/paimon/commit/<RC_COMMIT_SHA>

GitHub Actions release run:
<WORKFLOW_RUN_URL>

KEYS:
https://downloads.apache.org/paimon/KEYS

Closed Java staging repository:
<JAVA_NEXUS_URL>

PyPaimon RC:
https://test.pypi.org/project/pypaimon/${PAIMON_VERSION}rc${RC_NUMBER}/

Verification guide:
https://github.com/apache/paimon/blob/release-${PAIMON_VERSION}-rc${RC_NUMBER}/docs/docs/project/verifying-a-release-candidate.md

The vote will remain open for at least 72 hours.

截止之后，分别统计具有约束力和不具约束力的票数，并在同一邮件线程中发送 [RESULT][VOTE]。

替换失败的候选版本​

如果投票发现问题：

  1. 通过正常评审流程修复它。
  2. 丢弃属于失败 RC 的 Nexus staging 仓库。
  3. 移除被取代的 dist-dev 目录；若对投票讨论有用，也可暂时保留。绝不要替换其内容。
  4. 递增 RC_NUMBER；绝不要复用失败候选版本的 TestPyPI 版本。
  5. 创建新的本地 RC 工作分支和签名 tag，仅推送 tag，重新运行所有工作流流水线， 暂存新的源码候选包，并发起一轮新的 72 小时投票。

完成已批准的发布​

创建最终签名 tag​

最终 tag 必须精确指向已批准的 RC 提交：

git tag -s "${RELEASE_TAG}" "refs/tags/${RC_REF}^{commit}" \
  -m "Release Apache Paimon ${PAIMON_VERSION}"

test "$(git rev-parse "refs/tags/${RC_REF}^{commit}")" = \
     "$(git rev-parse "refs/tags/${RELEASE_TAG}^{commit}")"
git tag -v "${RELEASE_TAG}"
git push origin "refs/tags/${RELEASE_TAG}:refs/tags/${RELEASE_TAG}"

晋级源码发布物​

将两个已批准的候选目录移动（而不是复制或重建）到正式发布区：

svn mv -m "Release Apache Paimon ${PAIMON_VERSION}" \
  "https://dist.apache.org/repos/dist/dev/paimon/paimon-${PAIMON_VERSION}-rc${RC_NUMBER}" \
  "https://dist.apache.org/repos/dist/release/paimon/paimon-${PAIMON_VERSION}"

svn mv -m "Release PyPaimon ${PAIMON_VERSION}" \
  "https://dist.apache.org/repos/dist/dev/paimon/pypaimon-${PAIMON_VERSION}-rc${RC_NUMBER}" \
  "https://dist.apache.org/repos/dist/release/paimon/pypaimon-${PAIMON_VERSION}"

晋级便利产物​

  1. 在 Nexus 中，确认已记录的 Java staging 仓库仍处于关闭状态，且其产物树与投票 批准的完全一致。
  2. 将这个确切已关闭的仓库 release 到 Maven Central。不要重新上传或重建 Java 产物。
  3. 确认最终 tag 的 PyPI 发布任务是从已批准的 tag 提交构建 pypaimon==PAIMON_VERSION，且未改动项目源码。
  4. 在发布公告之前，先验证 Maven Central 和 PyPI。

发布与公告​

从 release-PAIMON_VERSION 创建 GitHub release，检查生成的说明，并链接两个源码 发布包。

在发布公告之前，发布带版本的文档并更新项目网站。将 apache/paimon 中的文档和 apache/paimon-website 中的项目网站视为两个独立且都必须完成的更新。

  1. 在 apache/paimon 中，从发布分支发布 DOC_VERSION 的文档，使发布的内容与 发布的代码一致：
    • 在 RELEASE_BRANCH 上，用已发布的 baseUrl、version、versionTitle、 branch、editUrl、isStable、stableDocs、previousDocs 以及 navbar 版本菜单更新 docs/docusaurus.config.js。
    • 在 master 上，设置下一个开发版本，并更新 stableDocs、previousDocs 以及 navbar 版本菜单，将 DOC_VERSION 作为稳定版纳入其中。
    • 检查 docs/docs/project/download.mdx 以及任何与发布相关的引擎或兼容性信息。 2.1-SNAPSHOT、<Stable> 和 <Unstable> 部分必须在稳定版站点上正确渲染 已发布的产物。
    • 对两种配置都在 docs 目录下运行 yarn build。
  2. 在 apache/paimon-website 中，更新所有公开的发布入口：
    • 将 Paimon 和 PyPaimon 的源码归档包、校验和、签名以及当前依赖示例添加到 community/docs/downloads.md。
    • 创建或更新相应的 community/docs/releases/release-${DOC_VERSION}.md 发布说明。 其 version front matter 必须等于 PAIMON_VERSION，其 weight 必须使其在发布 列表中处于正确位置。
    • 将 DOC_VERSION 添加到 src/app/components/header/header.component.ts 中的 versions 列表。如果菜单 保留固定数量的版本，移除最旧的条目。
    • 运行 pnpm build 解析发布元数据并构建网站。
  3. 部署后，先验证所有公开入口，再发送公告：
    • https://paimon.apache.org/docs/${DOC_VERSION}/ 提供已发布的文档，且版本切换器 将其标识为 stable；
    • 首页 DOCUMENT 菜单在桌面端和移动端都包含 DOC_VERSION；
    • https://paimon.apache.org/downloads/ 列出两个签名的源码发布包；
    • https://paimon.apache.org/releases/${PAIMON_VERSION} 展示发布说明。

当 ASF 镜像、Maven Central、PyPI、带版本的文档以及项目网站全部就绪后，使用 @apache.org 邮箱向 dev@paimon.apache.org 和 announce@apache.org 发布公告。

必要时从 ASF 在线分发区移除被取代的旧版本；它们仍然可以从 Apache 归档 获取。

关于投票人的检查清单，参见验证发布候选版本。
