Data Evolution

概述​

Paimon 支持 schema 演进,允许你添加、修改或删除列的 schema。Data Evolution 模式在此基础上为 append 表做了扩展:允许在不重写整个数据文件的情况下更新 部分列。被更新的列数据会写入新文件,并在读取时与原始数据合并。

Data Evolution 模式具有以下优势:

  • 高效的部分列更新:只更新部分列,避免重写未涉及列的 I/O 开销。
  • 减少文件重写:回填或演进数据时,将新的列数据追加到专用文件中。
  • 删除支持:通过 deletion vector 记录行删除,而无需重写已有列文件。
  • 优化的读取:在读取时合并原始列文件和更新后的列文件。

要启用 Data Evolution,创建一张 append 表,并将 row-tracking.enabled 和 data-evolution.enabled 都设置为 true。

  • Spark SQL
  • Flink SQL
  • Python API
CREATE TABLE target_table (id INT, b INT, c INT) TBLPROPERTIES (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

INSERT INTO target_table VALUES (1, 1, 1), (2, 2, 2);
CREATE TABLE target_table (id INT, b INT, c INT) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

INSERT INTO target_table VALUES (1, 1, 1), (2, 2, 2);
import pyarrow as pa

from pypaimon import CatalogFactory, Schema

catalog_options = {"warehouse": "/path/to/warehouse"}
catalog = CatalogFactory.create(catalog_options)
catalog.create_database("default", True)

pa_schema = pa.schema([
    ("id", pa.int32()),
    ("b", pa.int32()),
    ("c", pa.int32()),
])
schema = Schema.from_pyarrow_schema(
    pa_schema,
    options={
        "row-tracking.enabled": "true",
        "data-evolution.enabled": "true",
    },
)
catalog.create_table("default.target_table", schema, False)

table = catalog.get_table("default.target_table")
builder = table.new_batch_write_builder()
write = builder.new_write()
commit = builder.new_commit()
write.write_arrow(pa.Table.from_pydict(
    {"id": [1, 2], "b": [1, 2], "c": [1, 2]},
    schema=pa_schema,
))
commit.commit(write.prepare_commit())
write.close()
commit.close()

紧凑的 Write-Column 元数据​

带有专用 BLOB 或 vector 文件的表,通常会在每个普通文件的元数据中重复记录 完整的非专用列列表。对于宽表,可以将 data-evolution.write-cols-optimization.enabled 设为 true 来省略这份冗余 列表。此时缺失的 writeCols 值表示该文件包含所有非专用列;专用文件仍会 显式记录自己的列。

该选项只影响新写入,默认关闭。读取端无需任何读取选项即可同时支持两种 表示。在启用该选项之前,请把所有访问该表的读取端和维护作业升级到支持 紧凑表示的版本,因为旧版本读取端会把缺失的 writeCols 值解释为包含表的 全部列。请通过 ALTER TABLE 持久化该选项(或在建表时设置),以便文件 schema 版本记录这种紧凑表示。在将读取端回滚到旧版本之前,请重写使用该 选项生成的文件,或者保持这些读取端已升级。

部分列更新​

你可以使用 Spark SQL 的 UPDATE 或 MERGE INTO、Flink 的 data_evolution_merge_into 过程,或 PyPaimon 的表更新 API 来更新选定的列。 只有被更新的列会写出文件;未涉及的列保留在其原始文件中。

  • Spark SQL
  • Flink SQL
  • Python API
UPDATE target_table SET b = b + 10 WHERE id = 1;

CREATE TABLE source_table (id INT, b INT);
INSERT INTO source_table VALUES (1, 11), (2, 22);

MERGE INTO target_table AS t
USING source_table AS s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.b = s.b;

SELECT * FROM target_table;
+----+----+----+
| id | b  | c  |
+----+----+----+
| 1  | 11 | 1  |
| 2  | 22 | 2  |
+----+----+----+

Flink 目前不支持 MERGE INTO 语法,请改用 data_evolution_merge_into 过程:

CREATE TABLE source_table (id INT, b INT);
INSERT INTO source_table VALUES (1, 11), (2, 22);

CALL sys.data_evolution_merge_into(
    'default.target_table',
    '',
    '',
    'source_table',
    'source_table.id=target_table.id',
    'b=source_table.b',
    2
);

SELECT * FROM target_table;
+----+----+----+
| id | b  | c  |
+----+----+----+
| 1  | 11 | 1  |
| 2  | 22 | 2  |
+----+----+----+

PyPaimon 提供了类似 UPDATE 的表更新 API。它接受一个 Predicate 作为 WHERE 条件,以及字面量赋值作为 SET 子句。

table = catalog.get_table("default.target_table")

builder = table.new_batch_write_builder()
table_update = builder.new_update()
predicate = table_update.new_predicate_builder().is_in("id", [1, 2])

messages = table_update.update_by_predicate(predicate, {"b": 100})

commit = builder.new_commit()
commit.commit(messages)
commit.close()

注意事项:

  • Spark SQL 支持对 Data Evolution 表执行独立的 UPDATE 语句。
  • 并发执行、且更新同一数据文件和列的 Spark SQL UPDATE 语句可能会被 自动重试。使用 spark.paimon.write.data-evolution.update-conflict-retry.max-attempts 配置重试次数,使用 spark.paimon.write.data-evolution.update-conflict-retry.wait-ms 配置重试等待时间。
  • 如果 Spark SQL MERGE INTO 已将常规部分列文件暂存,而并发 compaction 在此期间改变了 row-ID 的文件边界,Spark 会在提交前把这些暂存文件重定位 (rebase)到最新边界上,而不是重新执行 MERGE 的源端扫描和 join。Spark 使用分布式 DataFrame 处理来执行这次重写,因此仅针对 PyPaimon 的 data-evolution.row-id-conflict-rewrite.max-size 限制不适用。当启用了 deletion vector,或暂存了已有行的 BLOB、VECTOR 文件时,该恢复机制不 适用;它也不会掩盖逻辑上的并发更新冲突。
  • 在 Spark SQL 中,MERGE INTO 对 Data Evolution 表支持 WHEN NOT MATCHED BY SOURCE 的删除动作。
  • Flink 的 data_evolution_merge_into 过程目前支持更新或插入列,但不 支持插入新行。

删除​

Data Evolution 表可以使用 deletion vector 记录被删除的行,而无需重写已有 列文件。要写入删除,请在启用 row tracking 和 Data Evolution 的同时启用 deletion vector:

注意

使用 deletion vector 删除行不会立即物理移除原始数据。Data Evolution 的 compaction 会保留 row ID 和逻辑删除,因此不会物化被删除的行。旧选项 data-evolution.compaction.rewrite-row-ids 已不再支持。请使用 materialize_deletion_vectors 过程将 deletion vector 应用到表的最新状态 并替换受影响的文件。历史快照和 tag 可能仍引用被替换的文件;回收它们的 存储需要等待这些引用过期、并由快照过期机制移除这些文件。

Flink 和 Spark 暴露相同的过程:

CALL sys.materialize_deletion_vectors(`table` => 'default.target_table');

该过程可以将重写限制在选定的分区内。partitions 和 where 不能同时使用:

CALL sys.materialize_deletion_vectors(
    `table` => 'default.target_table',
    partitions => 'dt=2026-08-12');

CALL sys.materialize_deletion_vectors(
    `table` => 'default.target_table',
    `where` => 'dt >= 20260801');

物化会重写受影响的数据,为存活的行分配新的 row ID,移除已应用的 deletion vector,并删除受影响的 Global Index。因此,持久化了 _ROW_ID 值的消费方必须与该操作做好协调。对受影响 row-ID 区间的并发修改会导致 该过程失败,而不会提交过期的结果。目前不支持物化 vector 存储文件。

Spark 会以有界的批次持续处理,直到所有匹配的 deletion vector 都被物化。 为了让 Flink 作业保持有界,一次 Flink 过程调用只处理一个批次,软目标为 100,000 条 deletion vector。相互重叠的 row-ID 组成部分不会被拆分,因此 可能超过该目标。请反复调用 Flink 过程,直到某次调用不再产生任何变更。

CREATE TABLE target_table (id INT, b INT, c INT) TBLPROPERTIES (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true',
    'deletion-vectors.enabled' = 'true'
);

Spark SQL 支持对 Data Evolution 表执行 DELETE FROM:

DELETE FROM target_table WHERE id = 1;

Spark SQL 也支持 MERGE INTO 中的删除动作:

CREATE TABLE source_table (id INT, op STRING);
INSERT INTO source_table VALUES (2, 'delete'), (3, 'update');

MERGE INTO target_table AS t
USING source_table AS s
ON t.id = s.id
WHEN MATCHED AND s.op = 'delete' THEN DELETE
WHEN MATCHED AND s.op = 'update' THEN UPDATE SET t.b = t.b + 10
WHEN NOT MATCHED BY SOURCE AND t.id > 10 THEN DELETE;

WHEN NOT MATCHED BY SOURCE 子句需要 Spark 3.4 或更高版本。

使用 Flink 1.17 或更高版本时,SQL 在批模式下支持对 Data Evolution 表执行 DELETE FROM。对于行级谓词,匹配的行会被记录到 deletion vector 中, 因此数据文件不会被重写:

DELETE FROM target_table WHERE id = 1;

Flink 用户还可以提交 delete action。

自更新(Self Updates)​

自更新会就地转换已有列的值。在 Flink SQL 中,基于 $row_tracking 系统表 创建一个临时源视图,并按 _ROW_ID 关联。在 PyPaimon 中,使用分片扫描 + 重写的工作流读取已有值,并把派生列写回。

  • Flink SQL
  • Python API
CREATE TEMPORARY VIEW source_view AS
SELECT _ROW_ID, b + c AS b
FROM default.target_table$row_tracking;

CALL sys.data_evolution_merge_into(
    'default.target_table',
    'TempT',
    '',
    'source_view',
    'TempT._ROW_ID=source_view._ROW_ID',
    'b=source_view.b',
    2
);
import pyarrow as pa

table = catalog.get_table("default.target_table")

builder = table.new_batch_write_builder()
table_update = builder.new_update()
table_update.with_read_projection(["b", "c"])
table_update.with_update_type(["b"])

updater = table_update.new_shard_updator(0, 1)
reader = updater.arrow_reader()
for batch in iter(reader.read_next_batch, None):
    b = batch.column("b").to_pylist()
    c = batch.column("c").to_pylist()
    updater.update_by_arrow_batch(pa.RecordBatch.from_pydict(
        {"b": [bi + ci for bi, ci in zip(b, c)]},
        schema=pa.schema([("b", pa.int32())]),
    ))

messages = updater.prepare_commit()
commit = builder.new_commit()
commit.commit(messages)
commit.close()

自更新注意事项:

  • 在 Flink 过程中,源表名和目标表名不能相同。请创建一个临时视图作为源。
  • 在 Flink 中使用 view._ROW_ID = source._ROW_ID 来标识自合并模式。
  • 在 SQL 中,_ROW_ID 只能通过 $row_tracking 系统表获取。
  • 自合并只支持 WHEN MATCHED THEN UPDATE 语义。

文件组规范​

通过 row-id 元数据,文件被组织成一个个文件组。

写入时,Data Evolution 的更新路径只把指定的更新列写入新文件,原始数据 文件保持不变。

读取时,Paimon 同时读取原始数据文件和包含更新列数据的新文件,并把具有 相同 first row id 的文件合并起来,呈现出表的统一视图。

  • 通过优化的合并处理保持高效的读取性能。
  • 只有被更新的列才会写入新文件,磁盘空间利用更高效。
