Ray Data

这需要安装 ray。

pypaimon.ray 暴露了顶层的 read_paimon / write_paimon 门面函数, 直接接受表标识符和 catalog 选项,形态上与 Ray 内置的 Iceberg 集成 保持一致。更底层的 TableRead.to_ray() 和 TableWrite.write_ray() 入口仍可供已解析出 (read_builder, splits) 对或通过常规 pypaimon API 构建了 table_write 的调用方使用。

如果你的应用使用 Daft DataFrame,且只需要 Ray 作为 Daft 的执行 后端,参见在 Ray 上运行 Daft。

读取​

read_paimon(推荐)​

from pypaimon.ray import read_paimon

ray_dataset = read_paimon(
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
)

print(ray_dataset)
# MaterializedDataset(num_blocks=1, num_rows=9, schema={f0: int32, f1: string})

print(ray_dataset.take(3))
# [{'f0': 1, 'f1': 'a'}, {'f0': 2, 'f1': 'b'}, {'f0': 3, 'f1': 'c'}]

print(ray_dataset.to_pandas())
#    f0 f1
# 0   1  a
# 1   2  b
# 2   3  c
# 3   4  d
# ...

read_paimon 会自行打开 catalog 并解析表,因此它是四步样板代码 CatalogFactory.create → get_table → new_read_builder → to_ray 的一次调用等价物。

投影和 limit:

ray_dataset = read_paimon(
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    projection=["id", "score"],
    limit=1000,
)

分布式 / 调度:

ray_dataset = read_paimon(
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    override_num_blocks=4,
    ray_remote_args={"num_cpus": 2, "max_retries": 3},
    concurrency=8,
)

时间旅行(Time travel):

# Read a specific snapshot.
ray_dataset = read_paimon(
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    snapshot_id=42,
)

# Read a tagged snapshot.
ray_dataset = read_paimon(
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    tag_name="release-2026-04",
)

snapshot_id 和 tag_name 互斥。

参数:

  • table_identifier:完整表名,如 "db_name.table_name"。
  • catalog_options:透传给 CatalogFactory.create() 的 kwargs, 如 {"warehouse": "/path/to/warehouse"}。
  • filter:可选的 Predicate,会下推到扫描中。
  • projection:可选的要读取的列名列表。
  • limit:可选的行数上限,在 scan planning 时生效。
  • snapshot_id:可选的时间旅行目标快照 id。与 tag_name 互斥。
  • tag_name:可选的时间旅行目标 tag 名称。与 snapshot_id 互斥。
  • override_num_blocks:可选的输出 block 数量覆盖值。 必须 >= 1。
  • ray_remote_args:可选的传给读任务中 ray.remote() 的 kwargs (如 {"num_cpus": 2, "max_retries": 3})。
  • concurrency:可选的并发运行 Ray 任务的最大数量。
  • **read_args:透传给 ray.data.read_datasource 的其他 kwargs (如 Ray 2.52.0+ 中的 per_task_row_limit)。

TableRead.to_ray()(更底层)​

如果你已经有 read_builder 和 splits,可以直接将它们转换为 Ray Dataset:

table_read = read_builder.new_read()
splits = read_builder.new_scan().plan().splits()
ray_dataset = table_read.to_ray(
    splits,
    override_num_blocks=4,
    ray_remote_args={"num_cpus": 2, "max_retries": 3},
)

to_ray() 接受与 read_paimon 相同的 override_num_blocks、ray_remote_args、 concurrency 和 **read_args 参数。

Ray Block 大小配置​

如果需要配置 Ray 的 block 大小(例如当 Paimon splits 超过 Ray 默认的 128MB block 大小时),在调用 read_paimon 或 to_ray 之前,在 DataContext 上设置:

from ray.data import DataContext

ctx = DataContext.get_current()
ctx.target_max_block_size = 256 * 1024 * 1024  # 256MB (default is 128MB)

更多细节参见 Ray Data API 文档。

写入​

write_paimon(推荐)​

import ray
from pypaimon.ray import write_paimon

ray_dataset = ray.data.read_json("/path/to/data.jsonl")

write_paimon(
    ray_dataset,
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
)

write_paimon 会自行打开 catalog、解析表,并通过 Ray 的 Datasink API 提交写入——没有单独的 prepare_commit 或 close 步骤需要执行。

覆盖(Overwrite)模式:

write_paimon(
    ray_dataset,
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    overwrite=True,
)

分布式 / 调度:

write_paimon(
    ray_dataset,
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    concurrency=4,
    ray_remote_args={"num_cpus": 2},
)

HASH_FIXED 预聚簇(pre-clustering):

HASH_FIXED 行总是由 writer 分配到正确的 Paimon bucket。 对于 append-only 表,预聚簇只是一种文件数量 优化。主键表还要求每个 (partition_keys..., bucket) 组 对应一个 writer,以生成有序的 sequence number。

默认情况下,write_paimon 写入 append-only HASH_FIXED 表时 不做预聚簇。这避免了 Ray 的 groupby().map_groups() 把整个 (partition_keys..., bucket) 组物化到一个 Ray 节点上。

HASH_FIXED 主键表拒绝 default/off 模式。直接的 Ray 写入可能把同一个 bucket 发给多个 writer 任务,而这些 writer 可能分配出重叠的 sequence number。显式的 map_groups 模式通过为每个完整的 (partition_keys..., bucket) 组运行一个 writer 来避免这种情况。

如果每个 (partition_keys..., bucket) 组都能放入单个 Ray 节点的内存,你可以选择启用遗留的小文件优化:

write_paimon(
    ray_dataset,
    "database_name.table_name",
    catalog_options={"warehouse": "/path/to/warehouse"},
    hash_fixed_precluster="map_groups",
)

hash_fixed_precluster="map_groups" 按 (partition_keys..., bucket) 对行分组。对于主键表,Paimon writer 在该 map_groups() 任务内运行,并返回序列化的 commit 消息交给 driver 提交。因此 Ray 的输出 block 切分 无法为同一个组创建多个 writer。该模式继承 Ray map_groups() 的内存限制。大 append-only bucket 或热点 append-only 分区应使用默认模式或 hash_fixed_precluster="off"。

对于非 HASH_FIXED 的 append-only 表,dataset 按原样写入。 Postpone-bucket 表(bucket = -2)遵循 postpone.batch-write-fixed-bucket(默认:true)。已有分区 复用其 bucket 数;新分区根据配置的目标 行数或大小推断 bucket 数。Ray 会为这个全局计划物化输入,然后 按分区、bucket 和主键哈希排序。一个主键始终对应一个 writer,而一个大 bucket 可以跨多个 Ray block。设置 hash_fixed_precluster="off" 可保留 bucket-postpone 写入。Fixed-bucket postpone 写入仅支持 bucket-function.type=default。HASH_DYNAMIC 和 CROSS_PARTITION 主键 Ray 写入不受支持,会快速失败, 包括默认的动态 bucket 主键表(bucket = -1)。 Ray 写入任务会创建独立的 Paimon writer,在这些模式下可能分配出 重叠的 bucket 或 sequence number。

参数:

  • dataset:要写入的 Ray Dataset。
  • table_identifier:完整表名,如 "db_name.table_name"。
  • catalog_options:透传给 CatalogFactory.create() 的 kwargs。
  • overwrite:若为 True,覆盖表中已有数据。
  • concurrency:可选的并发运行 Ray 写任务的最大数量。 对于 HASH_FIXED 主键和 postpone-bucket 写入,它限制 writer 任务数。
  • ray_remote_args:可选的传给写任务中 ray.remote() 的 kwargs (如 {"num_cpus": 2})。这些选项同样作用于 HASH_FIXED 主键和 postpone-bucket writer 任务。
  • hash_fixed_precluster:预聚簇模式。"auto" 遵循表选项, "off" 禁用预聚簇,"map_groups" 显式启用 HASH_FIXED 分组。该选项不会启用 HASH_DYNAMIC 或 CROSS_PARTITION 主键写入。

TableWrite.write_ray()(更底层)​

如果你已经从 write builder 构建了 table_write,可以把 Ray Dataset 直接交给它。write_ray() 使用与顶层 write_paimon() API 相同的 HASH_FIXED 预聚簇模式和安全检查。 它通过 Ray Datasink API 提交,因此 Ray 写入本身没有 prepare_commit / commit 步骤需要执行——用完后关闭 writer 即可:

import ray

table = catalog.get_table('database_name.table_name')

# 1. Create table write.
table_write = table.new_batch_write_builder().new_write()

# 2. Write Ray Dataset
ray_dataset = ray.data.read_json("/path/to/data.jsonl")
table_write.write_ray(
    ray_dataset,
    overwrite=False,
    concurrency=2,
    hash_fixed_precluster="auto",
    static_partition=None,
)
# Parameters:
#   - dataset: Ray Dataset to write
#   - overwrite: Whether to overwrite existing data (default: False)
#   - concurrency: Optional max number of concurrent Ray tasks
#   - ray_remote_args: Optional kwargs passed to ray.remote() (e.g., {"num_cpus": 2})
#   - hash_fixed_precluster: Same HASH_FIXED modes and primary-key safety
#     checks as write_paimon()
#   - static_partition: Optional partition spec to overwrite. When set,
#     write_ray() runs in overwrite mode for this partition.

# 3. Close resources
table_write.close()

显式的 new_postpone_fixed_bucket_write_builder() 也可以在不设置 hash_fixed_precluster 的情况下启用 real-bucket 路径。

覆盖(Overwrite)​

顶层 write_paimon() API 通过上面的 overwrite=True 标志支持整表覆盖。使用更底层的 write_ray() API 时,你可以 用 overwrite=True 做整表覆盖,用 static_partition={...} 做 分区覆盖:

table_write.write_ray(ray_dataset, overwrite=True)
table_write.write_ray(ray_dataset, static_partition={'dt': '2024-01-01'})

使用更底层的 builder API 时,你也可以在 write builder 本身上配置覆盖模式。 生成的 table_write 会带着覆盖 分区进入 write_ray()。直接传给 write_ray() 的 static_partition 参数会覆盖 builder 级别的分区:

# overwrite whole table
table_write = table.new_batch_write_builder().overwrite().new_write()
table_write.write_ray(ray_dataset)

# overwrite partition 'dt=2024-01-01'
table_write = (
    table.new_batch_write_builder()
    .overwrite({'dt': '2024-01-01'})
    .new_write()
)
table_write.write_ray(ray_dataset)

Bucket Join​

bucket_join 将两张**同桶(co-bucketed)**表(相同 bucket 数和相同 bucket-key)按 bucket-key 关联,不做全局 shuffle:相同的 key 落在 两侧相同的 bucket 中,因此每个 bucket 在各自的 Ray 任务中独立读取和关联。它返回一个 ray.data.Dataset,结果保持分布式(绝不 拉取到 driver)。

一个常见用途是,在不与大表做 shuffle join 的情况下,为一批 key 查找 全局 _ROW_ID:维护一张小的同桶 (key, _ROW_ID) 侧表,用 bucket_join 把传入的 key 与它关联,然后把得到的 row id 送入 row-id 更新。

from pypaimon.ray import bucket_join

ds = bucket_join(
    left="database_name.incoming_keys",   # co-bucketed table identifier
    right="database_name.key_rowid",       # co-bucketed table identifier
    catalog_options={"warehouse": "/path/to/warehouse"},
    on="url",                              # must equal the bucket-key
    left_projection=["url"],               # optional; must keep the join key
    right_projection=["url", "row_id"],    # optional; must keep the join key
)
# ds: ray.data.Dataset of the joined rows, e.g. {"url": ..., "row_id": ...}

参数:

  • left / right:待关联的两张同桶表的标识符。
  • on:join key。必须恰好是 bucket-key——只有按 bucket-key 关联时, 相等的 key 才会按 bucket 共置。
  • left_projection / right_projection:可选的读取时应用的列投影。 如果提供,每个都必须包含 join key。
  • join_type:仅支持 "inner"(outer join 需要 bucket 的并集, 而逐 bucket 的交集无法产生)。
  • ray_remote_args:应用到每个逐 bucket join 任务的 Ray remote 选项。

**返回:**关联行的 ray.data.Dataset。

注意:

  • 两张表都必须是 fixed-bucket(bucket > 0),且 bucket 数和 bucket-key 相同(列名、顺序和类型都相同);否则 bucket_join 会抛错。对于未显式设置 bucket-key 的主键表, bucket-key 解析为(裁剪分区后的)主键。
  • 两侧除 join key 外不得有其他同名列,否则 底层 pyarrow join 会撞名冲突;可用 left_projection / right_projection 先把这些列裁剪掉。
  • 每一侧都按其最新快照规划,一个 bucket 由 一个 Ray 任务完成关联,该任务会把整个 bucket 读入内存。请选择合适的 bucket 数, 让 key 均匀分布,避免倾斜、占内存大的任务。
  • 尚不支持分区表(bucket id 是分区内的)。

Range Join​

range_join 关联按第一个 join key 聚簇的表,无需全局 shuffle。每个 key range 在一个 Ray 任务中运行。

from pypaimon.ray import range_join

ds = range_join(
    left="database_name.incoming_keys",
    right="database_name.key_rowid",
    catalog_options={"warehouse": "/path/to/warehouse"},
    left_on="url",
    right_on="lookup_url",
    left_projection=["url"],
    right_projection=["lookup_url", "row_id"],
    left_partitions={"dt": "2026-07-30"},  # optional
    num_ranges=64,                          # optional
)

当 key 名一致时使用 on="url"。支持多个 key;第一个 定义 range。仅支持 inner join。

优先使用 manifest/key 统计信息;Parquet footer 作为兜底。缺失 统计信息会安全地降低并行度,可能降为单个任务。未聚簇的文件可能被 重复读取。不支持 float/double 和本地时区时间戳的 range key。

Merge Into​

merge_into 从源更新或删除data-evolution表中的匹配行,并可选择插入不匹配 行,类似 SQL 的 MERGE INTO。 匹配行通过 _ROW_ID 原地更新;只有涉及的列会被 重写。匹配的 delete 子句通过 deletion vectors 写入。 要求 ray >= 2.50,且目标表设置了 'data-evolution.enabled' 和 'row-tracking.enabled'。如果使用匹配的 delete 子句,目标 表还必须启用 'deletion-vectors.enabled'。

from pypaimon.ray import merge_into, WhenMatched, WhenNotMatched

metrics = merge_into(
    target="database_name.table_name",
    source=ray_dataset,          # ray.data.Dataset / pa.Table / pandas / table-name str
    catalog_options={"warehouse": "/path/to/warehouse"},
    on=["id"],                   # or {"target_col": "source_col"} for renamed keys
    when_matched=[WhenMatched.update("*")],
    when_not_matched=[WhenNotMatched(insert="*")],             # optional
)
print(metrics)   # {"num_matched": 3, "num_inserted": 2, "num_unchanged": 0}

带条件的子句过滤要作用于哪些匹配/不匹配行:

merge_into(
    target="db.table",
    source=source_ds,
    catalog_options=catalog_options,
    on=["id"],
    when_matched=[WhenMatched.update("*", condition="s.age > t.age")],
    when_not_matched=[WhenNotMatched(insert="*", condition="s.age > 18")],
)

使用 WhenMatched.delete() 删除匹配行:

merge_into(
    target="db.table",
    source=source_ds,
    catalog_options=catalog_options,
    on=["id"],
    when_matched=[
        WhenMatched.delete(condition="s.deleted = TRUE"),
        WhenMatched.update("*"),
    ],
)

条件使用 SQL 风格的表达式,用 s.(源)和 t.(目标) 列前缀。WhenNotMatched 条件只能引用源 列(s.*)。条件求值使用 PyPaimon DataFusion extra。 要求 Python 3.10 或更高版本。通过 pip install 'pypaimon[datafusion]' 安装。

  • update / delete / insert:WhenMatched.update(...) 更新匹配 行,WhenMatched.delete() 删除匹配行, WhenNotMatched(insert=...) 插入不匹配行。"*" 从源更新/插入 所有列,包括 blob 列。 映射可选择特定列: 
    from pypaimon.ray import source_col, target_col, lit

    WhenMatched.update({"age": source_col("age"), "name": target_col("name")})
    WhenMatched.delete()
    WhenNotMatched(insert={"id": source_col("id"), "status": lit("new")})
    "s.<col>" / "t.<col>" 简写同样有效(t.* 仅用于 update)。 对以 s. 或 t. 开头的字面量使用 lit()。
  • condition:可选的 SQL 风格布尔表达式。用 s.<col> 和 t.<col> 引用源列和目标列。
  • 多个子句按顺序求值,第一个命中的条件生效: 
    when_matched=[
        WhenMatched.update("*", condition="s.ts > t.ts"),
        WhenMatched.update("*"),  # fallback for unmatched rows
    ]

对于自合并(source == target 且 on=["_ROW_ID"]),update 值 也可以是 callable。callable 收到匹配行的 read_columns 加上 _ROW_ID(以 pyarrow.Table 形式),且必须对每行返回一个 pyarrow.Array 或 pyarrow.ChunkedArray 值:

import pyarrow.compute as pc

merge_into(
    target="db.table",
    source="db.table",
    catalog_options=catalog_options,
    on=["_ROW_ID"],
    read_columns=["age"],
    when_matched=[WhenMatched.update({
        "age": lambda rows: pc.add(rows["age"], 1),
    }, condition="t.id IN (1, 3)")],
)

callable 可能运行零次、一次或多次,必须是确定性的、 无副作用的、行局部的。一般的 source-target 合并不支持 callable。

参数:

  • source:ray.data.Dataset、pyarrow.Table、pandas.DataFrame,或 Paimon 表标识符字符串。传字符串时,会以相同的 catalog_options 在最新快照读取该表。
  • on:key 列,或 {target_col: source_col}(用于重命名的 key)。
  • read_columns:传给 callable 自合并赋值的列。当 update 映射包含 callable 时必填;否则必须省略。
  • num_partitions:join 和写入的 shuffle 并行度。当输入 内存字节大小元数据可靠时,默认值以 Ray 最大 block 大小为目标。否则使用 Ray 的 hash-shuffle 默认值。非空目标 表会把该默认值作为下限,集群 CPU 数则封顶结果。自合并 保留其基于 CPU 的默认值。显式设置以覆盖默认值。
  • ray_remote_args:应用到 merge 的 map/group 任务 (update/delete transform、group write、insert transform)的 Ray remote 选项。
  • concurrency:insert sink 的调度参数。

返回:{"num_matched", "num_inserted", "num_unchanged"}。num_matched 统计实际更新或删除的行数(条件过滤之后)。 当前实现中 num_unchanged 为 0。

Blob 表上端到端的特征更新工作流,参见 使用 Ray 进行分布式特征回填。

注意:

  • 分区键列不能被匹配的 update 子句更新,因为 未实现跨分区行移动。匹配的 delete 子句和 非分区列的匹配 update 可用于分区表。 向分区表做 not-matched insert 正常工作。
  • 匹配的 delete 子句要求 deletion-vectors.enabled = true。
  • Blob 列可以被 merge_into 更新和插入。使用 update="*" 或 insert="*" 时,源必须包含对应的 blob 列。 如果 insert 映射省略了某个 blob 列,该列将写为 NULL。

Update By Row Id​

update_by_row_id 从一个已经携带 _ROW_ID 和新值的源,直接更新 data-evolution表的列。每一行被路由到 拥有其 row id 的数据文件,且只重写这些文件——目标表 从不被全量读取,也不做针对它的 join(不同于 merge_into(on=["_ROW_ID"]),后者会读取并 shuffle-join 整个目标表)。它 与 bucket_join 搭配使用,后者无需 shuffle 就能产出 row id。要求 ray >= 2.50,且目标表启用 data-evolution.enabled 和 row-tracking.enabled。

from pypaimon.ray import update_by_row_id

metrics = update_by_row_id(
    target="database_name.table_name",
    source=ray_dataset,          # ray.data.Dataset / pa.Table / pandas, carrying _ROW_ID
    catalog_options={"warehouse": "/path/to/warehouse"},
    update_cols=["feature"],     # non-blob columns to overwrite
)
print(metrics)   # {"num_updated": 50}

参数:

  • source:携带目标 _ROW_ID 及 update_cols 中每一列的 ray.data.Dataset、pyarrow.Table 或 pandas.DataFrame;多余列会被忽略, 值会强转为目标列类型。不接受表名作为 source: 表的系统 _ROW_ID 属于它自己,无法寻址目标表的行。
  • update_cols:要覆盖的非 blob 列。必须非空。
  • num_partitions:按目标文件对更新行分组的并行度。 默认值在有可靠源元数据时使用元数据;否则使用 Ray 的 hash-shuffle 默认值。目标文件数和集群 CPU 数会约束结果。
  • ray_remote_args:应用到更新任务的 Ray remote 选项。

返回:{"num_updated": <rows>}。

注意:

  • row id 必须存在于目标表的当前快照中;过期或不属于目标表的 _ROW_ID 会抛错,而不是静默写入。
  • 多个源行映射到同一个 _ROW_ID 会被拒绝——先去重。
  • Blob 列不能通过这条路径更新。
  • 分区列不能更新(原地重写无法把行移动到其他分区)。
  • 尚不支持启用 deletion-vectors 的表:被 DV 删除的行仍存活在 其数据文件中,不读取目标表就无法与存活的行区分。

Read By Row Id​

read_by_row_id 是 update_by_row_id 的读取侧对应物:它针对一组 _ROW_ID 读取 data-evolution 表的列(包括 blob),而无需 扫描或 join 整个目标表。每个 row id 被路由到拥有它的数据文件, 只读取这些文件——且只读取匹配的行。它与 bucket_join(产出 row id)搭配,并为 update_by_row_id 提供输入:按 key 匹配 → 读取匹配行 → 转换 → 按 row id 写回。要求 ray >= 2.50,且目标表启用 data-evolution.enabled 和 row-tracking.enabled。

from pypaimon.ray import read_by_row_id

ds = read_by_row_id(
    target="database_name.table_name",
    row_ids=locator_ds,          # ray.data.Dataset / pa.Table / pandas, carrying the row ids
    catalog_options={"warehouse": "/path/to/warehouse"},
    projection=["image", "feature"],   # columns to read; may include blob columns
    row_id_col="row_id",         # source column holding the row ids (default "_ROW_ID")
)
# ds: ray.data.Dataset of (image, feature, _ROW_ID) for the matched rows

参数:

  • row_ids:在 row_id_col 列中携带目标 row id 的 ray.data.Dataset、pyarrow.Table 或 pandas.DataFrame;其他列被忽略。 不接受表名作为 source(表的系统 _ROW_ID 属于它自己,无法寻址目标表)。
  • projection:要读取的顶层列(不支持嵌套路径)。Blob 列 会解析为其 payload,除非通过 dynamic_options 覆盖。必须非空。
  • row_id_col:携带 row id 的源列(默认 _ROW_ID);例如设置 row_id_col="row_id" 可直接消费 bucket_join 的 locator。
  • dynamic_options:通过 table.copy 应用的读取选项,如 {"blob-as-descriptor": "true"} 可把 blob 列读取为小的 BlobDescriptor 字节 (稍后通过 map_with_blobs 解析),或用 scan.snapshot-id / scan.tag-name 读取特定快照。会翻转表不变量的选项(data-evolution.enabled、 row-tracking.enabled、deletion-vectors.enabled)会被拒绝。
  • num_partitions:按目标文件对 row id 分组的并行度。默认值 在有可靠源元数据时使用元数据;否则使用 Ray 的 hash-shuffle 默认值。目标文件数和集群 CPU 数约束结果。
  • ray_remote_args:应用到读取任务的 Ray remote 选项。

返回:(*projection, _ROW_ID) 的 ray.data.Dataset。

注意:

  • 查找/集合语义,类似 SQL ... WHERE _ROW_ID IN (...):每个去重后的 匹配 row id 返回一行(重复项被去重),不保留输入顺序(输出 按所属文件分组)。空源会产出空的、但类型正确的 Dataset。
  • row id 必须存在于解析出的目标快照(最新快照,或通过 dynamic_options 选择的快照)中;不属于目标表的 _ROW_ID 会抛错。
  • 尚不支持启用 deletion-vectors 的表,原因与 update_by_row_id 相同。
  • 对于非空目标表,row_ids 源由下游 action 惰性消费,而不是在这里读取。缺少 row_id_col 的惰性源 会在读取真正运行时抛错(已物化的源则会提前抛错)。

Process Row Id Ranges​

process_row_id_ranges 将最新快照规划为逻辑文件组,并对 每个达到目标大小的批次同步调用用户提供的 processor。 processor 收到一个 List[Range],并全权负责读取、分布式计算、 提交和重试策略。基础文件与重叠的 data-evolution、BLOB 或 VECTOR 文件保持在同一个不可分割的组中。

因此 rows_per_commit 是目标值而不是硬性上限:该函数 绝不拆分文件组,所以一个批次可能包含更多行。range 计划在 一次运行开始时捕获一次,回调按 row-id 顺序执行, 异常会中止后续回调。

从 BLOB 列做可恢复的 embedding 回填​

下面的模式读取 image BLOB,用 Ray 计算可空的 embedding VECTOR,每次提交约一百万个 row id。它把 embedding IS NULL 下推到每个 range 扫描中,因此已完成的行会在 其 image payload 被物化之前就被过滤掉。失败后重新运行整个函数; 已提交的 range 会被自动跳过。

import pyarrow as pa

from my_embedding_model import load_model
from pypaimon import CatalogFactory
from pypaimon.ray import process_row_id_ranges, update_by_row_id

TARGET = "database_name.images"
CATALOG_OPTIONS = {"warehouse": "/path/to/warehouse"}
EMBEDDING_DIM = 768


class EmbedImages:
    def __init__(self):
        # Constructed once in every Ray actor, not once per Arrow batch.
        self.model = load_model()

    def __call__(self, batch: pa.Table) -> pa.Table:
        vectors = self.model.encode(batch["image"].to_pylist())
        return pa.table({
            "_ROW_ID": batch["_ROW_ID"],
            "embedding": pa.array(
                vectors.tolist(),
                type=pa.list_(pa.float32(), EMBEDDING_DIM),
            ),
        })


def process_ranges(ranges):
    # Resolve a fresh table for every batch so this scan sees embeddings
    # committed by earlier callbacks. Force BLOB payloads rather than descriptors.
    table = (
        CatalogFactory.create(CATALOG_OPTIONS)
        .get_table(TARGET)
        .copy({"blob-as-descriptor": "false"})
    )
    read_builder = table.new_read_builder().with_projection(
        ["image", "embedding", "_ROW_ID"]
    )
    read_builder.with_filter(
        read_builder.new_predicate_builder().is_null("embedding")
    )
    splits = (
        read_builder.new_scan()
        .with_row_ranges(ranges)
        .plan()
        .splits()
    )
    pending = read_builder.new_read().to_ray(
        splits,
        concurrency=64,
        ray_remote_args={"num_cpus": 1},
    )
    if pending.limit(1).count() == 0:
        return

    updates = pending.map_batches(
        EmbedImages,
        batch_format="pyarrow",
        batch_size=128,
        concurrency=8,       # required for a callable-class Ray actor pool
        num_gpus=1,
    )

    # update_by_row_id executes the Ray pipeline and makes one Paimon commit.
    # It is valid for VECTOR/ARRAY embedding columns; BLOB columns themselves
    # cannot be updated through update_by_row_id.
    update_by_row_id(
        target=TARGET,
        source=updates,
        catalog_options=CATALOG_OPTIONS,
        update_cols=["embedding"],
        num_partitions=128,
    )


process_row_id_ranges(
    TARGET,
    CATALOG_OPTIONS,
    rows_per_commit=1_000_000,
    processor=process_ranges,
)

目标表必须启用 row-tracking.enabled 和 data-evolution.enabled;embedding 必须可空,且表不能 启用 deletion vectors。如果源 BLOB 或 embedding 模型可能变化, 请使用额外的 source/model-version 列,而不是把每个 非空 embedding 都当作永久完成的。process_row_id_ranges 本身不会 重试失败的 processor——本例中的可恢复性来自 重新运行它并只选择 embedding 仍为 null 的行。
