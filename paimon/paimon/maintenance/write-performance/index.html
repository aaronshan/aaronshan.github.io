写入性能

Paimon 的写入性能与 checkpoint 密切相关,因此如果你需要更高的写入吞吐:

  1. Flink 配置('flink-conf.yaml'/'config.yaml' 或在 SQL 中使用 SET):增大 checkpoint 间隔 ('execution.checkpointing.interval'),将最大并发 checkpoint 数增大到 3 ('execution.checkpointing.max-concurrent-checkpoints'),或者干脆使用批处理模式。
  2. 增大 write-buffer-size。
  3. 开启 write-buffer-spillable。
  4. 如果你使用的是 Fixed-Bucket 模式,调整 bucket 数量。

选项 'changelog-producer' = 'lookup' or 'full-compaction' 以及选项 'full-compaction.delta-commits' 对写入性能影响很大。如果处于 snapshot/全量同步阶段,你可以先取消这些选项,然后在增量阶段再重新开启。

如果你发现在背压情况下作业的输入呈现锯齿状,可能是工作节点负载不均衡。 你可以考虑开启异步 Compaction,观察吞吐是否提升。

并行度​

建议 sink 的并行度小于或等于 bucket 数量,最好相等。你可以通过 sink.parallelism 表属性来控制 sink 的并行度。

选项 是否必填 默认值 类型 描述
sink.parallelism
 否 (none) Integer 定义 sink 算子的并行度。默认情况下,并行度由框架决定,使用与上游链式算子相同的并行度。

本地合并(Local Merging)​

如果你的作业存在主键数据倾斜 (例如,你想统计网站中每个页面的浏览次数, 而某些页面在用户中特别受欢迎), 你可以设置 'local-merge-buffer-size',使输入记录在按 bucket shuffle 并写入 sink 之前先被缓冲和合并。 当同一主键在 snapshot 之间频繁更新时,这特别有用。

缓冲区满了之后会被 flush。当你面临数据倾斜但不知道从何开始调整缓冲区大小时,建议从 64 mb 开始。

(目前,本地合并不适用于 CDC 数据摄入)

文件格式​

如果你想追求极致的 compaction 性能,可以考虑使用行存文件格式 AVRO。

  • 优点是可以获得高写入吞吐和 compaction 性能。
  • 缺点是分析查询会很慢。行存最大的问题在于没有查询投影。例如,表有 100 列但只查询其中几列时, 行存的 IO 开销无法忽视。此外,压缩效率会下降,存储成本会上升。

这是一个取舍。

通过以下选项开启行存:

file.format = avro
metadata.stats-mode = none

行存的统计信息收集开销较大,因此建议同时关闭统计信息。

如果你不想把所有文件都改成 Avro 格式,至少可以考虑把前几层的文件改成 Avro 格式。你可以使用 'file.format.per.level' = '0:avro,1:avro' 来指定前两层的文件使用 Avro 格式。

文件压缩​

默认情况下,Paimon 使用 level 1 的 zstd,你可以修改压缩算法:

'file.compression.zstd-level':zstd 默认 level 为 1。为了更高的压缩率,可以配置为 9,但读写速度会显著下降。

稳定性​

如果 bucket 数量或资源太少,full-compaction 可能导致 checkpoint 超时,Flink 默认的 checkpoint 超时时间是 10 分钟。

如果你希望在这种情况下仍然保持稳定,可以调大 checkpoint 超时时间,例如:

execution.checkpointing.timeout = 60 min

写入初始化​

在写入初始化阶段,bucket 的 writer 需要读取所有历史文件。如果这里存在瓶颈 (例如同时写入大量分区),你可以使用 sink.writer-coordinator.enabled 启用 Flink coordinator 来缓存读取的 manifest 数据,从而加速初始化。coordinator 的缓存内存为 sink.writer-coordinator.cache-memory,默认为 Job Manager 上的 2GB。

coordinator 的 manifest 缓存通常以软引用(soft references)持有条目,因此当 Job Manager 堆内存不足时 JVM 可以回收它们。但在负载很重的 Job Manager 上,这可能适得其反:JVM 回收了缓存的 manifest,writer 立即重新读取并解压它们,这项工作又把堆内存推高,触发更多回收。缓存 不断抖动,反而起不到帮助。

如果你看到这种情况,请将 sink.writer-coordinator.cache-soft-values 设置为 false。此后条目将以强引用持有, GC 永远不会回收它们,抖动循环也就无法开始。

关闭软引用后,缓存不再随 GC 收缩,但仍按权重有界:它最多占用 sink.writer-coordinator.cache-memory,超出后逐出最近最少使用的条目。请将 Job Manager 的总堆内存配置为至少该值的两倍,这样过小的堆会以 OutOfMemoryError 快速失败,而不是 静默劣化。你也可以选择设置 sink.writer-coordinator.cache-expire-after-access,同时释放空闲 一段时间的条目。

同样的 cache.manifest.soft-values / cache.manifest.max-memory 设置也适用于 catalog 的 manifest 缓存。

写入内存​

Paimon writer 占用的内存主要有三处:

  • Writer 的内存缓冲区,由单个 task 的所有 writer 共享和抢占。该内存值可以通过 write-buffer-size 表属性调整。
  • compaction 时合并多个 sorted run 所消耗的内存。可以通过 num-sorted-run.compaction-trigger 选项调整要合并的 sorted run 数量。
  • 如果单行数据很大,compaction 时一次读取过多行会消耗大量内存。减小 read.batch-size 选项可以缓解这种情况。
  • 写入列式 ORC 文件所消耗的内存。减小 orc.write.batch-size 选项可以降低 ORC 格式的内存消耗。
  • 如果在写入 task 中自动执行 compaction,某些大列的 dictionary 会在 compaction 期间显著消耗内存。
    • 要禁用 Parquet 格式所有字段的 dictionary 编码,设置 'parquet.enable.dictionary'= 'false'。
    • 要禁用 ORC 格式所有字段的 dictionary 编码,设置 orc.dictionary.key.threshold='0'。此外,设置 orc.column.encoding.direct='field1,field2' 可以禁用特定列的 dictionary 编码。

如果你的 Flink 作业不依赖状态,请避免使用 managed memory,可以通过以下 Flink 参数控制:

taskmanager.memory.managed.size=1m

或者你也可以使用 Flink managed memory 作为写缓冲区以避免 OOM,设置表属性:

sink.use-managed-memory-allocator=true

提交内存​

如果写入表的数据量特别大,Committer 节点可能会占用大量内存,内存过小 可能发生 OOM。这种情况下,你需要增大 Committer 的堆内存,但你可能不想 统一增大 Flink TaskManager 的内存,因为这可能造成内存浪费。

你可以使用 Flink 的 fine-grained-resource-management,只增大 committer 的堆内存:

  1. 配置 Flink 配置 cluster.fine-grained-resource-management.enabled: true。(Flink 1.18 之后默认开启)
  2. 配置 Paimon 表选项:sink.committer-memory,例如 300 MB,取决于你的 TaskManager。 (同样支持 sink.committer-cpu)
  3. 如果你使用 Flink 批处理作业向 Paimon 写入数据或运行独立 compaction,请配置 Flink 配置 fine-grained.shuffle-mode.all-blocking: true。
