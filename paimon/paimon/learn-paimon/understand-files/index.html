理解文件

本文专门用于厘清各类文件操作对文件产生的影响。

本页提供具体的示例和实用技巧,帮助你有效地管理这些文件。此外,通过对 commit(提交)和 compact(压缩)等 操作的深入探讨,我们将揭示文件的创建与更新机制。

前置条件​

在深入阅读本页之前,请确保你已读完以下章节:

  1. 基本概念,
  2. Primary Key Table 和 Append Table
  3. 如何在 Flink 中使用 Paimon。

理解文件操作​

创建 Catalog​

通过 ./sql-client.sh 启动 Flink SQL 客户端,逐条执行以下语句来创建 Paimon catalog。

CREATE CATALOG paimon WITH (
'type' = 'paimon',
'warehouse' = 'file:///tmp/paimon'
);

USE CATALOG paimon;

这只会创建给定路径 file:///tmp/paimon 下的目录。

创建表​

执行以下建表语句将创建一张包含 3 个字段的 Paimon 表:

CREATE TABLE T (
  id BIGINT,
  a INT,
  b STRING,
  dt STRING COMMENT 'timestamp string in format yyyyMMdd',
  PRIMARY KEY(id, dt) NOT ENFORCED
) PARTITIONED BY (dt);

这将在路径 /tmp/paimon/default.db/T 下创建 Paimon 表 T, 其 schema 存储在 /tmp/paimon/default.db/T/schema/schema-0 中。

向表中插入记录​

在 Flink SQL 中运行以下 insert 语句:

INSERT INTO T VALUES (1, 10001, 'varchar00001', '20230501');

Flink 作业完成后,记录通过一次成功的 commit 写入 Paimon 表。 用户可以执行 SELECT * FROM T 查询来验证这些记录的可见性,该查询将返回一行数据。 commit 过程会在路径 /tmp/paimon/default.db/T/snapshot/snapshot-1 创建一个 snapshot。 snapshot-1 时刻的文件布局如下图所示:

从表中删除记录​

现在让我们删除满足条件 dt>=20230503 的记录。 在 Flink SQL 中执行以下语句:

Batch 
DELETE FROM T WHERE dt >= '20230503';

第三次 commit 发生,产生了 snapshot-3。现在列出表下的文件, 你会发现没有任何分区被删除。取而代之的是,分区 20230503 到 20230510 各自新增了一个数据文件:

./T/dt=20230510/bucket-0:
data-b93f468c-b56f-4a93-adc4-b250b3aa3462-0.orc # newer data file created by the delete statement 
data-0fcacc70-a0cb-4976-8c88-73e92769a762-0.orc # older data file created by the insert statement

这是合理的,因为我们在第二次 commit 中插入了一条记录(即 +I[10, 10010, 'varchar00010', '20230510']),然后在第三次 commit 中删除了 该记录。执行 SELECT * FROM T 将返回 2 行数据,即:

+I[1, 10001, 'varchar00001', '20230501']
+I[2, 10002, 'varchar00002', '20230502']

注意,manifest-3-0 包含 8 个 ADD 操作类型的 manifest entry, 对应 8 个新写入的数据文件。

压缩表(Compact Table)​

你可能已经注意到,随着 snapshot 的不断增加,小文件的数量会越来越多, 这可能导致读取性能下降。因此,需要进行一次 full-compaction 来减少小文件数量。

现在让我们触发 full-compaction,通过 flink run 运行一个专用的 compaction 作业:

Batch
  • Flink SQL
  • Flink Action
CALL sys.compact(
   `table` => 'database_name.table_name', 
   partitions => 'partition_name', 
   order_strategy => 'order_strategy',
   order_by => 'order_by',
   options => 'paimon_table_dynamic_conf'
);
<FLINK_HOME>/bin/flink run \
    -D execution.runtime-mode=batch \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    compact \
    --warehouse <warehouse-path> \
    --database <database-name> \
    --table <table-name> \
    [--partition <partition-name>] \
    [--catalog_conf <paimon-catalog-conf> [--catalog_conf <paimon-catalog-conf> ...]] \
    [--table_conf <paimon-table-dynamic-conf> [--table_conf <paimon-table-dynamic-conf>] ...]

一个例子如下(假设你已经在 Flink home 目录下):

  • Flink SQL
  • Flink Action
CALL sys.compact('T');
./bin/flink run \
    ./lib/paimon-flink-action-2.1-SNAPSHOT.jar \
    compact \
    --path file:///tmp/paimon/default.db/T

当前表中的所有文件都会被压缩,并生成一个新的 snapshot,即 snapshot-4, 它包含以下信息:

注意,manifest-4-0 包含 20 个 manifest entry(18 个 DELETE 操作和 2 个 ADD 操作):

  1. 对于分区 20230503 到 20230510,对两个数据文件各有一次 DELETE 操作。
  2. 对于分区 20230501 到 20230502,对同一个数据文件有一次 DELETE 操作和一次 ADD 操作。 这是因为该文件发生了从 level 0 升级到最高 level 的变化。请放心, 这只是元数据上的变化,文件本身仍然是同一个。

修改表(Alter Table)​

执行以下语句来配置 full-compaction:

ALTER TABLE T SET ('full-compaction.delta-commits' = '1');

它会为 Paimon 表创建一个新的 schema,即 schema-1,但直到下一次 commit 之前, 还没有任何 snapshot 真正使用这个 schema。

过期 Snapshot(Expire Snapshots)​

请注意,被标记的数据文件在 snapshot 过期且没有任何消费者依赖该 snapshot 之前,并不会被真正删除。 更多信息参见过期 Snapshot。

在 snapshot 过期过程中,首先确定要过期的 snapshot 范围,然后将这些 snapshot 中的数据文件标记为待删除。 只有当某个数据文件存在一个 DELETE 类型的 manifest entry 引用它时,它才会被 marked(标记)为待删除。 该标记确保该文件不会被后续的 snapshot 使用,从而可以被安全地移除。

假设上图中的全部 4 个 snapshot 都即将过期。过期过程如下:

  1. 首先删除所有被标记的数据文件,并记录发生变化的 bucket。

  2. 然后删除所有 changelog 文件和关联的 manifest。

  3. 最后删除 snapshot 本身,并写入最早提示文件(earliest hint file)。

如果删除过程后有任何目录变为空目录,它们也会被删除, 但仅在启用 snapshot.clean-empty-directories 时才会如此(默认为 false)。 默认情况下,空目录会保留在磁盘上。参见管理 Snapshot。

假设又创建了一个 snapshot snapshot-5,并触发了 snapshot 过期。snapshot-1 到 snapshot-4 将被 删除。为简单起见,我们只关注之前 snapshot 的文件,过期完成后的最终布局如下:

Flink 流式写入​

最后,我们将借助 CDC 入湖的例子来分析 Flink 流式写入。 本节将介绍如何将变更数据捕获并写入 Paimon,以及异步 compact、 snapshot 提交与过期背后的机制。

首先,让我们仔细看看 CDC 入湖的工作流,以及其中每个组件扮演的独特角色。

  1. MySQL CDC Source 统一读取快照数据和增量数据,其中 SnapshotReader 读取快照数据, BinlogReader 读取增量数据。
  2. Paimon Sink 以 bucket 为粒度将数据写入 Paimon 表。其内部的 CompactManager 会异步触发 compaction。
  3. Committer Operator 是一个单例算子,负责提交 snapshot 和执行 snapshot 过期。

接下来,我们将梳理端到端的数据流。

MySQL Cdc Source 读取快照数据和增量数据,在归一化之后发往下游。

Paimon Sink 首先将新记录缓存在基于堆内存的 LSM tree 中,当内存缓冲区写满时将其刷写到磁盘。 注意,写出的每个数据文件都是一个 sorted run。此时不会创建任何 manifest 文件和 snapshot。 在 Flink checkpoint 发生之前,Paimon Sink 会刷写所有缓冲的记录,并将 committable 消息 发送到下游,由 Committer Operator 在 checkpoint 期间读取并提交。

在 checkpoint 期间,Committer Operator 会创建一个新的 snapshot,并将其与 manifest list 关联, 使该 snapshot 包含表中所有数据文件的信息。

稍后异步 compaction 可能发生,CompactManager 产出的 committable 中包含旧文件和合并后文件的信息, 以便 Committer Operator 构造相应的 manifest entry。在这种情况下, Committer Operator 可能在一次 Flink checkpoint 中产生两个 snapshot:一个对应数据写入(Append 类型的 snapshot), 另一个对应 compact(Compact 类型的 snapshot)。如果 checkpoint 间隔内没有写入任何数据文件, 则只会创建 Compact 类型的 snapshot。Committer Operator 会检查 snapshot 过期条件, 并对被标记的数据文件执行物理删除。

理解小文件​

许多用户都很关心小文件问题,它可能导致:

  1. 稳定性问题:HDFS 中小文件过多,NameNode 会不堪重负。
  2. 成本问题:HDFS 中的一个小文件会临时占用至少一个 Block 的大小,例如 128 MB。
  3. 查询效率:查询过多小文件时效率会受到影响。

理解 Checkpoint​

假设你使用 Flink Writer,每个 checkpoint 会生成 1-2 个 snapshot,而 checkpoint 会强制在 DFS 上生成文件,因此 checkpoint 间隔越小,产生的小文件就越多。

  1. 所以第一件事是增大 checkpoint 间隔。

默认情况下,不仅 checkpoint 会导致文件生成,writer 内存(write-buffer-size)耗尽 也会将数据刷到 DFS 并生成相应的文件。你可以启用 write-buffer-spillable, 让 writer 产生溢出(spill)文件,从而在 DFS 上生成更大的文件。

  1. 所以第二件事是增大 write-buffer-size 或启用 write-buffer-spillable。

理解 Snapshot​

Paimon 维护文件的多个版本,文件的压缩和删除都是逻辑上的,并不会真正删除文件。 只有当 Snapshot 过期时文件才会被真正删除,因此减少文件的第一种方式是 缩短 snapshot 过期所需的时间。Flink writer 会自动执行 snapshot 过期。

参见过期 Snapshot。

理解分区和分桶​

Paimon 的文件按层次化方式组织。下图展示了文件布局。从一个 snapshot 文件出发, Paimon 的 reader 可以递归地访问表中的所有记录。

例如,下面这张表:

CREATE TABLE MyTable (
    user_id BIGINT,
    item_id BIGINT,
    behavior STRING,
    dt STRING,
    hh STRING,
    PRIMARY KEY (dt, hh, user_id) NOT ENFORCED
) PARTITIONED BY (dt, hh) WITH (
    'bucket' = '10'
);

表数据在物理上被切分到不同的分区,分区内部又切分到不同的 bucket。因此,如果整体 数据量太小,单个 bucket 中至少也有一个文件,我建议你配置较小的 bucket 数, 否则同样会产生不少小文件。

理解主键表的 LSM​

LSM tree 将文件组织成若干 sorted run。一个 sorted run 由一个或多个数据文件组成, 每个数据文件恰好属于一个 sorted run。

默认情况下,sorted run 的数量取决于 num-sorted-run.compaction-trigger,参见主键表的 Compaction。 这意味着一个 bucket 中至少有 5 个文件。如果你想减少这个数量,可以保留更少的文件,但写入性能可能会受影响。

理解 Bucketed Append 表的文件​

默认情况下,Append 表也会自动执行 compaction 以减少小文件数量。

然而,对于 Bucketed Append 表,compaction 只会在 bucket 内部进行以保证顺序性, 这可能会保留更多的小文件。参见分桶 Append。

理解 Full-Compaction​

也许你觉得主键表的 5 个文件其实可以接受,但 Append 表(bucket) 单个 bucket 中可能有 50 个小文件,这就很难接受了。更糟糕的是,那些 已经不再活跃的分区也会保留这么多小文件。

配置 full-compaction.delta-commits 可以在 Flink 写入过程中周期性地执行 full-compaction, 并能确保分区在写入结束前完成 full compaction。
