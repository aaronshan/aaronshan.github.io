表模式

Primary Key 表的文件结构大致如上图所示。表或分区包含 多个 bucket,每个 bucket 是一棵独立的 LSM 树结构,包含多个文件。

LSM 的写入过程大致如下:Flink checkpoint 时刷写 L0 文件,并按需触发一次 compaction 来合并数据。根据写入期间不同的处理方式,有三种模式:

  1. MOR(Merge On Read):默认模式,只执行 minor compaction,读取时需要进行合并。
  2. COW(Copy On Write):使用 'full-compaction.delta-commits' = '1',full compaction 是同步执行的, 也就是说合并是在写入时完成的。
  3. MOW(Merge On Write):使用 'deletion-vectors.enabled' = 'true',在写入阶段会查询 LSM, 为数据文件生成 deletion vector 文件,在读取时直接过滤掉不需要的行。

对于一般的 Primary Key 表(merge-engine 为默认值 deduplicate),推荐使用 Merge On Write 模式。

Merge On Read​

MOR 是 Primary Key 表的默认模式。

当模式为 MOR 时,读取时需要合并所有文件,由于所有文件都是有序的,会进行多路归并, 其中包含主键的比较计算。

这里有一个明显的问题:单棵 LSM 树只能由单个线程读取,因此读取并行度 受限。如果 bucket 中的数据量过大,会导致读取性能变差。所以为了读取 性能,建议分析表的查询需求,把 bucket 内的数据量设置在 200MB 到 1GB 之间。但如果 bucket 太小,又会产生大量小文件读写, 给文件系统带来压力。

另外,由于存在合并过程,无法基于 Filter 在非主键列上做数据跳过, 否则新数据会被过滤掉,导致读出错误的旧数据。

  • 写入性能:非常好。
  • 读取性能:不太好。

Copy On Write​

ALTER TABLE orders SET ('full-compaction.delta-commits' = '1');

将 full-compaction.delta-commits 设置为 1,表示每次写入都会进行全量合并,所有数据 都会被合并到最高层级。此时读取无需合并,读取性能最高。 但每次写入都需要全量合并,写放大非常严重。

  • 写入性能:很差。
  • 读取性能:非常好。

Merge On Write​

ALTER TABLE orders SET ('deletion-vectors.enabled' = 'true');

得益于 Paimon 的 LSM 结构,它具备按主键查询的能力。我们可以在写入时生成 deletion vector 文件,标识文件中哪些数据已被删除。读取时直接过滤掉 不需要的行,相当于完成了合并,并且不影响读取性能。

可见性保证:在 deletion vectors 模式下,level 0 的文件只有在 compaction 之后才可见。 因此默认情况下 compaction 是同步的;如果开启异步,数据可能会有延迟。

MOR Read Optimized​

如果你不想使用 Deletion Vectors 模式,又希望在 MOR 模式下足够快地查询, 并且可以接受只能查询到较旧的数据,你也可以:

  1. 在写入数据时配置 'compaction.optimization-interval'。
  2. 从 read-optimized 系统表查询。读取 优化后的文件结果可以避免合并相同键的记录,从而提高读取性能。

你可以在读取时灵活地平衡查询性能与数据延迟。
