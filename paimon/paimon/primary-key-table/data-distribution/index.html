数据分布

Bucket 是读写的最小存储单元,每个 bucket 目录包含一棵 LSM 树。

固定 Bucket​

配置一个大于 0 的 bucket 数,使用固定 Bucket 模式,按照 Math.abs(key_hashcode % numBuckets) 计算 记录所属的 bucket。

重新调整 bucket 数量只能通过离线流程完成,参见 Rescale Bucket。 bucket 数量过多会产生大量小文件,bucket 数量过少会导致写入性能变差。

动态 Bucket​

Primary Key 表的默认模式,或配置 'bucket' = '-1'。

先到达的键落入旧的 bucket,新的键落入新的 bucket,bucket 与键的 分布取决于数据到达的顺序。Paimon 维护一个索引来确定 哪个键对应哪个 bucket。

Paimon 会自动扩展 bucket 数量。

  • 选项 1:'dynamic-bucket.target-row-num':控制单个 bucket 的目标行数。
  • 选项 2:'dynamic-bucket.initial-buckets':控制初始 bucket 的数量。
  • 选项 3:'dynamic-bucket.max-buckets':控制最大 bucket 数量。
信息

动态 Bucket 仅支持单写入作业。请不要启动多个作业写入同一个分区 (这会导致数据重复)。即使你启用 'write-only' 并启动专用 compaction 作业,也是不可行的。

当你的更新不跨分区时(没有分区,或主键包含所有分区字段),动态 Bucket 模式使用 HASH 索引维护键到 bucket 的映射,它比固定 bucket 模式 需要更多内存。

性能:

  1. 一般来说,没有性能损失,但会有一些额外的内存消耗,一个分区中的 1 亿 条 记录会多占用 1 GB 内存,不再活跃的分区不占用内存。
  2. 对于更新率较低的表,推荐使用该模式,可显著提升性能。

Postpone Bucket​

Postpone bucket 模式通过 'bucket' = '-2' 配置。 该模式旨在解决难以确定固定 bucket 数量的问题, 并支持不同分区使用不同的 bucket 数量。

默认情况下,postpone.batch-write-fixed-bucket 为 true。该固定 bucket 流程使用 Spark 的 DataSource V1 写入路径,即使启用了 spark.paimon.write.use-v2-write 也是如此。除非适用 直接写入,Spark 会分三步完成每个批次:

  1. 将当前批次写入未提交的 bucket -2 文件。Spark 直接从暂存文件的元数据中获取每个分区的行 数和文件大小;没有额外的输入扫描、缓存或逐行统计过程。
  2. 计算每个涉及分区所需的 bucket 数量。对于没有真实 bucket 的分区, 显式配置的 postpone.default-bucket-num 会被精确使用。否则, postpone.target-row-num-per-bucket(若配置)优先于 postpone.target-size-per-bucket(默认 1 GB)。推断结果至少为 1, 向上取整为 2 的幂,并受 postpone.batch-write-fixed-bucket.max-parallelism 限制。
  3. 将暂存的记录路由到真实的 bucket 并提交。当前批次只有在这次 提交后才可见。

已有分区通常保持其 bucket 数量。当未封顶的所需 bucket 数量大于现有 bucket 数量乘以 postpone.batch-write-fixed-bucket.rescale-load-factor(默认 32),且封顶后的结果也 大于现有布局时,Spark 会先对真实 bucket 执行 rescale。不同分区可以有不同的目标 bucket 数量。 rescale 是一次独立的 overwrite 提交,只改变真实 bucket;当前批次在随后的一次提交中追加 写入。

postpone.default-bucket-num 没有默认值。显式配置后,Spark 可以 跳过暂存的 bucket -2 文件,直接在 INSERT OVERWRITE 时写入真实 bucket, 或当基础 snapshot 中没有真实 bucket 时直接写入。overwrite 始终精确使用配置的数量, 不会对被替换的布局执行 rescale。向已有真实 bucket 分区追加写入时会忽略该选项, 仍使用暂存批次来决定是否需要 rescale。如果一个 批次同时混合了已有和新的真实 bucket 分区,整个批次保持暂存;只有新 分区使用配置的默认值。

此前已提交的 bucket -2 文件不参与计算,也不会被追加或 rescale 读取、重写或删除。它们仍可用于 merge-on-read 和常规的 postpone compaction。INSERT OVERWRITE 仍遵循其正常的替换语义。

当 postpone.batch-write-fixed-bucket 为 false 时, 记录首先存储在每个分区的 bucket-postpone 目录中, 对读取者不可见。 要把这些记录移动到正确的 bucket 并使其可读,需要运行 compaction 作业。 参见 compact 过程。 首次执行 compaction 的分区的 bucket 数量可以通过选项 postpone.default-bucket-num 配置。该值会被精确使用,并优先于自动 估算。若未配置,则当配置了 postpone.target-row-num-per-bucket 时,bucket 数量按 ceil(row_count / target_row_count) 计算;若未配置,则 Paimon 按 ceil(postpone_file_size / postpone.target-size-per-bucket) 计算,目标大小 默认为 1 GB。两种估算结果都至少为 1。执行并行度不决定 逻辑 bucket 数量。 已有真实 bucket 文件的分区保留其现有 bucket 数量。

最后,当你觉得某个分区的 bucket 数量过小时, 也可以运行 rescale 作业。 参见 rescale 过程。

跨分区 Upsert​

当你需要跨分区 upsert(主键不包含所有分区字段)时,推荐使用 '-1' bucket。 键动态模式直接维护键到分区和 bucket 的映射,使用本地磁盘,并在 启动流式写入作业时通过读取表中所有已有键来初始化索引。不同 Merge Engine 有不同行为:

  1. Deduplicate:从旧分区删除数据,并向新分区插入新数据。
  2. PartialUpdate 与 Aggregation:将新数据插入旧分区。
  3. FirstRow:如果存在旧值,则忽略新数据。

性能:对于数据量很大的表,性能会有明显损失。此外, 初始化需要较长时间。

如果你的 upsert 不依赖过于陈旧的数据,可以考虑配置索引 TTL 来减少索引大小和初始化时间:

  • 'cross-partition-upsert.index-ttl':本地索引与初始化中的 TTL,这可以避免维护过多 索引导致性能越来越差。

你也可以在 bucket (N > 0) 或 bucket (-2) 模式下使用跨分区 Upsert,在这些模式下,没有全局索引 来保证你的数据经过合理的去重,因此依赖你的输入是完整的 changelog 来 保证数据的唯一性。

选择分区字段​

以下三类字段可以在数仓中被定义为分区字段:

  • 创建时间(推荐):创建时间通常是不可变的,因此你可以放心地把它当作分区字段, 并把它加入主键。
  • 事件时间:事件时间是原始表中的字段。对于 CDC 数据,例如从 MySQL CDC 同步的表,或由 Paimon 生成的 Changelog,它们都是完整的 CDC 数据,包含 UPDATE_BEFORE 记录,即使 你声明的主键包含分区字段,也可以实现唯一性效果(需要 'changelog-producer'='input')。
  • CDC op_ts:它不能被定义为分区字段,因为无法知道前一条记录的时间戳。因此你需要使用跨分区 upsert,这会消耗更多资源。
