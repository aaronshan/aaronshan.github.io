Changelog Producer

流式写入可以持续产出最新的变更,供流式读取使用。

用户可以在建表时通过指定 changelog-producer 表属性,选择从表文件中产出变更的模式。

信息

changelog-producer 可能显著降低 Compaction 性能,除非必要,请勿启用。

None​

默认情况下,表的写入器不会应用任何额外的 changelog producer。Paimon source 只能看到跨 snapshot 合并后的变更,例如哪些键被删除了、某些键的新值是什么。

然而,这些合并后的变更无法构成完整的 changelog,因为我们无法直接从它们中读取键的 旧值。合并后的变更要求消费者"记住"每个键的值,并在看不到旧值的情况下重写这些值。 但有些消费者需要旧值来保证正确性或效率。

考虑一个在某些分组键(可能不等于主键)上计算求和的消费者。如果消费者只看到新值 5,它无法确定应该把什么值加到求和结果上。例如,如果旧值是 4,它应该给结果 加 1;但如果旧值是 6,它反而应该从结果中减 1。旧值对这类消费者非常重要。

总而言之,none changelog producer 最适合数据库系统这类的消费者。Flink 也有一个 内置的 "normalize" 算子,它把每个键的值持久化到状态中。显而易见,这种算子的 代价非常高,应当避免使用。(你可以通过 'scan.remove-normalize' 强制移除 "normalize" 算子。)

Input​

通过指定 'changelog-producer' = 'input',Paimon 写入器依赖其输入作为完整 changelog 的来源。 所有输入记录都会被保存在独立的 changelog 文件中,并由 Paimon source 提供给消费者。

当 Paimon 写入器的输入本身就是完整 changelog(例如来自数据库 CDC,或由 Flink 有状态计算生成)时,可以使用 input changelog producer。

Lookup​

如果你的输入无法产出完整的 changelog,但又想摆脱昂贵的 normalize 算子,可以 考虑使用 'lookup' changelog producer。

通过指定 'changelog-producer' = 'lookup',Paimon 会在 Compaction 期间通过 'lookup' 生成 changelog(你也可以启用异步 Compaction)。除非通过 write-only 属性禁用,否则默认在提交写入数据之前执行 lookup compaction。

Lookup 会把数据缓存在内存和本地磁盘中,你可以使用以下选项调优性能:

选项 默认值 类型 描述
lookup.cache-file-retention
 1 h Duration lookup 缓存文件的保留时间。文件过期后,如果仍需访问,会从 DFS 重新读取并在本地磁盘上重新构建索引。
lookup.cache-max-disk-size
 unlimited MemorySize lookup 缓存的最大磁盘大小,你可以用此选项限制本地磁盘的使用。
lookup.cache-max-memory-size
 256 mb MemorySize lookup 缓存的最大内存大小。

Lookup changelog-producer 支持 changelog-producer.row-deduplicate,以避免为同一条记录生成 -U、+U changelog。它还支持 changelog-producer.ignore-update-before(从 changelog 文件中排除 UPDATE_BEFORE(-U)记录)以及 changelog-producer.ignore-delete(排除 DELETE(-D)记录)。 当下游消费者只需要最新状态(例如 upsert sink)而不需要 retract 时,这些选项 非常有用。

(注意:请调大 Flink 配置 'execution.checkpointing.max-concurrent-checkpoints',这对 性能非常重要)。

Full Compaction​

你也可以考虑使用 'full-compaction' changelog producer 来生成 changelog,它更适合 可以容忍较大延迟的场景(例如 30 分钟)。

  1. 通过指定 'changelog-producer' = 'full-compaction',Paimon 会对比两次 full compaction 之间的结果, 并将差异作为 changelog 产出。changelog 的延迟受 full compaction 频率的影响。
  2. 通过指定 full-compaction.delta-commits 表属性,可以在每经过 delta 次提交 (checkpoint)后持续触发 full compaction。该值默认为 1,即每个 checkpoint 都会触发一次 full compaction 并生成 changelog。

一般来说,full compaction 的成本和开销都很高,因此我们更推荐使用 'lookup' changelog producer。

信息

Full compaction changelog producer 可以为任何类型的 source 产出完整的 changelog。但它不如 input changelog producer 高效,且产出 changelog 的延迟可能较高。

Full-compaction changelog-producer 支持 changelog-producer.row-deduplicate,以避免为同一条 记录生成 -U、+U changelog。它还支持 changelog-producer.ignore-update-before 和 changelog-producer.ignore-delete,分别用于从 changelog 文件中过滤掉 -U 和 -D 记录。

Changelog 合并​

适用于 input、lookup、full-compaction 的 'changelog-producer'。

如果 Flink 的 checkpoint 间隔很短(例如 30 秒)且 bucket 数量很多,每个 snapshot 可能 产生大量小的 changelog 文件。文件过多可能给分布式存储集群带来负担。

为了将小 changelog 文件合并成大文件,你可以设置表选项 precommit-compact = true。 该选项默认为 false,设置为 true 后,会在 writer 算子之后添加一个 compact coordinator 和 worker 算子,用于把 changelog 文件合并成大文件。
