链式表(Chain Table)

链式表是 Primary Key 表的一项新能力,它改变了你处理增量数据的方式。 想象这样一个场景:你周期性地保存数据的全量快照(例如每天一次),即使 快照之间只有一小部分数据发生变化。ODS binlog 全量导入就是这一模式的典型例子。

以每日 binlog 全量导入作业为例。一个批处理作业将昨天的全量数据集与今天的 增量变更合并,生成新的全量数据集。这种方式有两个明显的缺点:

  • 全量计算:合并操作涉及全部数据,且会引入 shuffle,性能较差。
  • 全量存储:每天存储一份全量数据,而变化的数据通常只占很小的比例。

Paimon 通过直接只消费变化的数据并执行 merge-on-read 来解决这个问题。 通过这种方式,全量计算和存储被转变为增量模式:

  • 增量计算:离线 ETL 每日作业只需消费当天的变化数据,无需合并全部数据。
  • 增量存储:每天只存储变化的数据,并在生命周期内周期性地(例如每周)异步合并,构建全局的链式表。

基于普通表,链式表引入了 snapshot 分支和 delta 分支,分别表示全量和增量 数据。写入时,你指定分支来写入全量或增量数据。读取时,Paimon 会根据读取模式(如全量、增量或混合)自动选择合适的策略。

启用链式表​

要启用链式表,必须在建表时通过表选项配置 chain-table.enabled 为 true, 并需要创建 snapshot 分支和 delta 分支。

  • Spark SQL
  • Flink SQL
CREATE TABLE default.t (
    `t1` string ,
    `t2` string ,
    `t3` string
) PARTITIONED BY (`date` string)
TBLPROPERTIES (
  'chain-table.enabled' = 'true',
  -- props about primary key table  
  'primary-key' = 'date,t1',
  'sequence.field' = 't2',
  'bucket-key' = 't1',
  'bucket' = '2',
  -- props about partition
  'partition.timestamp-pattern' = '$date', 
  'partition.timestamp-formatter' = 'yyyyMMdd'
);

CALL sys.create_branch('default.t', 'snapshot');

CALL sys.create_branch('default.t', 'delta');

ALTER TABLE default.t SET tblproperties 
    ('scan.fallback-snapshot-branch' = 'snapshot', 
     'scan.fallback-delta-branch' = 'delta');
 
ALTER TABLE `default`.`t$branch_snapshot` SET tblproperties
    ('scan.fallback-snapshot-branch' = 'snapshot',
     'scan.fallback-delta-branch' = 'delta');

ALTER TABLE `default`.`t$branch_delta` SET tblproperties 
    ('scan.fallback-snapshot-branch' = 'snapshot',
     'scan.fallback-delta-branch' = 'delta');
CREATE TABLE default.t (
    `t1` STRING,
    `t2` STRING,
    `t3` STRING,
    `date` STRING
) PARTITIONED BY (`date`) WITH (
  'chain-table.enabled' = 'true',
  'primary-key' = 'date,t1',
  'sequence.field' = 't2',
  'bucket-key' = 't1',
  'bucket' = '2',
  'partition.timestamp-pattern' = '$date',
  'partition.timestamp-formatter' = 'yyyyMMdd'
);

CALL sys.create_branch('default.t', 'snapshot');

CALL sys.create_branch('default.t', 'delta');

ALTER TABLE default.t SET (
    'scan.fallback-snapshot-branch' = 'snapshot', 
    'scan.fallback-delta-branch' = 'delta');
 
ALTER TABLE `default`.`t$branch_snapshot` SET (
    'scan.fallback-snapshot-branch' = 'snapshot',
    'scan.fallback-delta-branch' = 'delta');

ALTER TABLE `default`.`t$branch_delta` SET (
    'scan.fallback-snapshot-branch' = 'snapshot',
    'scan.fallback-delta-branch' = 'delta');

请注意:

  • 链式表仅支持 Primary Key 表,这意味着你应该为表定义 bucket 和 bucket-key。
  • 链式表应确保每个分支的 schema 保持一致。
  • Deletion Vector 仅支持使用 DEDUPLICATE Merge Engine 的链式表。
  • 如果你计划使用流式读取或 lookup join,delta 分支必须使用 DEDUPLICATE Merge Engine(默认值)。 对于这些增量读取路径,delta 分支不支持其他 Merge Engine 类型。批量读取不受影响。
  • 链式表要求 sequence.field,因此不支持 FIRST_ROW 和 AGGREGATE Merge Engine。
  • 对于链式表的 delta 计算,partition.timestamp-formatter 必须指定完整的日期 (年-月-日或年-一年中的第几天),只能使用可往返转换的日期/时间字段 (y/u、M/L、d、D、H、k、m、s),且最小步长至少为一秒。

写入数据​

创建链式表后,你可以将数据写入 snapshot 分支或 delta 分支。

全量写入​

将数据写入 t$branch_snapshot。

insert overwrite `default`.`t$branch_snapshot` partition (date = '20250810') 
    values ('1', '1', '1');

增量写入​

将数据写入 t$branch_delta。

insert overwrite `default`.`t$branch_delta` partition (date = '20250811') 
    values ('2', '1', '1');

读取数据​

你可以以全量、增量或混合模式查询链式表。

全量查询​

如果 snapshot 分支已有全量分区,则直接读取;否则,以链式合并模式读取。

select t1, t2, t3 from default.t where date = '20250811'

你将得到以下结果:

+---+----+-----+
| t1|  t2|   t3|
+---+----+-----+
| 1 |   1|   1 |
| 2 |   1|   1 |
+---+----+-----+

增量查询​

从 t$branch_delta 读取增量分区。

select t1, t2, t3 from `default`.`t$branch_delta` where date = '20250811'

你将得到以下结果:

+---+----+-----+
| t1|  t2|   t3|
+---+----+-----+
| 2 |   1|   1 |
+---+----+-----+

混合查询​

同时读取全量和增量数据。

select t1, t2, t3 from default.t where date = '20250811'
union all
select t1, t2, t3 from `default`.`t$branch_delta` where date = '20250811'

你将得到以下结果:

+---+----+-----+
| t1|  t2|   t3|
+---+----+-----+
| 1 |   1|   1 |
| 2 |   1|   1 |
| 2 |   1|   1 |
+---+----+-----+

链式表 Compaction​

将 snapshot 分支和 delta 分支的数据合并到 snapshot 分支。 这对于周期性地将增量数据合并进全量快照非常有用。 你可以使用 compact_chain_table 过程合并指定分区:

CALL sys.compact_chain_table(table => 'default.t', partition => 'date="20250811"');

合并后,snapshot 分支中的数据将包含来自 snapshot 分支和 delta 分支的合并结果, 后续查询可直接访问 snapshot,无需 merge-on-read 的开销。

select t1, t2, t3 from `default`.`t$branch_snapshot` where date = '20250811';

你将得到以下结果:

+---+----+-----+
| t1|  t2|   t3|
+---+----+-----+
| 1 |   1|   1 |
| 2 |   1|   1 |
+---+----+-----+

流式读取​

链式表支持 Flink 流式读取。流式读取作业分为两个阶段:

  1. 全量加载阶段:默认通过读取最新的 snapshot 分区(每个 group)及其之后 的 delta 分区来产生轻量级结果。更旧的 snapshot 分区会被排除。你可以启用 chain-table.streaming.merge-snapshot 在该阶段执行基于锚点的链式合并,使 跨分支的 DELETE 记录能与 snapshot 数据一起被正确处理。
  2. 增量阶段:持续读取 delta 分支中新提交的 commit。

写入侧要求​

流式读取假设链式表遵循本页开头描述的标准写入模式:

  • snapshot 分支接收周期性的全量数据(例如每日 ODS binlog 导入作业通过 INSERT OVERWRITE t$branch_snapshot 写入)。每个 snapshot 分区代表该时间点 完整的的数据视图。
  • delta 分支接收快照之间的增量变更(例如批处理作业通过 INSERT INTO t$branch_delta 写入当天新增/更新的记录)。每个 delta 分区 仅包含该周期的变化。

流式读取依赖此模式来产生正确的结果。全量加载阶段之后, 只有 delta 分支的新 commit 会被消费——对 snapshot 分支的写入不会触发 流式输出。要纳入新的快照,请重启流式作业。

使用方法​

SET 'execution.runtime-mode' = 'streaming';

INSERT INTO downstream_sink SELECT * FROM default.t;

在全量加载阶段合并 Snapshot​

默认情况下,全量加载阶段是轻量级的:对每个 group,它读取最新的 snapshot 以及 其后的 delta 分区,作为独立的 split。这种方式很快,但跨分支的删除不可见——delta 分支中的 DELETE 记录无法删除 snapshot 分支中的数据。

如果你需要一个完全调和的初始快照,请启用合并模式:

ALTER TABLE default.t SET (
  'chain-table.streaming.merge-snapshot' = 'true'
);

启用合并模式后,全量加载阶段会将每个 group 的最新 snapshot 分区与其链键严格 大于该 snapshot 的 delta 分区进行合并,从而正确解析跨分支的 删除。代价是启动扫描更重。

为减少开销,请定期运行 CALL sys.compact_chain_table(...)。 Compaction 之后,只有 compaction 之后到达的 delta 变更需要合并。

限制​

  • 增量阶段仅监听 delta 分支。对 snapshot 分支的写入在 流式作业重启之前不会被感知。
  • 感知链式表的流式扫描仅支持默认启动模式(latest-full)。 当用户指定显式的起始位置——如 scan.snapshot-id、 scan.timestamp-millis、scan.mode = 'latest' 或 consumer-id——会抛出 UnsupportedOperationException。如需使用不带链式表逻辑的标准流式读取, 请读取具体的分支表(例如 t$branch_delta)而不是主表。
  • 链式表的流式读取不支持分区过滤。通过分区列上的 WHERE 子句或 scan.partitions 表选项指定分区过滤会抛出 UnsupportedOperationException。这是因为链式表的流式扫描基于 跨 snapshot 和 delta 分支的链式合并逻辑来确定要读取的分区, 应用分区过滤会干扰这一逻辑。如需读取特定分区,请改用批模式。
  • delta 分支必须使用 DEDUPLICATE Merge Engine(默认值)。不支持其他 Merge Engine 类型。
  • changelog-producer 选项必须为 none(默认值)或 input;链式表 不支持 lookup 和 full-compaction。
    • 当 changelog-producer 为 none 时,Flink 的算子会按包含链分区在内的完整 主键对记录做 normalize。与原始 +I 记录不在同一链分区中的 -D/-U 记录会被丢弃。如果下游必须接收跨分区的 changelog 记录,请使用 input。

Lookup Join​

链式表支持 Flink lookup join。作为维表使用时,lookup join 反映链式表的最新状态:每个 group 最近的 snapshot 分区, 结合其后的 delta 分区。更旧的 snapshot 分区被视为过期并被排除。 初始加载之后,delta 分支的新写入会通过周期性的增量刷新变得可见。

SELECT
    orders.order_id,
    dim.product_name
FROM orders
LEFT JOIN dim /*+ OPTIONS('continuous.discovery-interval' = '5s') */
    FOR SYSTEM_TIME AS OF orders.proc_time AS dim
    ON orders.product_id = dim.product_id;

增量刷新仅监听 delta 分支。对 snapshot 分支的写入在 lookup join 作业重启之前不会被感知。

限制​

  • 增量刷新仅监听 delta 分支。对 snapshot 分支的写入在 lookup join 作业重启之前不会被感知。
  • Join 键不能包含分区键。链式表的分区模型跨越两个分支(snapshot + delta), 且基于锚点合并,这使得分区级路由在 lookup join 中不可靠。如果分区键出现在 join 条件中,将抛出错误。
  • 链式表的 lookup join 不支持分区过滤。通过 scan.partitions 表选项指定分区过滤会抛出 UnsupportedOperationException。这是因为链式表的 lookup 扫描基于跨 snapshot 和 delta 分支的链式合并逻辑来确定要读取的分区, 应用分区过滤会干扰这一逻辑。
  • 感知链式表的 lookup 扫描仅支持默认启动模式(latest-full)。 当用户指定显式的起始位置——如 scan.snapshot-id、 scan.timestamp-millis、scan.mode = 'latest' 或 consumer-id——会抛出 UnsupportedOperationException。
  • lookup.cache 必须为 AUTO 或 FULL。链式表不支持其他缓存模式。
  • delta 分支必须使用 DEDUPLICATE Merge Engine(默认值)。不支持其他 Merge Engine 类型。

Group Partition​

在实际场景中,一张表通常有多个分区维度。例如,数据可能同时 按 region 和 date 分区。在这种情况下,不同 region 是彼此独立的数据孤岛—— 每一个 region 都应独立维护自己的链,而不是在所有 region 之间共享一条全局链。

Paimon 通过 group partition 支持这一模式:分区键被分为两部分:

  • Group partition 键(前缀字段):标识独立数据孤岛的维度(例如 region)。 每组不同的 group partition 值组合形成各自独立的链。
  • Chain partition 键(后缀字段):在 group 内部构成按时间有序的链的维度 (例如 date)。

使用 chain-table.chain-partition-keys 指定链维度。该值必须是表分区键的 连续后缀。它之前的分区字段自动成为 group 维度。如果不设置该选项, 所有分区属于单个隐式的 group(单维度分区表的默认行为)。

考虑这样一个示例:表按 region 和 date 分区,你希望每个 region 拥有自己的链:

CREATE TABLE default.t (
    `t1` string ,
    `t2` string ,
    `t3` string
) PARTITIONED BY (`region` string, `date` string)
TBLPROPERTIES (
  'chain-table.enabled' = 'true',
  'primary-key' = 'region,date,t1',
  'sequence.field' = 't2',
  'bucket-key' = 't1',
  'bucket' = '2',
  'partition.timestamp-pattern' = '$date',
  'partition.timestamp-formatter' = 'yyyyMMdd',
  -- specify that only `date` is the chain dimension; `region` becomes the group dimension
  'chain-table.chain-partition-keys' = 'date'
);

在该配置下:

  • 分区键:[region, date]
  • Group partition 键:[region] —— CN 和 US 各自拥有独立的链
  • Chain partition 键:[date] —— 每个 region 内部按时间有序的链

当读取像 (region='CN', date='20250811') 这样的分区时,Paimon 会在 同一 region 内查找最近的更早 snapshot 分区(例如 (region='CN', date='20250810')) 作为链的锚点,只针对 CN group 向前合并 delta 数据。US group 使用自己的锚点独立解析。

对于带 region 维度的小时级分区表,你可以同时将 dt 和 hour 设置为 chain partition 键:

'chain-table.chain-partition-keys' = 'dt,hour'

这将 (dt, hour) 作为复合链维度,它之前的字段(例如 region)作为 group 维度。

分区过期​

链式表支持通过标准的 partition.expiration-time 选项进行自动分区过期。 但为了保持链的完整性,其过期算法与普通表不同。

工作原理​

在普通表中,每个早于截止时间(now - partition.expiration-time)的分区都会被 独立地删除。链式表不能这样做,因为一个 delta 分区依赖其最近的更早 snapshot 分区作为 merge-on-read 的锚点。删除锚点会破坏链。

链式表的过期按**段(segment)**进行。一个段由一个 snapshot 分区以及 时间落在该 snapshot 与排序后下一个 snapshot 之间的所有 delta 分区组成。 段是过期的原子单位:要么整段过期,要么段内分区全部保留。

每个 group 的算法如下:

  1. 按 chain partition 时间排序列出 snapshot 分支的所有分区。
  2. 筛选出早于截止时间(now - partition.expiration-time)的分区。
  3. 如果截止时间之前的 snapshot 少于 2 个,则没有可过期的内容——唯一的 snapshot 必须保留作为锚点。
  4. 截止时间之前最近的 snapshot 是锚点(保留)。所有更早的 snapshot 及其 关联的 delta 分区构成可过期的段。
  5. delta 分区先于 snapshot 分区删除,以确保 commit 前置检查始终通过。

对于有 group partition 的表,每个 group 独立处理。一个有许多过期 snapshot 的 group 可以过期其段,而另一个在截止时间之前只有一个 snapshot 的 group 则保留 全部数据。

示例​

ALTER TABLE default.t SET TBLPROPERTIES (
    'partition.expiration-time' = '30 d',
    'partition.expiration-check-interval' = '1 d'
);
ALTER TABLE `default`.`t$branch_snapshot` SET TBLPROPERTIES (
    'partition.expiration-time' = '30 d',
    'partition.expiration-check-interval' = '1 d'
);
ALTER TABLE `default`.`t$branch_delta` SET TBLPROPERTIES (
    'partition.expiration-time' = '30 d',
    'partition.expiration-check-interval' = '1 d'
);

假设 snapshot 分支有分区 S(0101)、S(0201)、S(0301),delta 分支有 D(0110)、D(0210)、D(0315)。在 2025-03-31,保留 30 天时截止时间为 2025-03-01:

  • 截止时间之前的 snapshot:S(0101)、S(0201)。锚点 = S(0201)(保留)。
  • 段 1 过期:S(0101) + D(0110)(位于 S(0101) 与 S(0201) 之间的 delta)。
  • 保留:S(0201)、S(0301)、D(0210)、D(0315)。

重要说明​

  • 仅有 delta 的 group 不会被过期。 如果一个 group 有 delta 分区但没有 snapshot 分区,这些 delta 是该 group 数据的唯一副本。分区过期不会触碰它们。只有当 该 group 存在至少两个早于截止时间的 snapshot 分区后,它们才会开始过期。
  • 冲突检测能感知锚点。 当 partition.expiration-strategy 为 values-time 时, 写入期间的冲突检测能够正确识别锚点分区会被保留,不会拒绝对它们的写入。
  • partition.expiration-time 和 partition.expiration-check-interval 选项应在 主表和两个分支上保持一致地设置。
