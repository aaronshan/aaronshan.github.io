Compaction

随着越来越多的记录写入 LSM 树,sorted run 的数量会增加。由于查询 LSM 树需要合并所有 sorted run,过多的 sorted run 会导致查询性能变差,甚至 内存溢出。

为了限制 sorted run 的数量,我们必须时不时地把若干个 sorted run 合并成一个大的 sorted run。这个过程称为 compaction。

然而,compaction 是一个资源密集型操作,会消耗一定的 CPU 时间和磁盘 IO,因此过于 频繁的 compaction 反而可能导致写入变慢。这是查询性能与写入性能之间的权衡。Paimon 目前采用与 Rocksdb 的 universal compaction 类似的 compaction 策略。

Compaction 解决的问题:

  1. 减少 Level 0 文件,避免查询性能变差。
  2. 通过 changelog-producer 产出 changelog。
  3. 为 MOW 模式 生成 deletion vector。
  4. Snapshot 过期、Tag 过期、分区过期。

限制:

  • 同一分区的 compaction 只能有一个作业在执行,否则会导致冲突,一方抛出异常失败。

写入性能几乎总会受到 compaction 的影响,因此它的调优至关重要。

异步 Compaction​

Compaction 本质上是异步的,但如果你希望它完全异步、不阻塞写入, 以获得最大的写入吞吐,可以让 compaction 慢慢进行,不必着急。 你可以为表使用以下策略:

num-sorted-run.stop-trigger = 2147483647
sort-spill-threshold = 10
lookup-wait = false

该配置会在写入高峰期产生更多文件,并在写入低谷期逐步合并它们,以获得最佳的 读取性能。

专用 compaction 作业​

一般来说,如果你期望有多个作业写入同一张表,就需要将 compaction 分离出来。你可以 使用专用 compaction 作业。

记录级过期​

在 compaction 中,你可以配置记录级过期时间来过期记录,需要配置:

  1. 'record-level.expire-time':记录的保留时间。
  2. 'record-level.time-field':记录级过期使用的时间字段。

过期发生在 compaction 中,无法保证记录一定被及时过期。 你可以手动触发一次 full compaction 来过期那些未及时过期的记录。

Full Compaction​

Paimon 的 Compaction 使用 Universal-Compaction。 默认情况下,当增量数据过多时会自动执行 Full Compaction。你通常 不需要为此操心。

Paimon 还提供了可以周期性执行 Full Compaction 的配置。

  1. 'compaction.optimization-interval':表示多久执行一次优化性的 full compaction, 该配置用于保证 read-optimized 系统表的查询时效性。
  2. 'full-compaction.delta-commits':每经过 delta 次提交后持续触发 full compaction。其缺点 是只能同步执行 compaction,会影响写入效率。

Lookup Compaction​

当 Primary Key 表配置了 lookup changelog producer 或 first-row merge-engine, 或为 MOW 模式启用了 deletion vectors 时,Paimon 会 在每次触发 compaction 时采用激进的 compaction 策略,强制把 level 0 文件合并到更高的层级。

Paimon 也提供了用于优化这类 compaction 频率的配置。

  1. 'lookup-compact':lookup compaction 使用的压缩模式。可选值:radical,使用 ForceUpLevel0Compaction 策略激进地压缩新文件;gentle,使用 UniversalCompaction 策略 温和地压缩新文件;
  2. 'lookup-compact.max-interval':gentle 模式下触发强制 L0 lookup compaction 的最大间隔。 该选项仅在 lookup-compact 模式为 gentle 时有效。

通过将 'lookup-compact' 配置为 gentle,L0 中的新文件不会被立即压缩,在某些情况下,这 能以牺牲数据新鲜度为代价大幅降低整体资源消耗。

Compaction 选项​

暂停写入的 Sorted Run 数量​

当 sorted run 数量较少时,Paimon 写入器会在独立的线程中异步执行 compaction,这样 记录就可以持续写入表中。然而,为了避免 sorted run 无限增长,当 sorted run 数量达到 阈值时,写入器会暂停写入。以下表属性决定该阈值。

选项 是否必填 默认值 类型 描述
num-sorted-run.stop-trigger
 否 (无) Integer 触发停止写入的 sorted run 数量,默认值为 'num-sorted-run.compaction-trigger' + 3。

num-sorted-run.stop-trigger 越大,写入停顿就越少,从而提高写入 性能。但是,如果该值过大,查询表时就需要更多的内存和 CPU 时间。 如果你担心 OOM 问题,请配置以下选项。 其取值取决于你的内存大小。

选项 是否必填 默认值 类型 描述
sort-spill-threshold
 否 (无) Integer 如果排序 reader 的最大数量超过该值,将尝试 spill。这可以防止过多 reader 消耗过多内存导致 OOM。

触发 Compaction 的 Sorted Run 数量​

Paimon 使用支持大量更新的 LSM 树。LSM 将文件组织为若干 sorted run。查询 LSM 树中的记录时,必须合并所有 sorted run 才能得到全部记录的完整视图。

显而易见,过多的 sorted run 会导致查询性能变差。为了把 sorted run 数量维持在合理范围内,Paimon 写入器会自动执行 compaction。以下表属性决定触发一次 compaction 的最小 sorted run 数量。

选项 是否必填 默认值 类型 描述
num-sorted-run.compaction-trigger
 否 5 Integer 触发 compaction 的 sorted run 数量。包括 level0 文件(一个文件一个 sorted run)和高层级 run(一个 level 一个 sorted run)。

num-sorted-run.compaction-trigger 越大,compaction 就越不频繁,从而提高写入 性能。但如果该值过大,查询表时就需要更多的内存和 CPU 时间。这是写入性能与查询性能之间的权衡。
