REST Management API

REST Management API 是一套实验性的 OpenAPI 3.1 控制面扩展，用于在 Paimon REST Catalog 中管理对象权限、 行过滤器和列掩码。其当前协议版本为 1.0，在设计验证期间未来可能会出现不兼容的演进。

RESTCatalog 直接暴露 permissionManagement() 和 policyManagement() 方法。这些方法刻意不属于通用的 Catalog 接口，其他 Catalog 实现不会暴露这套管理协议。

Catalog 寻址​

所有管理端点都使用 REST Catalog 配置端点返回的不透明 prefix。它不是请求体中的 Catalog 名称，也与本地 引擎中的 Catalog 别名无关。

GET  /v1/{prefix}/permissions
POST /v1/{prefix}/permissions/grant
POST /v1/{prefix}/permissions/revoke

GET    /v1/{prefix}/databases/{database}/tables/{table}/policies
POST   /v1/{prefix}/databases/{database}/tables/{table}/policies
POST   /v1/{prefix}/databases/{database}/tables/{table}/policies/drop

目前策略（policy）只能挂载在表上。路径本身就是挂载身份的标识，因此策略请求体不再重复 Catalog、database、 table 或资源类型。Catalog 级与 database 级的匹配可以在之后以显式匹配语义的方式加入，而不是隐式的路径继承。

完整的线上传输协议见 rest-management-open-api.yaml。

权限与策略相互独立​

权限（permission）是将某个资源上的一种访问权授予某个主体（principal）。数据策略（data policy）则是在一次 已被授权的读取之上进一步限制可见的行或列。创建策略永远不会授予 SELECT，撤销 SELECT 也不会删除策略。

这种分离也定义了预期的查询路径：

  1. 服务端评估对象权限。
  2. 服务端解析适用于调用方的所有行过滤与列掩码策略。
  3. 现有的 REST Catalog 表授权端点将存储的 Paimon 谓词（predicate）和列转换（transform）返回给引擎。
  4. 引擎在规划扫描时应用这些限制。

管理请求体使用与现有 AuthTableQueryResponse 相同的序列化 Paimon Predicate 和 Transform 表示形式。策略冲突检测、schema 校验与主体解析均由服务端负责。

权限模型​

权限资源是结构化对象：

资源类型必需定位符示例
CATALOG无{"type":"CATALOG"}
CATALOG_ALL无{"type":"CATALOG_ALL"}
DATABASEdatabase{"type":"DATABASE","database":"sales"}
DATABASE_ALLdatabase{"type":"DATABASE_ALL","database":"sales"}
TABLEdatabase、table{"type":"TABLE","database":"sales","table":"orders"}
COLUMNdatabase、table{"type":"COLUMN","database":"sales","table":"orders"}
FUNCTIONdatabase、function{"type":"FUNCTION","database":"sales","function":"calculate_tax"}
VIEWdatabase、view{"type":"VIEW","database":"sales","view":"daily_orders"}

主体（principal）是不透明、规范化的字符串，在服务端命名空间内全局唯一。其格式由服务端定义，可编码用户、 组、角色或服务身份，例如 role:analyst 或外部身份提供方的 ARN。主体类型与成员关系解析由服务端负责。 access 值长度限制为 32 个字符，主体长度限制为 128 个字符。实现方可以将线上定位符与主体解析为不同的 稳定持久化标识符；这些内部 id 不在本 API 中暴露。

内置的 access 采用通用的数据授权词汇。创建类 access 刻意使用其不带下划线的持久化名称：

Access含义
ALL适用于该资源的全部访问权。
CREATEDATABASE在 Catalog 中创建数据库。
DESCRIBE读取数据库元数据或选择当前数据库。
ALTER修改资源元数据。
DROP删除资源。
CREATETABLE在数据库中创建表。
CREATEFUNCTION在数据库中创建函数。
CREATEVIEW在数据库中创建视图。
LIST列出数据库中的资源。
SELECT读取表或视图数据，或使用函数。
UPDATE写入表数据，包括 insert、update 和 delete 操作。
GRANT对资源授予或撤销授权。

Java 辅助方法对 access 名称大小写不敏感，并会在发送前归一化。REST 线上格式使用大写。内置 access 与 资源类型强相关：

资源Access
CATALOGALL、ALTER、DROP、GRANT、CREATEDATABASE
CATALOG_ALLALL、DESCRIBE、ALTER、DROP、GRANT、CREATETABLE、CREATEVIEW、CREATEFUNCTION、LIST、SELECT、UPDATE
DATABASEALL、DESCRIBE、ALTER、DROP、GRANT、CREATETABLE、CREATEVIEW、CREATEFUNCTION、LIST
DATABASE_ALLALL、SELECT、UPDATE、ALTER、DROP、GRANT
TABLEALL、SELECT、UPDATE、ALTER、DROP、GRANT
COLUMNSELECT
VIEWALL、SELECT、ALTER、DROP、GRANT
FUNCTIONALL、SELECT、ALTER、DROP、GRANT

一条授权（assignment）的身份由 resource、access 和 principal 组成。对同一身份重复授权会替换其 过期时间，撤销操作是幂等的。CATALOG、DATABASE、TABLE、COLUMN、VIEW 和 FUNCTION 仅作用于 精确引用的资源。CATALOG_ALL 是对所配置 Catalog 下所有 database、table、view 和 function 后代资源的 显式范围；DATABASE_ALL 是对指定 database 下所有 table、view 和 function 后代资源的显式范围。这些 范围授权同样适用于之后创建的后代资源。它们在列表响应中仍表现为直接授权；服务端不会合成继承而来的授权。 组成员关系与角色继承的解析仍由服务端负责。

列权限​

列权限使用 COLUMN 资源（其定位符为所在表）、SELECT access，以及一个 columns 对象。columns 中有且仅有一个非空列表：

  • columnNames 是允许列表。只有被点名的顶层列可读。
  • excludedColumnNames 是拒绝列表。除被点名列之外的所有当前顶层列均可读。

例如，下面这条授权只允许读取 order_id 和 region：

{
  "resource": {
    "type": "COLUMN",
    "database": "sales",
    "table": "orders"
  },
  "access": "SELECT",
  "principal": "role:analyst",
  "columns": {
    "columnNames": ["order_id", "region"]
  }
}

授权身份仍然是 (resource, access, principal)；columns 不属于身份的一部分。对同一身份重复授权会 整体替换之前的允许列表或拒绝列表，而不是合并单个列名。因此撤销操作不携带 columns，并会移除整条列授权。

在授权时被点名的所有列必须存在，且表必须开启查询授权。服务端可以在执行授权的同时原子地开启 query-auth.enabled；否则必须拒绝该授权。列名仅指向顶层字段。对于每个生效的调用方主体，适用的列范围 会取交集。如果任意一个适用的范围拒绝了被查询的列，查询将失败，而不是静默丢弃该列。

Schema 演进会将授权绑定在稳定的表身份上。重命名被引用列会更新其存储的列名，删除被引用列会将其从范围中 移除。服务端必须拒绝会导致允许列表为空的 schema 变更，因为移除该授权会扩大访问范围；而空拒绝列表等同于 没有列限制，因此该授权会被移除。允许列表会拒绝之后新增的列，而拒绝列表会放行它们，因此在新增列可能包含 敏感数据时允许列表更安全。

expireTime（如存在）是相对于 REST 服务端时钟求值的开区间上界。当 now >= expireTime 时，该授权 不得再授予访问权。过期的直接授权在服务端清理之前可能仍出现在列表中。时间戳精度不得超过毫秒；线上值使用 UTC Z，小数位最多三位。

本 API 中的资源对象是线上定位符，而非持久化身份。服务端必须将直接授权绑定到稳定的内部资源身份：重命名 数据库、表、函数或视图会保留其授权，且后续响应使用新定位符；删除资源会移除其直接授权；以相同定位符重建 资源不会恢复这些授权。

数据策略模型​

数据策略直接挂载在一张表和一个主体上。在服务端解析完组与角色成员关系后，只要该主体对调用方生效，策略即 生效。一个主体在一张表上最多有一个行过滤器，在每个表列上最多有一个列掩码。行过滤器的身份为 (table, ROW_FILTER, principal)；列掩码的身份为 (table, COLUMN_MASKING, principal, onColumn)。

每个策略恰好包含一个类型化定义：

定义必需字段结果
rowFilterpredicate一条序列化的 Paimon Predicate，应用于每一次扫描。
columnMaskonColumn、transform一条序列化的 Paimon Transform，其结果替换被保护的列。

公共字段是一个 principal。rowFilter.predicate 直接映射为 AuthTableQueryResponse.filter 中的一条 记录。columnMask.onColumn 和 columnMask.transform 分别直接映射为 AuthTableQueryResponse.columnMasking 中的一个键和值。每个 JSON 值在 UTF-8 编码下不超过 60 KiB。 这是 Paimon 的版本化序列化格式，而不是 SQL 文本或可移植的策略 DSL；客户端与服务端必须使用兼容的 Paimon 版本。

除非满足以下全部条件，否则创建策略必须被拒绝：

  1. 目标数据库和表存在。
  2. 表已设置 query-auth.enabled=true；否则存储的策略可能被静默绕过。
  3. 被引用的主体存在。
  4. 谓词或转换能被服务端识别，可反序列化为非空的 Paimon 对象，并在存储前被规范化。
  5. 每个被引用的字段以及 onColumn 都存在于目标表中，且 transform 的输出类型与被保护列匹配。

这些不变量在表的整个生命周期内持续生效。服务端必须将策略绑定到稳定的表身份上，在表重命名后保留该绑定， 并在表被删除时移除策略。带有策略的表必须拒绝会禁用 query-auth.enabled、或移除/重命名被保护或被 引用列的变更，除非策略更新与 schema 变更以原子方式执行。如果一个实现把某个主体的所有掩码持久化在同一个 文档中，那么创建或删除一个列掩码时必须原子地保留其他列的掩码。

在授权时，所有适用的行过滤器必须以逻辑 AND 组合。多于一个针对同一列的适用列掩码必须失败关闭（fail closed）。无效、不受支持或与 schema 不兼容的谓词或转换也必须失败关闭，而不是省略该限制。

这个实验性协议刻意不定义受治理的标签（governed tags）、Catalog/数据库级策略继承或标签驱动的匹配。这些 功能在加入之前需要明确的匹配条件与冲突规则。

Spark SQL 存储过程​

以下示例假设 Spark 中名为 paimon 的 Catalog。请将其替换为你 spark.sql.catalog.<catalog-name> 中 配置的 Catalog 名称。

授予权限​

当服务端接受授权时，grant_permission 返回一行 result = true。

授予在 Catalog 中创建数据库的权限：

CALL paimon.sys.grant_permission(
  resource_type => 'CATALOG',
  access => 'CREATEDATABASE',
  principal => 'role:catalog_user'
);

授予对 Catalog 中当前或之后创建的所有适用对象的读权限。这不会授予 CREATEDATABASE 之类的 Catalog 级 操作：

CALL paimon.sys.grant_permission(
  resource_type => 'CATALOG_ALL',
  access => 'SELECT',
  principal => 'role:catalog_reader'
);

授予在数据库中创建视图的权限，可选地携带过期时间：

CALL paimon.sys.grant_permission(
  resource_type => 'DATABASE',
  database => 'sales',
  access => 'CREATEVIEW',
  principal => 'role:data_engineer',
  expire_time => '2027-01-01T00:00:00Z'
);

授予对一个数据库中当前或之后创建的所有适用表的写权限。DATABASE_ALL 要求提供 database，但不接受 table、function 或 view 定位符：

CALL paimon.sys.grant_permission(
  resource_type => 'DATABASE_ALL',
  database => 'sales',
  access => 'UPDATE',
  principal => 'role:sales_writer'
);

使用匹配的定位符授予表、函数和视图的访问权：

CALL paimon.sys.grant_permission(
  resource_type => 'TABLE',
  database => 'sales',
  table => 'orders',
  access => 'SELECT',
  principal => 'user:alice'
);

CALL paimon.sys.grant_permission(
  resource_type => 'FUNCTION',
  database => 'sales',
  function => 'calculate_tax',
  access => 'SELECT',
  principal => 'role:analyst'
);

CALL paimon.sys.grant_permission(
  resource_type => 'VIEW',
  database => 'sales',
  view => 'daily_orders',
  access => 'SELECT',
  principal => 'service:reporting_job'
);

授予对部分列的访问权。这要求表开启查询授权；推荐使用命名参数，因为两种列范围模式互斥：

ALTER TABLE paimon.sales.orders
SET TBLPROPERTIES ('query-auth.enabled' = 'true');

CALL paimon.sys.grant_permission(
  resource_type => 'COLUMN',
  database => 'sales',
  table => 'orders',
  access => 'SELECT',
  principal => 'role:analyst',
  column_names => array('order_id', 'region')
);

使用 excluded_column_names 表示拒绝列表。重复执行授权会在一次操作中替换之前的允许列表：

CALL paimon.sys.grant_permission(
  resource_type => 'COLUMN',
  database => 'sales',
  table => 'orders',
  access => 'SELECT',
  principal => 'role:analyst',
  excluded_column_names => array('email', 'phone_number')
);

列出权限​

list_permissions 始终精确指向某一个资源或显式的后代范围。省略可选过滤条件将列出其上的所有直接授权； 从范围继承来的生效授权不会被合成：

CALL paimon.sys.list_permissions(
  resource_type => 'TABLE',
  database => 'sales',
  table => 'orders'
);

按主体或 access 过滤：

CALL paimon.sys.list_permissions(
  resource_type => 'TABLE',
  database => 'sales',
  table => 'orders',
  principal => 'role:analyst',
  access => 'SELECT'
);

列出挂载在某个主体上的列范围。结果以 ARRAY<STRING> 类型的列暴露 column_names 和 excluded_column_names，一条 COLUMN 授权恰好只有其中一个有值：

CALL paimon.sys.list_permissions(
  resource_type => 'COLUMN',
  database => 'sales',
  table => 'orders',
  principal => 'role:analyst',
  access => 'SELECT'
);

输出的 next_page_token 是不透明的；携带相同过滤条件原样回传即可：

CALL paimon.sys.list_permissions(
  resource_type => 'TABLE',
  database => 'sales',
  table => 'orders',
  max_results => 50,
  page_token => 'opaque-token-from-previous-row'
);

撤销权限​

提供与授权时相同的三个身份字段。expire_time 不是身份的一部分。

CALL paimon.sys.revoke_permission(
  resource_type => 'TABLE',
  database => 'sales',
  table => 'orders',
  access => 'SELECT',
  principal => 'role:sales_reader'
);

即使授权已不存在，重复执行的调用也会成功。

列权限的撤销使用所在表的身份，并移除整个列范围：

CALL paimon.sys.revoke_permission(
  resource_type => 'COLUMN',
  database => 'sales',
  table => 'orders',
  access => 'SELECT',
  principal => 'role:analyst'
);

创建行过滤策略​

在挂载任何策略之前，先开启表的查询授权：

ALTER TABLE paimon.sales.orders
SET TBLPROPERTIES ('query-auth.enabled' = 'true');

create_policy 接收规范化的 principal 和一条序列化的 Paimon Predicate。下面的 JSON 与 AuthTableQueryResponse.filter 中一条记录所接受的表示形式相同。推荐使用命名参数，因为行过滤与列掩码 定义使用不同的字段：

CALL paimon.sys.create_policy(
  database => 'sales',
  table => 'orders',
  policy_type => 'ROW_FILTER',
  principal => 'group:analysts',
  predicate_json => '{"kind":"LEAF","transform":{"name":"FIELD_REF","fieldRef":{"index":1,"name":"region","type":"STRING"}},"function":"EQUAL","literals":["APAC"]}'
);

如果该主体在该表上已有行过滤器，调用将失败。在为同一身份创建不同定义之前，先删除已有策略。为第二个主体 创建策略需要另一次单独的调用。

创建列掩码策略​

对于列掩码，on_column 标识被保护的列，transform_json 是与 AuthTableQueryResponse.columnMasking 中所用值相同的序列化 Paimon Transform 表示形式。本示例将所有可见的电话号码替换为固定字符串：

CALL paimon.sys.create_policy(
  database => 'sales',
  table => 'customers',
  policy_type => 'COLUMN_MASKING',
  principal => 'role:support',
  on_column => 'phone_number',
  transform_json => '{"name":"CONCAT","inputs":["****"]}'
);

transform 可以按名称引用表字段。服务端会将它们的索引重映射到当前 schema，拒绝不存在的字段，并校验结果 类型与 on_column 匹配：

CALL paimon.sys.create_policy(
  database => 'sales',
  table => 'customers',
  policy_type => 'COLUMN_MASKING',
  principal => 'group:support',
  on_column => 'email',
  transform_json => '{"name":"CONCAT","inputs":[{"index":1,"name":"region","type":"STRING"},"-masked"]}'
);

predicate_json 仅在 ROW_FILTER 时必需。on_column 和 transform_json 仅在 COLUMN_MASKING 时必需。含有单引号的 JSON 必须在 SQL 字符串字面量内将其转义为 ''。

列出策略​

列出直接挂载在一张表上的所有策略：

CALL paimon.sys.list_policies(
  database => 'sales',
  table => 'orders'
);

按策略类型或主体过滤。column 过滤条件仅在 policy_type => 'COLUMN_MASKING' 时有效：

CALL paimon.sys.list_policies(
  database => 'sales',
  table => 'orders',
  policy_type => 'ROW_FILTER',
  principal => 'group:analysts'
);

输出列为 database、table、policy_type、principal、predicate_json、on_column、 transform_json 和 next_page_token。行过滤器只有 predicate_json；列掩码只有 on_column 和 transform_json。将不透明的续页 token 携带相同的过滤条件原样回传：

CALL paimon.sys.list_policies(
  database => 'sales',
  table => 'orders',
  max_results => 50,
  page_token => 'opaque-token-from-previous-row'
);

管理类列表接口遵循现有的 Paimon 分页协议：空页表示分页结束，因此没有续页 token。每个 Spark 存储过程 恰好返回由 page_token 选定的页面；将非空的 next_page_token 原样回传以获取下一页。

删除策略​

删除已有策略：

CALL paimon.sys.drop_policy(
  database => 'sales',
  table => 'orders',
  policy_type => 'ROW_FILTER',
  principal => 'group:analysts'
);

默认情况下，删除不存在的策略会报错。设置 if_exists => true 可获得幂等操作：

CALL paimon.sys.drop_policy(
  database => 'sales',
  table => 'orders',
  policy_type => 'ROW_FILTER',
  principal => 'group:analysts',
  if_exists => true
);

创建、删除或查看权限与策略，要求服务端为调用方授权其拥有相关资源上的 GRANT 权限。认证、主体成员关系、 策略持久化、schema 校验与审计日志仍属于 REST 服务端的职责。
