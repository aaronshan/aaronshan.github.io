  • Append Table

概述

如果一张表没有定义主键,它就是一张 Append 表(仅追加表)。与主键表相比,它没有直接接收 changelog 的能力,无法通过 upsert 直接更新数据,只能接收 append 形式写入的数据。

  • Flink
CREATE TABLE my_table (
    product_id BIGINT,
    price DOUBLE,
    sales BIGINT
) WITH (
    -- 'target-file-size' = '256 MB',
    -- 'file.format' = 'parquet',
    -- 'file.compression' = 'zstd',
    -- 'file.compression.zstd-level' = '3'
);

在典型的批写、批读应用场景中,它类似于普通的 Hive 分区表,但与 Hive 表相比,它可以带来:

  1. 时间旅行(Time Travel)支持使用完全相同的表 snapshot 进行可复现的查询,也让用户可以轻松检查变更。版本回滚允许用户通过将表重置到良好状态来快速纠正问题。
  2. 扫描规划很快 — 利用表元数据,通过分区和列级统计信息裁剪数据文件。File Index(BloomFilter、Bitmap、Range Bitmap)和聚合下推进一步加速查询。
  3. Schema 演进支持添加、删除、更新或重命名列,且没有副作用。
  4. 丰富的生态 — 可以将表接入 Flink、Spark、Hive、Trino、Presto、StarRocks、Doris 等计算引擎,使用起来就像普通的 SQL 表一样。
  5. 支持基于 z-order/hilbert/order 排序的增量聚簇(Incremental Clustering),以低成本优化数据布局。
  6. 像队列一样的流式读写,DELETE / UPDATE / MERGE INTO 支持低成本的行级操作。

Append 流式处理​

你可以通过 Flink 以非常灵活的方式向 Append 表流式写入,或通过 Flink 读取 Append 表,将其当作队列使用。唯一的区别是它的延迟在分钟级。它的优势是成本非常低,并且支持下推过滤和投影。

提交前小文件合并(Pre small files merging)

"Pre" 表示这种 compaction 发生在将文件提交到 snapshot 之前。

如果 Flink 的 checkpoint 间隔很短(例如 30 秒),每个 snapshot 可能会产生大量小 changelog 文件。文件过多可能会给分布式存储集群带来负担。

为了将小 changelog 文件合并为大文件,你可以设置表选项 precommit-compact = true。 该选项的默认值是 false;如果设置为 true,它会在 writer operator 之后增加一个 compact coordinator 和 worker operator,用于将 changelog 文件合并为大文件。

提交后小文件合并(Post small files merging)

"Post" 表示这种 compaction 发生在将文件提交到 snapshot 之后。

在流式写入作业中,如果没有定义 bucket,writer 中不会发生 compaction,而是使用 Compact Coordinator 扫描小文件,并将 compaction 任务传递给 Compact Worker。在流式模式下,如果你在 Flink 中运行 insert sql,拓扑结构如下:

不用担心背压(backpressure),compaction 永远不会被背压。

如果将 write-only 设置为 true,拓扑中的 Compact Coordinator 和 Compact Worker 会被移除。

自动 compaction 仅在 Flink 引擎的流式模式下支持。你也可以通过 Paimon 的 Flink action 在 Flink 中启动一个独立的 compaction 作业,并通过设置 write-only 禁用所有其他 compaction。

流式查询

你可以流式读取 Append 表,并将其当作消息队列使用。与主键表一样,流式读取有两种方式:

  1. 默认情况下,流式读取在首次启动时读取表的最新 snapshot,然后继续读取最新的增量记录。
  2. 你可以指定 scan.mode、scan.snapshot-id、scan.timestamp-millis 和/或 scan.file-creation-time-millis 来只流式读取增量数据。

与 flink-kafka 类似,默认情况下不保证顺序,如果你的数据有某种顺序要求,还需要考虑定义 bucket-key,参见分桶 Append。

聚合下推​

Append 表支持聚合下推:

SELECT COUNT(*) FROM TABLE WHERE DT = '20230101';

此查询可以在编译期加速,并非常快地返回结果。

对于 Spark SQL,使用默认 metadata.stats-mode 的表可以加速以下查询:

SELECT MIN(a), MAX(b) FROM TABLE WHERE DT = '20230101';

SELECT * FROM TABLE ORDER BY a LIMIT 1;

Min、Max、TopN 查询也可以在编译期加速,并非常快地返回结果。

基于排序的数据跳过​

Paimon 默认在 manifest 文件中记录每个字段的最大值和最小值。

在查询时,根据查询的 WHERE 条件,结合 manifest 中的统计信息,我们可以进行文件过滤。如果过滤效果好,原本需要数分钟的查询可以加速到毫秒级完成。

通常数据分布并不总是利于过滤,那么能否按照 WHERE 条件中的字段对数据进行排序呢? 你可以查看 Flink COMPACT Action、 Flink COMPACT Procedure 或 Spark COMPACT Procedure。

基于 File Index 的数据跳过​

你也可以使用 file index,它在读取侧通过索引过滤文件。

定义 file-index.bitmap.columns 后,数据文件索引是一个外部索引文件,Paimon 会为每个数据文件创建对应的索引文件。如果索引文件太小,它会直接存储在 manifest 中,否则存储在数据文件所在的目录中。每个数据文件对应一个索引文件,索引文件有独立的文件定义,可以包含不同类型的索引和多个列。

不同的 file index 在不同场景下效率各异。例如,bloom filter 可以在点查场景下加速查询;bitmap 会消耗更多空间,但精度更高。

  • BloomFilter: file-index.bloom-filter.columns。
  • Bitmap: file-index.bitmap.columns。
  • Range Bitmap: file-index.range-bitmap.columns。

如果你想为现有表添加 file index,并且不想重写任何数据,可以使用 rewrite_file_index procedure。在使用该 procedure 之前,你需要在目标表上配置好相应的配置项,可以使用 ALTER 语句为表配置 file-index.<filter-type>.columns。

调用方式:参见 Flink Procedures。

行级操作​

目前只有 Spark SQL 支持 DELETE & UPDATE & MERGE INTO,你可以查看 Spark Write。

示例:

DELETE FROM my_table WHERE currency = 'UNKNOWN';

更新 append 表有两种模式:

  1. COW(Copy on Write):先搜索命中的文件,然后重写每个文件,将需要删除的数据从文件中移除。此操作代价较高。
  2. MOW(Merge on Write):通过指定 'deletion-vectors.enabled' = 'true',可以启用 Deletion Vectors 模式。该模式只标记对应文件中需要删除的某些记录并写入删除文件,而不重写整个文件。
