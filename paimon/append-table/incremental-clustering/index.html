增量聚簇(Incremental Clustering)

Paimon 目前支持使用 SFC(空间填充曲线,Space-Filling Curve)对 append 表进行排序(更多信息参见 sort compact)。 由此产生的数据布局通常为针对聚簇键的查询带来更好的性能。 然而,在当前的 SortCompaction 下,即使数据和聚簇键都没有变化, 每次运行仍然需要重写整个数据集,代价极高。

为此,Paimon 引入了一种更灵活的增量聚簇机制 —— Incremental Clustering。 每次运行时,它只选择特定的文件子集进行聚簇,避免全量重写。这使得基于排序的数据布局优化成本更低, 并提升查询性能。此外,借助 Incremental Clustering, 你可以在不重写现有数据的情况下调整聚簇键;数据布局随聚簇运行动态演进, 并逐渐收敛到最优状态,显著降低了围绕数据布局的决策复杂度。

Incremental Clustering 支持:

  • 支持增量聚簇,尽可能最小化写放大。
  • 支持小文件合并,重写时遵循 target-file-size。
  • 支持变更聚簇键,新写入的数据会按照最新的聚簇键进行聚簇。
  • 提供 full 模式,选择后将对整个数据集重新聚簇。

unaware-bucket 模式(bucket = -1)和分桶模式(bucket > 0)的 append 表均支持 Incremental Clustering。 对于分桶 append 表,由于聚簇放弃了 bucket 内的有序追加保证,因此需要满足额外要求。

启用增量聚簇​

要启用 Incremental Clustering,需要为表设置以下配置:

选项取值是否必填类型描述
clustering.incremental
true是Boolean必须设置为 true 才能启用增量聚簇。默认为 false。
clustering.columns
'clustering-columns'是String聚簇列,格式为 'columnName1,columnName2'。不建议使用分区键作为聚簇键。
clustering.strategy
'zorder' 或 'hilbert' 或 'order'否String用于聚簇的排序算法。如果不设置,将根据聚簇列的数量决定:1 列时使用 'order',少于 5 列时使用 'zorder',5 列及以上时使用 'hilbert'。
clustering.incremental.mode
'global-sort' 或 'local-sort'否Enum增量聚簇 compaction 的排序模式。默认为 global-sort。global-sort 在本地排序之前先跨任务进行一次全局 range shuffle,输出文件按聚簇列全局有序,代价是产生网络 shuffle。local-sort 跳过全局 shuffle,仅在每个 compaction 任务内部独立排序,每个输出文件内部有序但文件之间没有全局顺序;该模式成本更低,并且足以满足 Parquet 文件级查找优化。

对于分桶 append 表(bucket > 0),你还必须设置以下选项:

选项取值是否必填类型描述
bucket-append-ordered
false是Boolean启用增量聚簇的分桶 append 表必须设置为 false。

启用 Incremental Clustering 的分桶 append 表不支持 deletion-vectors.enabled = true。

示例:

ALTER TABLE T SET (
    'bucket-append-ordered' = 'false',
    'clustering.incremental' = 'true',
    'clustering.columns' = 'event_time,user_id',
    'clustering.strategy' = 'zorder'
);

为表启用 Incremental Clustering 之后,你可以定期以批模式运行 Incremental Clustering, 持续优化表的数据布局,从而获得更好的查询性能。

注意:由于普通 compaction 也会重写文件,它可能会破坏 Incremental Clustering 构建的有序数据布局。 因此,启用 Incremental Clustering 后,该表不再支持写入时 compaction 或独立 compaction; 聚簇和小文件合并必须完全通过 Incremental Clustering 运行来完成。

运行增量聚簇​

信息

以下示例提交的是批式 compact 作业,这是显式运行 Incremental Clustering 的推荐方式。

按照以下说明运行 Incremental Clustering 作业。

运行 Incremental Clustering 时不需要指定任何与聚簇相关的参数, 这些选项已经定义为表选项。如果需要更改聚簇设置,请更新相应的表选项。

  • Spark SQL
  • Flink Action

运行以下 SQL:

--设置写入并行度,如果过大,可能会生成大量小文件。
SET spark.sql.shuffle.partitions=10;

-- 运行增量聚簇
CALL sys.compact(table => 'T')

-- 以 full 模式运行增量聚簇,将重新聚簇全部数据
CALL sys.compact(table => 'T', compact_strategy => 'full')

-- 以 global-sort 模式(默认)运行增量聚簇
-- 跨任务进行全局 range shuffle,输出文件全局有序
CALL sys.compact(table => 'T', options => 'clustering.incremental.mode=global-sort')

-- 以 local-sort 模式运行增量聚簇
-- 仅在每个任务内排序,无全局 shuffle,成本更低且足以满足 Parquet 查找优化
CALL sys.compact(table => 'T', options => 'clustering.incremental.mode=local-sort')

运行以下命令,为该表提交一个增量聚簇作业。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    compact \
    --warehouse <warehouse-path> \
    --database <database-name> \
    --table <table-name> \
    [--compact_strategy <minor / full>] \
    [--table_conf <table_conf>] \
    [--catalog_conf <paimon-catalog-conf> [--catalog_conf <paimon-catalog-conf> ...]]

示例:以 global-sort 模式(默认)运行增量聚簇,输出文件在所有任务之间全局有序。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    compact \
    --warehouse s3:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --table_conf sink.parallelism=2 \
    --table_conf clustering.incremental.mode=global-sort \
    --compact_strategy minor \
    --catalog_conf s3.endpoint=https://****.com \
    --catalog_conf s3.access-key=***** \
    --catalog_conf s3.secret-key=*****

示例:以 local-sort 模式运行增量聚簇,仅在每个任务内排序,不进行全局 shuffle,成本更低且足以满足 Parquet 查找优化。

<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-2.1-SNAPSHOT.jar \
    compact \
    --warehouse s3:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --table_conf sink.parallelism=2 \
    --table_conf clustering.incremental.mode=local-sort \
    --compact_strategy minor \
    --catalog_conf s3.endpoint=https://****.com \
    --catalog_conf s3.access-key=***** \
    --catalog_conf s3.secret-key=*****
  • --compact_strategy 决定如何挑选要聚簇的文件,默认为 minor。
    • full:所有文件都会被选中进行聚簇。
    • minor:根据指定条件挑选需要聚簇的文件集合。

注意:写入并行度由 sink.parallelism 设置,如果过大,可能会生成大量小文件。

你可以使用 -D execution.runtime-mode=batch 或 -yD execution.runtime-mode=batch(用于 ON-YARN 场景)来使用批模式。

历史分区自动聚簇​

信息

历史分区自动聚簇目前仅适用于 unaware-bucket append 表(bucket = -1)。 分桶 append 聚簇不使用 clustering.history-partition.* 表选项。

在对最近活跃的分区执行增量聚簇的同时,Paimon 可以自动检测历史分区和不活跃分区, 并评估它们的数据布局是否已达到最优状态。 对于尚未达到最优布局的历史分区,Paimon 也会在同一操作中对它们执行全量聚簇, 从而提升其查询性能。

要启用历史分区自动聚簇,需要为表设置以下配置:

选项取值是否必填类型描述
clustering.history-partition.idle-to-full-sort
3d是Duration一个分区在指定时长内没有新更新后,即被视为历史分区。默认为空。
clustering.history-partition.limit
5是Integer自动执行全量聚簇的历史分区数量上限。默认值为 5。

实现原理​

为了在写放大和排序效果之间取得平衡,Paimon 借鉴 LSM Tree 的 level 概念对数据文件进行分层, 并使用 Universal Compaction 策略来选择要聚簇的文件。

  • 新写入的数据落在 level-0;level-0 中的文件是未聚簇的。
  • level-i 中的所有文件都是在同一个排序集合中排序产生的。
  • 类比 Universal Compaction:在 level-0 中,每个文件是一个 sorted run;在 level-i 中,所有文件共同构成一个 sorted run。聚簇时,sorted run 是基本的工作单元。

通过引入更多的 level,我们可以控制每次聚簇运行处理的数据量。 更高 level 的数据聚簇得更加稳定,不太可能被重写,从而在保持良好排序效果的同时降低写放大。
