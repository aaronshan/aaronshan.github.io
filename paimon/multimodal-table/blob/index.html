Blob 存储

概述​

BLOB(Binary Large Object,二进制大对象)类型是一种专为在 Paimon 表中存储多模态数据(如图片、视频、音频文件及其他大型二进制对象)而设计的数据类型。与将二进制数据与其他列内联存储的传统 BYTES 类型不同,BLOB 类型将大型二进制数据存储在独立的文件中并维护对其的引用,从而为大型对象提供更好的性能。字段还可以使用 ARRAY<BLOB> 表示有序集合,或使用 MAP<K, BLOB> 表示带键的 Blob。

Blob 存储基于 Data Evolution 模式。

Blob 类型非常适合以下场景:

  • 图片存储:存储商品图片、用户头像、医学影像数据
  • 视频内容:存储视频片段、监控录像、多媒体内容
  • 音频文件:存储语音录音、音乐文件、播客节目
  • 文档存储:存储 PDF 文档、办公文件、大型文本文件
  • 机器学习:存储 Embedding、模型权重、特征向量
  • 任何大型二进制数据:任何因过大而无法高效内联存储的数据

存储布局​

当你定义一张包含 Blob 列的表时,Paimon 会自动分离存储:

  1. 普通数据文件(如 .parquet、.orc):存储常规列(INT、STRING 等)
  2. Blob 数据文件(.blob):存储实际的 blob 数据

对于仅追加(append-only)的视频帧工作负载,一个或多个标量 BLOB 字段可以改用 video pack 格式(.video)。一个 video pack 将多个完整编码的视频拼接在一起, 并内嵌一个紧凑的帧区间(frame-run)索引。帧序号存放在 VideoFrameDescriptor 中; 普通数据文件里不需要 frame_index 或 frame_timestamp 列。当配置了多个视频 字段时,它们的物理边界可以相互嵌套,但每一次负载变化都必须发生在逻辑 episode 边界上,以保证普通文件和专用文件始终是一个对齐的文件组。

例如,对于 schema 为 (id INT, name STRING, picture BLOB) 的表:

table/
├── bucket-0/
│   ├── data-uuid-0.parquet      # Contains id, name columns
│   ├── data-uuid-1.blob         # Contains picture blob data
│   ├── data-uuid-2.blob         # Contains more picture blob data
│   └── ...
├── manifest/
├── schema/
└── snapshot/

这种分离带来以下好处:

  • 高效的列投影(读取非 blob 列时不会加载 blob 数据)
  • 基于 blob 大小优化的文件滚动
  • 常规列式数据获得更好的压缩效果

关于 blob 文件格式结构的详细信息,请参阅 File Format - BLOB。

存储模式​

Paimon 为 BLOB 字段支持三种存储模式,通过列上的 comment 指令进行选择:

  1. 默认 blob 存储(__BLOB_FIELD) Blob 字节被写入表路径下由 Paimon 管理的 .blob 文件。 该模式支持 BLOB、ARRAY<BLOB> 和 MAP<K, BLOB> 字段。

  2. 仅描述符存储(__BLOB_DESCRIPTOR_FIELD) 只有序列化后的 BlobDescriptor 字节被内联存储在数据文件中。Paimon 不会为这些字段写入 .blob 文件,且非空值必须以描述符形式提供输入。

  3. Blob view 存储(__BLOB_VIEW_FIELD) 序列化后的 BlobViewStruct 字节被内联存储。该 struct 通过表标识符、BLOB 字段和 row id 指向上游表中的一个 BLOB 值,实际的 blob 字节在读取时从上游表解析得到。

这使得一张表可以为不同的 BLOB 列混合使用不同的存储模式。 ARRAY<BLOB> 和 MAP<K, BLOB> 仅由 __BLOB_FIELD 支持; 仅描述符和 blob-view 的 comment 指令只接受标量 BLOB 字段。 Map 键支持整数家族、BOOLEAN、DECIMAL、DATE、TIME、BINARY、 VARBINARY(BYTES)、CHAR 和 VARCHAR。为了在 Flink、Spark 和 Python 之间保持兼容,请使用非空键。

CREATE TABLE image_table (
    id INT,
    name STRING,
    image BYTES COMMENT '__BLOB_FIELD'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true',
    'fs.oss.endpoint' = 'aaa',                   -- This is for Paimon's own config
    'blob-descriptor.fs.oss.endpoint' = 'bbb'    -- This is for input blob descriptors' config
);

创建表​

在 SQL 中创建 blob 表的推荐方式是在列上使用 comment 指令 __BLOB_FIELD、__BLOB_DESCRIPTOR_FIELD 或 __BLOB_VIEW_FIELD。Paimon 会自动把该列转换为对应的 BLOB 类型,并将其注册到相应的配置项中。

  • Flink SQL
  • Spark SQL
  • Java API
  • Python API
CREATE TABLE image_table (
    id INT,
    name STRING,
    image BYTES COMMENT '__BLOB_FIELD; product image',
    gallery ARRAY<BYTES> COMMENT '__BLOB_FIELD; product gallery'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

-- Multiple blob columns with different storage modes
CREATE TABLE media_table (
    id INT,
    photo BYTES COMMENT '__BLOB_FIELD; original photo',
    thumbnail BYTES COMMENT '__BLOB_DESCRIPTOR_FIELD; thumbnail descriptor',
    preview BYTES COMMENT '__BLOB_VIEW_FIELD; preview from upstream'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);
CREATE TABLE image_table (
    id INT,
    name STRING,
    image BINARY COMMENT '__BLOB_FIELD; product image',
    gallery ARRAY<BINARY> COMMENT '__BLOB_FIELD; product gallery'
) TBLPROPERTIES (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);
// Comment directives convert binary source types and register the blob fields.
Schema schema = Schema.newBuilder()
        .column("id", DataTypes.INT())
        .column("name", DataTypes.STRING())
        .column("image", DataTypes.BYTES(), "__BLOB_FIELD; product image")
        .column("gallery", DataTypes.ARRAY(DataTypes.BYTES()),
                "__BLOB_FIELD; product gallery")
        .option("row-tracking.enabled", "true")
        .option("data-evolution.enabled", "true")
        .build();
import pyarrow as pa
from pypaimon import Schema

# Scalar, list, and map types with large_binary() values are recognized as blob types.
pa_schema = pa.schema([
    ('id', pa.int32()),
    ('name', pa.string()),
    ('image', pa.large_binary()),
    ('gallery', pa.list_(pa.large_binary())),
])

schema = Schema.from_pyarrow_schema(
    pa_schema,
    options={
        'row-tracking.enabled': 'true',
        'data-evolution.enabled': 'true',
    }
)

视频帧存储​

当逻辑表每行对应一帧、而物理存储和解码单元是完整编码视频时,使用 video-frame-field。该逗号分隔的配置项同时会把每个被点名的 SQL BYTES 或 BINARY 列标记为 BLOB 列。它选择专用的 .video 格式;普通的 .blob 版本 及其布局不受影响。

CREATE TABLE video_frames (
    episode_id BIGINT,
    camera_front BYTES,
    camera_wrist BYTES
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true',
    'video-frame-field' = 'camera_front,camera_wrist'
);

每个逻辑值都是一个 VideoFrameDescriptor:它的 URI 区间标识一个完整编码的视频, 其帧序号在该视频中选中一帧。写入时,.video 数据区将原始视频负载直接拼接, 不带普通 BLOB 条目包装。四个内嵌的 delta-varint 索引分别记录物理视频长度、逻辑 区间长度、区间到视频的引用以及每个区间的首帧序号。因此连续的帧只需要一条区间 记录,而无需每行一条索引记录。NULL 和 data-evolution 占位值使用负的区间引用。

物理复用基于精确的负载描述符一致性(URI、offset 和 length),而不是内容哈希。 它局限于每个 .video 文件内部:每个 pack 都是自包含的,绝不会指向其他 Paimon 数据文件所拥有的负载。一个 pack 可以包含多个 MP4 负载。达到大小或行数目标后, 滚动会等待当前物理视频组结束,因此对于大视频该目标是软性的。之后的提交或更早 的滚动可能会再次存储同一个源视频的另一份物理副本。对于多摄像头表,只要每次 切换都发生在 episode 边界,各字段的负载边界可以相互嵌套。一旦在 episode 内部 达到目标,普通文件、BLOB 和 vector 的滚动都会推迟到下一个负载边界,且所有 活跃的 writer 一起关闭。这样得到的文件组仍保持行对齐,单个超大 episode 可能 会超过配置的目标大小。

Compaction 会把完整编码视频的区间按字节拷贝进一个新的自包含 .video pack, 并重建内嵌索引;它不会解码或重新编码帧。对齐的普通数据文件只包含 episode_id、 state、action 等应用列。Paimon 将帧映射存储在 .video 的描述符/索引路径中。

当前限制:

  • 仅支持 append-only 表;primary-key 表继续使用受管 BLOB 存储。
  • 每个被配置的字段必须是标量 BLOB;ARRAY<BLOB> 和 MAP<K, BLOB> 继续使用 .blob。
  • 非空写入必须是精确的、由描述符承载的 BlobRef 值,且其中包含 VideoFrameDescriptor。内联字节和普通的 BlobDescriptor 值会被拒绝。
  • 版本 1 以从零开始、步长为一的展示顺序序号来寻址帧。它不存储 PTS 值,也不 解析编解码器/容器元数据。
  • 视频字段不支持 BlobConsumer 回调。

即使 blob-as-descriptor 为 false,读取 .video 字段也会返回序列化的 VideoFrameDescriptor 值。如果为每个逻辑帧都完整物化一次 MP4,就违背了该格式 的设计目的。

关于 Python 数据摄入和 PyTorch DataLoader 的用法(包括在 worker 中复用解码器 会话),请参阅 PyPaimon Multimodal API: Video Frame Storage。

comment 指令的格式为 __DIRECTIVE; optional user comment。Paimon 会将 BYTES/BINARY 转换为 BLOB,将 ARRAY<BYTES>/ARRAY<BINARY> 转换为 ARRAY<BLOB>,将 MAP<K, BYTES>/MAP<K, BINARY> 转换为 MAP<K, BLOB>。它会将该字段注册到相应的配置项中,并把 ; 之后的文本存为该列的真实 comment。

支持的指令:

指令存储模式配置项
__BLOB_FIELD原始标量、数组元素或 map 值存入 .blob 文件blob-field
__BLOB_DESCRIPTOR_FIELD描述符字节内联存储blob-descriptor-field
__BLOB_VIEW_FIELDview 引用内联存储blob-view-field

添加 Blob 列​

同样的 comment 指令也可用于 ALTER TABLE ADD COLUMN:

  • Flink SQL
  • Spark SQL
  • Java API
  • Python API
ALTER TABLE image_table ADD picture BYTES COMMENT '__BLOB_FIELD';

ALTER TABLE image_table
    ADD video BYTES COMMENT '__BLOB_DESCRIPTOR_FIELD; promotional video';
ALTER TABLE image_table ADD COLUMN picture BINARY COMMENT '__BLOB_FIELD';

ALTER TABLE image_table
    ADD COLUMN video BINARY COMMENT '__BLOB_DESCRIPTOR_FIELD; promotional video';
// Java API: add column with BlobType directly
schemaManager.commitChanges(
    SchemaChange.addColumn("picture", DataTypes.BLOB()));

// Or use comment directive like SQL
schemaManager.commitChanges(
    SchemaChange.addColumn("video", DataTypes.BYTES(),
        "__BLOB_DESCRIPTOR_FIELD; promotional video", null));
# pa.large_binary() is automatically recognized as BLOB type
catalog.alter_table(
    'default.image_table',
    [('add', 'picture', pa.large_binary())]
)

仅描述符存储​

如果你希望下游表复用上游的 blob 文件(不拷贝数据、也不生成新的 .blob 文件),可以使用 __BLOB_DESCRIPTOR_FIELD:

CREATE TABLE descriptor_table (
    id INT,
    image BYTES COMMENT '__BLOB_DESCRIPTOR_FIELD; reused image'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

Paimon 只在普通数据文件中存储序列化的 BlobDescriptor 字节。读取 blob 时会按照描述符中的 URI 访问字节,这些字段的非空值必须以描述符形式输入。

OSS Blob 的预签名 URL​

Paimon 可以为 OSS 上的 BlobDescriptor 生成一个临时 HTTPS URL。该描述符可能 指向一个更大的 .blob 文件内部的某个字节区间。Paimon 首先会把该区间精确地 物化为一个不带文件扩展名的独立 OSS 对象,将其 content type 设置为 application/octet-stream,然后返回一个预签名的 GET URL。

请为 catalog 配置标准的公网 HTTPS OSS endpoint。内网 endpoint 以及不带 https 协议的 endpoint 会被拒绝,因为外部消费方必须能够访问返回的 URL:

fs.oss.endpoint=https://oss-cn-hangzhou.aliyuncs.com

要从普通 BLOB 列获取描述符,请以 blob-as-descriptor=true 读取源表。相关 SQL 函数有严格版和容错版两种形式:

-- Flink SQL
SELECT sys.descriptor_to_presigned_url(
    'default.image_table',
    image,
    INTERVAL '5' MINUTE)
FROM image_table /*+ OPTIONS('blob-as-descriptor'='true') */;

SELECT sys.try_descriptor_to_presigned_url(
    'default.image_table',
    image,
    INTERVAL '5' MINUTE)
FROM image_table /*+ OPTIONS('blob-as-descriptor'='true') */;
-- Spark SQL
ALTER TABLE image_table SET TBLPROPERTIES ('blob-as-descriptor' = 'true');

SELECT sys.descriptor_to_presigned_url(
    'default.image_table',
    image,
    INTERVAL '5' MINUTE)
FROM image_table;

在 Flink 和 Spark 中,source_table 都必须是以 database.table 形式书写的 非空字符串字面量。当 catalog 与函数所属的 catalog 一致时,也接受 catalog.database.table 形式。动态列和 CASE 表达式会在规划阶段被拒绝。 严格版函数会把行级错误向上抛出;try_descriptor_to_presigned_url 对行级错误 返回 NULL。有效期必须是正的整秒数。

Java API 使用同样的表根路径安全检查:

DataTable table = ...;
Blob blob = ...;
String url =
        blob.toPresignedUrl(
                table.fileIO(), table.location(), Duration.ofMinutes(5));

物化对象的字节内容保持不变。消费方必须检查内容本身,而不能依赖 URL 后缀或 特定格式的 content type。对于直接作为模型 image_url 输入的场景,只使用已 与目标模型验证过的格式;该入口不覆盖 PDF。

物化对象以完整的描述符指纹作为键。对同一个描述符在短期内重复调用时,只要 已有对象的长度、content type 和指纹仍然匹配,就会复用该对象并生成一个新的 URL。第一个版本不会处理与过期缓存清理或孤儿文件清理之间的竞争。

请将返回的 URL 视为持有者凭证(bearer credential):立即提交给外部服务,不要 持久化它,也绝不要把该 URL 或其签名/安全令牌查询参数写入日志。

Blob View​

当下游表需要引用已存储在上游表中的 BLOB 值,而又不想拷贝字节或创建新的 .blob 文件时,Blob view 就很有用。blob view 字段只内联存储一个很小的 BlobViewStruct。读取该字段时,Paimon 会从上游表解析出被引用的 BLOB。

Blob view 要求:

  • 上游表已启用 row tracking,使每行都有稳定的 _ROW_ID
  • 下游字段使用 __BLOB_VIEW_FIELD comment 指令声明
  • 写入时提供序列化的 BlobViewStruct;在 Flink SQL 中可使用内置的 sys.blob_view 函数

Flink SQL 函数签名为:

sys.blob_view(table_name, field_name, row_id)

参数说明:

  • table_name:上游表名。必须使用 database.table 或 catalog.database.table 的完整限定形式,非限定表名会被拒绝。
  • field_name:上游 BLOB 字段名。
  • row_id:上游 row-tracking 表中的 _ROW_ID 值。

下面的示例写入一张下游表,其 image_ref 字段引用 image_table 中的 image 字段:

CREATE TABLE image_table (
    id INT,
    name STRING,
    image BYTES COMMENT '__BLOB_FIELD'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

CREATE TABLE image_view_table (
    id INT,
    label STRING,
    image_ref BYTES COMMENT '__BLOB_VIEW_FIELD'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

INSERT INTO image_view_table
SELECT
    id,
    name AS label,
    sys.blob_view('default.image_table', 'image', _ROW_ID)
FROM `image_table$row_tracking`;

如果表名中包含当前 Paimon catalog 的名称,该函数也接受 catalog.database.table 形式:

SELECT sys.blob_view('my_catalog.default.image_table', 'image', _ROW_ID)
FROM `image_table$row_tracking`;

读取 image_view_table.image_ref 会以与普通 blob 字段相同的方式返回被引用的 BLOB 字节。被引用的上游表和行必须保持可用,view 才能被解析。

转发 Blob View 引用

默认情况下,读取 blob view 字段会解析 BlobViewStruct 并返回上游 BLOB 内容。 如果你希望把一个 blob view 表的数据导入另一个 blob view 表而不拷贝 BLOB 字节, 可以用 blob-view.resolve.enabled=false 读取源表,并把结果写入用 __BLOB_VIEW_FIELD 声明的目标字段。

禁用该选项后,Paimon 在读取时会保留序列化的 BlobViewStruct。当保留的值被 写入另一个 blob view 字段时,目标表存储的是同一个上游引用,而不是创建一个 链式的 view 引用。

例如,如果表 T1 中的 blob view 引用指向表 T0 中的 BLOB,那么以 blob-view.resolve.enabled=false 把 T1 导入 T2 后,T2 仍然直接引用 T0。

CREATE TABLE t2 (
    id INT,
    image_ref BYTES COMMENT '__BLOB_VIEW_FIELD'
) WITH (
    'row-tracking.enabled' = 'true',
    'data-evolution.enabled' = 'true'
);

-- Flink SQL example: the source table is read with blob view resolution disabled.
INSERT INTO t2
SELECT id, image_ref
FROM t1 /*+ OPTIONS('blob-view.resolve.enabled'='false') */;

MERGE INTO 支持​

对于 Flink 和 Spark 中的 Data Evolution 写入:

  • 原始数据的 BLOB 列在部分列更新的 MERGE INTO 中仍会被拒绝
  • 基于描述符的 BLOB 列是允许的

对应的 Python 用法请参阅 Blob Storage in pypaimon。

限制​

  1. Primary Key 表:primary-key 表中的受管 BLOB 存储有额外要求,请参阅 Primary-Key BLOB Storage。primary-key 表支持 merge-engine=partial-update 搭配标量 blob-descriptor-field、受管 blob-field(changelog-producer=none)以及标量 blob-view-field;不支持 ARRAY / MAP 形式的描述符或 view 字段。
  2. 不支持谓词下推:Blob 列不能用于过滤谓词。
  3. 不支持统计信息:Blob 列不支持统计信息收集。
  4. Append 表配置项:对于 append 表,row-tracking.enabled 和 data-evolution.enabled 必须设为 true。
  5. Blob View 依赖:Blob view 字段依赖于被引用的上游表和行。如果上游数据被删除或不再可读,view 将无法解析。
  6. 集合存储模式:ARRAY<BLOB> 和 MAP<K, BLOB> 仅支持原始受管 blob 存储(__BLOB_FIELD),不支持 __BLOB_DESCRIPTOR_FIELD 或 __BLOB_VIEW_FIELD。

最佳实践​

  1. 使用列投影:始终只选择需要的列。如果不需要 blob 数据,避免使用 SELECT *。

  2. 设置合适的目标文件大小:根据你的 blob 大小配置 blob.target-file-size。更大的值意味着更少的文件,但单个文件更大。

  3. 复用外部 blob 文件时使用描述符字段:对于应当保留描述符引用、而不写入新 .blob 文件的字段,使用 __BLOB_DESCRIPTOR_FIELD。

  4. 使用 Blob View 避免拷贝 BLOB 数据:当下游表只需要引用上游表中的 BLOB 值时,使用 __BLOB_VIEW_FIELD。

  5. 使用分区:按日期或其他维度对 blob 表进行分区,以提升查询性能和数据管理效率。
