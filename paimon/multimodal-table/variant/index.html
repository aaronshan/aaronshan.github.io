Variant 存储

概述​

VARIANT 类型用于存储行与行之间结构可以不同的半结构化数据。一个值可以是对象、 数组,也可以是字符串、数字或布尔值等标量。这使得 VARIANT 非常适合事件属性、 模型输出、工具参数等变化过于频繁、无法把每个字段都建模为表列的数据。

Paimon 使用 Parquet Variant 二进制编码 来存储 VARIANT,而不是存储其 JSON 文本。数据在转换为 VARIANT 时被解析,查询 可以按指定的 SQL 类型提取某个路径。

VARIANT 不要求启用 Data Evolution 模式。SQL 支持需要 Spark 4.0 或更高版本,或 Flink 2.1 或更高版本。Variant 数据文件必须使用 Parquet;ORC 和 Avro 不支持该类型。

Variant 与 JSON 字符串​

JSON 字符串和 VARIANT 值可以表示相同的逻辑文档,但它们的存储和查询行为不同。

以 STRING 存储的 JSONVARIANT
逻辑类型不透明的字符串半结构化、带类型的数据
校验可以写入任意文本;只有 JSON 函数解析时才检查 JSON 合法性输入在转换为 VARIANT 时被解析
物理存储一个字符串列中的 UTF-8 文本二进制的 value 和 metadata 字段
值类型数字、布尔值和 null 在被解析前都是文本类型被编码在值中
字段访问JSON 函数在查询期间解释文本Variant 函数读取路径并转换为指定的 SQL 类型
物理优化需要读取并解释整个字符串高频查询的字段可以拆解(shred)成带类型的子列
适用场景需要保留 JSON 原文,或很少检查内容反复查询不断演进的半结构化数据

将 JSON 转换为 VARIANT 会保留其数据语义,但不保留其文本表示。转换后不要依赖 原有的空白字符、对象字段顺序或数字格式。如果出于审计目的需要原始文本,请将其 保存在单独的 STRING 列中。

写入和查询 Variant​

下面的 Spark SQL 示例创建了一个 Variant 列,并使用 parse_json 转换 JSON 字符串:

CREATE TABLE events (
    id BIGINT,
    payload VARIANT
) USING paimon
TBLPROPERTIES (
    'file.format' = 'parquet'
);

INSERT INTO events VALUES
    (1, parse_json('{"user":{"id":1001},"city":"Hangzhou","active":true}')),
    (2, parse_json('{"user":{"id":1002},"city":"Beijing","score":9.5}'));

使用 variant_get 提取路径并指定其结果类型:

SELECT
    id,
    variant_get(payload, '$.user.id', 'bigint') AS user_id,
    variant_get(payload, '$.city', 'string') AS city
FROM events
WHERE variant_get(payload, '$.active', 'boolean') = true;

路径可以寻址嵌套的对象和数组,例如 $.user.id、$.items[0].sku 或 $[0]。路径不存在时返回 NULL。对于不兼容值的转换行为,由查询引擎和所使用 的 Variant 函数定义。

如果使用 JSON 字符串,等价的查询会使用面向字符串的 JSON 函数,且通常在执行 查询时解析文本:

SELECT
    id,
    CAST(get_json_object(payload_json, '$.user.id') AS BIGINT) AS user_id
FROM json_events;

存储布局​

普通 Variant​

默认情况下,Variant 列在 Parquet 文件内部以两个二进制字段存储:

payload (GROUP)
├── value      BYTE_ARRAY  -- encoded values and structure
└── metadata   BYTE_ARRAY  -- object-key dictionary and encoding metadata

二进制表示避免了存储和重复解析 JSON 语法,同时也保留了每个标量值的类型。要 从普通 Variant 中提取子字段,仍需要读取该 Variant 列的二进制 value 字段。

Shredded Variant​

Shredding 会把选定的 Variant 路径物化为带类型的 Parquet 子列,同时逻辑表列仍 保持为 VARIANT。例如,对 age 和 city 进行 shred 后,得到的布局类似于:

payload (GROUP)
├── metadata   BYTE_ARRAY
├── value      BYTE_ARRAY OPTIONAL       -- fields that were not shredded
└── typed_value (GROUP) OPTIONAL
    ├── age (GROUP)
    │   ├── value        BYTE_ARRAY OPTIONAL
    │   └── typed_value  INT32 OPTIONAL
    └── city (GROUP)
        ├── value        BYTE_ARRAY OPTIONAL
        └── typed_value  BYTE_ARRAY OPTIONAL (STRING)

typed_value 字段是普通的带类型 Parquet 叶子列。能够将 Variant 路径提取下推 到扫描阶段的读取端,可以只读取所需的叶子列,而无需解码完整的 Variant 值。 当文档很宽、但查询总是反复访问一小部分路径时,这最有价值。

Shredding 是无损的:

  • 不在 shredding schema 中的字段仍保留在溢出的 value 字节中。
  • 与配置的 shredded 类型不匹配的值也保留在 value 中。
  • 读取完整 Variant 时,会从带类型字段和溢出字节中透明地重建它。
  • 一张表可以同时包含普通文件和 shredded 文件。修改 shredding 配置只影响新 文件,不会重写已有文件。

Shredding 以额外的写入开销和物理列换取更快的投影读取。对于通常需要选择整个 Variant、访问路径无法预测、或写入的是重复字段很少的极稀疏文档的工作负载, 它可能没有帮助。

配置 Shredding​

显式 Schema​

将 variant.shreddingSchema 设置为 JSON 编码的 Paimon ROW 类型。顶层字段 标识表中的 Variant 列;其嵌套类型描述需要物化的路径。

CREATE TABLE user_events (
    id BIGINT,
    payload VARIANT
) USING paimon
TBLPROPERTIES (
    'file.format' = 'parquet',
    'variant.shreddingSchema' =
    '{"type":"ROW","fields":[{"name":"payload","type":{"type":"ROW","fields":[{"name":"user_id","type":"BIGINT"},{"name":"city","type":"STRING"}]}}]}'
);

该 schema 将 $.user_id shred 为 BIGINT,将 $.city shred 为 STRING。其他 字段仍可通过溢出字节访问。旧键 parquet.variant.shreddingSchema 作为别名也 被接受。

shredded 的带类型值支持字符和二进制类型、布尔类型、decimal 和数值类型,以及 嵌套的 ROW 和 ARRAY 类型。shredding schema 中的 VARIANT 分支会保持其 二进制表示。

当重要的查询路径及其类型已知时,使用显式 schema。它能给文件带来可预测的物理 布局,并避免推断阶段的缓冲。

自动 Schema 推断​

Paimon 可以为每个输出文件独立推断 shredding schema:

CREATE TABLE inferred_events (
    id BIGINT,
    payload VARIANT
) USING paimon
TBLPROPERTIES (
    'file.format' = 'parquet',
    'variant.inferShreddingSchema' = 'true',
    'variant.shredding.maxInferBufferRow' = '4096',
    'variant.shredding.maxSchemaWidth' = '300',
    'variant.shredding.maxSchemaDepth' = '50',
    'variant.shredding.minFieldCardinalityRatio' = '0.1'
);

写入端会缓冲文件的初始若干行,推断它们的公共结构,创建物理 schema,然后刷写 这些行。稀有字段、超出配置的宽度或深度的字段,以及观测类型不兼容的字段,都 不会被 shred。

配置项默认值说明
variant.inferShreddingSchemafalse在未配置显式 schema 时,启用按文件的 shredding schema 推断。
variant.shredding.maxInferBufferRow4096用于推断的最大初始缓冲行数。
variant.shredding.maxSchemaWidth300推断出的 shredding schema 中的最大字段数。
variant.shredding.maxSchemaDepth50推断期间的最大 Variant 遍历深度。
variant.shredding.minFieldCardinalityRatio0.1采样的非空 Variant 值中,一个字段至少出现多大比例才会被 shred。

自动推断适用于探索性或快速演进的数据。由于推断是按文件进行的,不同文件可以 有不同的 shredded 路径;读取端会透明地使用每个文件各自的物理 schema。

查询下推​

Shredding 和查询下推是两个独立的能力。Shredding 创建带类型的物理列;而查询 引擎还必须把请求的 Variant 路径下推到 Paimon 扫描中,才能避免读取完整的 Variant。

Spark 4.1 及更高版本在启用 spark.sql.variant.pushVariantIntoScan 后,可以将 variant_get 提取下推到 Paimon:

SET spark.sql.variant.pushVariantIntoScan = true;

SELECT
    variant_get(payload, '$.user_id', 'bigint'),
    variant_get(payload, '$.city', 'string')
FROM user_events;

对于普通、shredded 和混合布局的文件,SQL 语句和结果都相同。shredded 文件能 带来最大的 I/O 收益,因为被请求的路径已经是独立的 Parquet 叶子列。而选择 完整的 Variant(例如 SELECT payload)则仍需读取并重建完整的值。

限制​

  • Variant 数据文件必须使用 Parquet,不支持 ORC 和 Avro。
  • VARIANT 不能用作主键或分区键。
  • Variant 提取本身不会创建索引,也不保证谓词下推。使用 shredding 可以减少 子列 I/O;当某个路径需要索引过滤时,请使用合适的索引或建模后的表列。
