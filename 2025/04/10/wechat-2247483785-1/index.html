谷歌A2A协议来袭，MCP协议的时代要被终结了？

谷歌面向多Agent场景，发布了A2A协议（Agent2Agent），该协议将使 AI Agents 能够相互通信，安全地交换信息，并在各种企业平台或应用程序之上协调行动。本文讲述了A2A和MCP的关系，以及一些细节信息。

Aaron2025-04-1012 分钟阅读大模型 · AI · 公众号

概要

谷歌面向多Agent场景，发布了A2A协议（Agent2Agent），该协议将使 AI Agents 能够相互通信，安全地交换信息，并在各种企业平台或应用程序之上协调行动。谷歌表示，A2A 是对 Anthropic 的模型上下文协议（MCP）的补充。该协议得到了 Atlassian、Box、Cohere、Intuit、Langchain、MongoDB、PayPal、Salesforce、SAP、ServiceNow、UKG 和 Workday 等 50 多家技术合作伙伴的支持与贡献；以及包括埃森哲、波士顿咨询集团、凯捷、高知特、德勤、HCLTech、印孚瑟斯、毕马威、麦肯锡、普华永道、塔塔咨询服务公司和威普罗在内的领先服务提供商的参与。

A2A ❤️ MCP

为什么使用协议？

标准协议对实现代理互操作性至关重要，特别是在将代理连接到外部系统时。这在两个互相关联的创新领域中至关重要：工具和代理。

工具是具有结构化输入和输出的原语，且通常具有已知的行为。代理是能够通过使用工具、推理和用户交互来完成新任务的自主应用。自主应用必须同时使用工具和代理来实现用户的目标。

互补性

模型上下文协议（MCP）是将大型语言模型与数据、资源和工具连接的一个新兴标准。我们已经观察到MCP正在其不同模型和框架中标准化“函数调用”。这正在创造一个工具服务提供商的生态系统，并显著降低将代理与工具和数据连接的复杂性。随着越来越多的框架、服务提供商和平台采用MCP，我们预计这种趋势将继续。

A2A关注的是一个不同的问题。A2A是一种应用层协议，使代理能够在其自然模式下进行协作。它允许代理以代理（或用户）的身份进行通信，而不是以工具的身份。我们希望A2A能够作为MCP的补充被广泛采用，从而促成代理生态系统的发展，并将与社区开放合作以实现这一目标。

MCP（模型上下文协议）用于工具和资源，通过结构化的输入/输出将代理连接到工具、API和资源。Google ADK支持MCP工具，使得可以使用多种MCP服务器与代理进行连接。

A2A（Agent2Agent协议）用于代理间协作，不同代理之间进行动态、多模态通信，而无需共享内存、资源和工具。

示例

让我们来看一个示例：

考虑一家修理汽车的汽车修理店。该店雇佣了能够使用专用工具（例如，举升机、万用表和套筒扳手）来诊断和修理问题的自主员工。工作人员经常需要诊断和修理他们以前从未遇到过的问题。维修过程可能需要与客户进行深入对话、研究以及与零件供应商合作。

现在，让我们将店员建模为AI代理：

  • MCP是连接这些代理与其结构化工具的协议（例如，将平台升高2米，向右旋转扳手4毫米）。

  • A2A是使最终用户或其他代理能够与店员合作的协议（“我的车发出了咔哒声”）。A2A支持持续的来回沟通和不断发展的计划以取得成果（“给我发一张左轮的照片”，“我注意到有液体泄漏。这种情况持续了多久？”）。A2A还帮助汽车店员工与其他代理（如零件供应商）进行合作。

交集

我们建议应用将A2A代理建模为MCP资源（以其AgentCard表示）。框架随后可以使用A2A与他们的用户、远程代理和其他代理进行通信。

A2A 设计原则

A2A是一种开放协议，提供了一种标准的方法，让代理可以相互协作，无论底层框架或供应商如何。在与合作伙伴设计该协议时，我们坚持了五个关键原则：

  • 利用代理能力：A2A集中于实现代理在其自然、非结构化的模式中进行协作，即使它们不共享记忆、工具和上下文。我们正在实现真正的多代理场景，而不是将代理限制为“工具”。

  • 建立在现有标准之上：该协议构建在现有的、流行的标准之上，包括HTTP、SSE、JSON-RPC，这意味着更容易与企业日常使用的现有IT技术堆栈集成。

  • 默认安全：A2A设计用于支持企业级认证和授权，与OpenAPI的认证方案达到同等水平。

  • 支持长时间运行的任务：我们设计了A2A以提供灵活性，并支持在场景中从快速任务到可能需要数小时甚至数天的人参与的深度研究等完成任务。在这一过程中，A2A可以为用户提供实时反馈、通知和状态更新。

  • 模式无关性：代理的世界不仅限于文本，这就是为什么我们设计A2A以支持各种模式，包括音频和视频流。

细节

参与者

A2A 协议有三个参与者：

  • 用户。终端用户（人类或服务），使用代理系统完成任务。

  • 客户端。代表用户向不透明代理请求动作的实体（服务、代理、应用程序）。

  • 远程代理（服务器）。不透明（“黑盒”）代理，即 A2A 服务器。

传输

该协议利用 HTTP 在客户端和远程代理之间进行传输。根据客户端和远程代理的能力，他们可能利用 SSE（服务器发送事件）来支持从服务器接收更新的流式传输。

A2A 使用 JSON-RPC 2.0 作为客户端和远程代理之间通信的数据交换格式。

异步

A2A 客户端和服务器可以使用标准的请求/响应模式并轮询更新。然而，A2A 还通过 SSE（在连接时）支持流式更新，并通过推送通知（在断开连接时）接收更新。

认证和授权

A2A 将代理建模为企业应用程序（之所以能这样做，是因为 A2A 代理是不透明的，不共享工具和资源）。这为代理互操作带来了企业就绪性。 A2A 遵循 Open API 的认证规范进行认证。重要的是，A2A 代理不在 A2A 协议内交换身份信息。相反，它们通过带外方式获取材料（如令牌），并在 HTTP 头中传输材料，而不是在 A2A 负载中。

虽然 A2A 不通过协议传输身份，但服务器会在 A2A 负载中发送认证要求。服务器至少应在其AgentCard中发布其要求。关于发现AgentCard的思考见此主题。

客户端应使用服务器发布的认证协议之一来验证其身份并获取凭证材料。A2A 服务器应对每个请求进行认证，并使用标准的 HTTP 响应码（401、403）拒绝或质疑请求，并附带特定于认证协议的头和主体（如带有 WWW-Authenticate 头的 HTTP 401 响应，指示所需的认证方案，或在已知路径上的 OIDC 发现文档）。更多细节在“企业就绪”中讨论。

注意：如果代理在执行任务时要求客户端/用户提供额外凭证（例如使用特定工具），代理应返回任务状态为“需要输入”，负载为认证结构。客户端应再次通过带外方式获取 A2A 的凭证材料。

AgentCard

支持 A2A 的远程代理必须以 JSON 格式发布AgentCard，描述代理的能力/技能和认证机制。客户端使用AgentCard信息识别能够执行任务的最佳代理，并利用 A2A 与该远程代理通信。

发现

我们建议将AgentCard托管在 https://base url/.well-known/agent.json。这与 DNS 方法兼容，客户端通过 DNS 找到服务器 IP 并发送 HTTP GET 请求以检索代理卡。我们还预计系统将维护私有注册表（例如“代理目录”或私有市场等）。更多讨论见本文档。

表示形式

以下是AgentCard的提议表示形式：

// 代理卡传达关键信息：
// - 总体详情（版本、名称、描述、用途）
// - 技能：代理能够执行的一组能力
// - 代理支持的默认模式/内容类型
// - 认证要求
interfaceAgentCard {
// 代理的人类可读名称
//（例如“食谱代理”）
name: string;
// 代理的人类可读描述，用于帮助用户和其他代理理解代理的功能
//（例如“帮助用户处理食谱和烹饪的代理”）
description: string;
// 代理托管的 URL 地址
url: string;
// 代理的服务提供者
provider?: {
    organization: string;
    url: string;
  };
// 代理的版本 - 格式由提供者决定（例如“1.0.0”）
version: string;
// 代理文档的 URL
documentationUrl?: string;
// 代理支持的可选能力
capabilities: {
    streaming?: boolean; // 如果代理支持 SSE，则为 true
    pushNotifications?: boolean; // 如果代理可以通知客户端更新，则为 true
    stateTransitionHistory?: boolean; // 如果代理暴露任务的状态变更历史，则为 true
  };
// 代理的认证要求
// 旨在匹配 OpenAPI 认证结构
authentication: {
    schemes: string[]; // 例如 Basic、Bearer
    credentials?: string; // 客户端用于私有卡的凭证
  };
// 代理在所有技能中支持的交互模式集，此项可按技能覆盖
defaultInputModes: string[]; // 支持的输入 MIME 类型
defaultOutputModes: string[]; // 支持的输出 MIME 类型
// 技能是代理能够执行的能力单元
skills: {
    id: string; // 代理技能的唯一标识符
    name: string; // 技能的人类可读名称
    // 技能描述 - 供客户端或人类用作理解技能功能的提示
    description: string;
    // 描述此特定技能能力类别的标签集（例如“烹饪”、“客户支持”、“账单”）
    tags: string[];
    // 技能可以执行的示例场景集
    // 供客户端用作理解技能使用方式的提示（例如“我需要面包的食谱”）
    examples?: string[]; // 任务的示例提示
    // 技能支持的交互模式集（如果与默认值不同）
    inputModes?: string[]; // 支持的输入 MIME 类型
    outputModes?: string[]; // 支持的输出 MIME 类型
  }[];
}

代理间通信

客户端与远程代理之间的通信以任务完成为导向，代理协作完成终端用户的请求。任务对象允许客户端和远程代理协作完成提交的任务。 任务可以由远程代理立即完成，也可能是长时间运行的。对于长时间运行的任务，客户端可以轮询代理以获取最新状态。代理还可以通过 SSE（如果已连接）或通过外部通知服务向客户端推送通知。

核心对象

任务（Task）

任务是一个有状态的实体，允许客户端和远程代理实现特定结果并生成成果。客户端和远程代理在任务中交换消息。远程代理生成结果作为产物。 任务总是由客户端创建，状态总是由远程代理确定。如果客户端需要，多个任务可以属于同一会话（由可选的 sessionId 表示）。为此，客户端在创建任务时设置一个可选的 sessionId。

代理可能：

  • 立即满足请求

  • 安排稍后执行工作

  • 拒绝请求

  • 协商不同的模式

  • 要求客户端提供更多信息

  • 委托给其他代理和系统

即使在达成目标后，客户端仍可针对同一任务请求更多信息或更改上下文。（例如，客户端：“画一只兔子”，代理：“<图片>”，客户端：“把它变成红色”）。

任务用于传输产物（结果）和消息（想法、指令、其他内容）。任务维护状态和可选的状态及消息历史。

interface Task {
id: string; // 任务的唯一标识符
sessionId: string; // 客户端生成的持有任务的会话 ID
status: TaskStatus; // 任务的当前状态
history?: Message[];
artifacts?: Artifact[]; // 代理创建的产物集合
metadata?: Record<string, any>; // 扩展元数据
}
// 任务状态及附带消息
interfaceTaskStatus {
state: TaskState;
message?: Message; // 为客户端提供的额外状态更新
timestamp?: string; // ISO 日期时间值
}
// 在 sendSubscribe 或 subscribe 请求期间由服务器发送
interfaceTaskStatusUpdateEvent {
id: string;
status: TaskStatus;
final: boolean; // 指示事件流的结束
metadata?: Record<string, any>;
}
// 在 sendSubscribe 或 subscribe 请求期间由服务器发送
interfaceTaskArtifactUpdateEvent {
id: string;
artifact: Artifact;
metadata?: Record<string, any>;
}
// 由客户端发送给代理以创建、继续或重启任务
interfaceTaskSendParams {
id: string;
sessionId?: string; // 如果未设置，服务器为新任务创建新的 sessionId
message: Message;
historyLength?: number; // 要检索的最近消息数量
// 服务器在断开连接时应发送通知的位置
pushNotification?: PushNotificationConfig;
metadata?: Record<string, any>; // 扩展元数据
}
typeTaskState =
  | "submitted"// 已提交
  | "working"// 工作中
  | "input-required"// 需要输入
  | "completed"// 已完成
  | "canceled"// 已取消
  | "failed"// 已失败
  | "unknown"; // 未知

产物（Artifact）

代理生成产物作为任务的最终结果。产物是不可变的，可以命名，并且可以有多个部分。流式响应可以将部分附加到现有产物上。 单个任务可以生成多个产物。例如，“创建网页”可以分别创建 HTML 和图像产物。

interface Artifact {
name?: string;
description?: string;
parts: Part[];
metadata?: Record<string, any>;
index: number;
append?: boolean;
lastChunk?: boolean;
}

消息（Message）

消息包含除产物外的任何内容。这可能包括代理的想法、用户上下文、指令、错误、状态或元数据等。

客户端的所有内容都以消息形式发送。代理发送消息以传达状态或提供指令（而生成的结果作为产物发送）。

消息可以有多个部分来表示不同的内容片段。例如，用户请求可能包括用户的文本描述，然后是客户端用作上下文的多个文件。

interface Message {
  role: "user" | "agent"; // 用户或代理
  parts: Part[];
  metadata?: Record<string, any>;
}

部分（Part）

客户端与远程代理之间作为消息或产物一部分交换的完整内容片段。每个部分都有自己的内容类型和元数据。

interface TextPart {
type: "text"; // 文本
text: string;
}
interfaceFilePart {
type: "file"; // 文件
file: {
    name?: string;
    mimeType?: string;
    // 以下之一
    bytes?: string; // base64 编码内容
    uri?: string;
  };
}
interfaceDataPart {
type: "data"; // 数据
data: Record<string, any>;
}
typePart = (TextPart | FilePart | DataPart) & {
metadata: Record<string, any>;
};

推送通知

A2A 支持一种安全的通知机制，代理可以通过 PushNotificationService 在未连接会话的情况下通知客户端更新。在企业内部和跨企业中，代理验证通知服务的身份、向服务认证自身并提供与执行任务关联的标识符至关重要。

推送通知服务的目标服务器应视为独立服务，不保证（甚至不期望）直接是客户端。此推送通知服务负责认证和授权代理，并将验证后的通知代理到适当的端点（可以是从发布/订阅队列到电子邮件收件箱或其他服务的任何内容）。

对于孤立客户端-代理对（例如在受控 VPC 中的本地服务网格等）或没有企业安全考虑的隔离环境，客户端可以选择简单地打开一个端口并充当自己的推送通知服务。任何企业实现都可能有一个集中的服务，使用可信的通知凭证认证远程代理，并能处理在线/离线场景。（这应类似于移动推送通知服务）。

interface PushNotificationConfig {
url: string;
token?: string; // 此任务/会话的唯一令牌
authentication?: {
    schemes: string[];
    credentials?: string;
  };
}
interfaceTaskPushNotificationConfig {
id: string; // 任务 ID
pushNotificationConfig: PushNotificationConfig;
}
