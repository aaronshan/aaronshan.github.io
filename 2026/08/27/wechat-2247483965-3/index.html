1. 项目概览

OpenMinis 是一款完全运行在设备端（on-device）的开源 AI Agent 应用，覆盖 iOS 与 Android 双平台。它把主流大模型（Claude / GPT / Gemini / xAI / Kimi / OpenRouter 等）接入原生移动体验，并给模型配上一台”真正的电脑”来干活——一个跑在 App 进程内的完整 Linux 沙箱、浏览器自动化、可扩展的 Skills、跨会话持久记忆，以及深度的系统集成。

维度 说明
定位 私有、端侧的 AI Agent——数据不出设备（除非主动调用云上模型 API）
平台 iOS（Swift / SwiftUI，iOS 26.2，Swift 6.0）/ Android（Kotlin / Compose，minSdk 26，arm64-v8a）
许可证 GPLv3（因链接 iSH GPLv3 与 PRoot GPLv2，组合工作以 GPLv3 分发）
模型接入 自带 API Key 或账号 OAuth 登录；支持自定义 Base URL（OpenAI 兼容端点，可接 DeepSeek 等中转）
核心能力 Linux Shell、浏览器自动化、设备集成（Health/Calendar/Contacts/HomeKit/…）、Skills、Memory、Workspaces、原生卸载
沙箱内核 iOS 用 iSH（ARM64 用户态 Linux 模拟）；Android 用 PRoot（ptrace 系统调用拦截 + bind mount）；均启动 Alpine Linux aarch64

产品哲学（README）：“在 AI 时代，技术设计与代码不再是产品的优势所在。最好的 Agent 源于与使用者的紧密反馈闭环——他们的期望与反馈共同收敛于产品。” 因此主仓库不接受 PR（是私有开发树的镜像），通过 Issues、AwesomeMinis（用例集）与 MinisSkills（Skill 集）接收社区贡献。

典型用法

  • 拍一张饭菜照片 → 识别菜品、估算卡路里与宏量营养素 → 写入 Apple Health

  • Shortcuts 触发 → 抓取 X 时间线、摘要、合成语音 → 作为闹钟播放

  • 从 Telegram 群拉消息 → 抽取 bug 与待办、去重 → 写入 Apple Reminders

  • 挂载 Obsidian vault → 研究、清理并写回 Markdown 笔记（作为普通 workspace）

  • 通过 iOS Share Sheet 发送页面/消息 → 自动创建日历事件（含时间地点）

2. 顶层架构

OpenMinis 是一个分层 + 桥接的端侧 Agent 系统。自上而下分四层：UI 与交互层、Agent 运行时层、能力层（LLM Provider + Linux 沙箱 + 原生卸载 + Skills/Memory/Browser/Speech）、持久化与同步层。层与层之间通过明确的协议/接口解耦，使 LLM Provider 可互换、沙箱实现可平台替换（iOS 用 iSH，Android 用 PRoot）。

2.1 整体分层架构图

2.2 设计要点

  • Agent-first：一切持久产物以 minis:// URL 回传模型，模型可在后续轮次直接引用（图片内联渲染、文件可点击预览）。

  • 沙箱是产品的心脏：iOS 在 App 进程内跑一个完整 Alpine Linux（iSH 用户态内核），Android 用 PRoot 在用户态 chroot 出同样的环境。模型由此获得 apk/pip/node 等真实工具链，而非被关在玩具沙箱里。

  • 原生卸载桥接：guest 进程对 /usr/local/bin/apple-*（或 android-*）调用 execve 时被拦截，路由到原生 iOS/Android Framework——让 guest 命令能访问 HealthKit、相册、日历等硬件/系统能力。传输分两套：iOS 是进程内 execve 钩子（handler 直接函数调用，结果经 noff_emit_json 写 guest 的 stdout fd，无 IPC）；Android 经 abstract Unix socket（二进制帧 NOFF/NORF），handler 输出写 rootfs tmpfile、PRoot 把 execve 重写为 /bin/cat <tmpfile>。

  • Provider 可互换：LLMProvider / AgentProvider 协议统一所有模型后端；xAI、Kimi、OpenRouter 直接复用 OpenAIProvider，仅靠自定义 Base URL + 凭证区分，几乎零重复代码。

  • 跨平台共享语义：系统提示词、工具 schema、bashism 检测规则（assets/bashism/bashism_rules.json）双平台单一真相源，保证同一 prompt 在两平台行为一致。

4. 核心子系统详解

4.1 Agent 运行时

Agent 运行时是 OpenMinis 的核心：把用户 prompt 驱动为一个多轮 Agent 循环——调用 LLM 生成文本与工具调用、并发执行工具（shell 命令、文件操作、浏览器操作、记忆读写）、把工具结果回传 LLM、最终产出完整回复。

4.1.2 Agent 循环流程

关键执行细节：

  • 孤儿工具修复：每轮先扫描 agentHistory，为无配对 tool_result 的 tool_use 注入占位结果，移除无配对的孤儿 tool_result——防止协议错位导致 Provider 拒绝请求。

  • 流式节流：文本 delta 按累积长度分层刷新 UI（<500 字 200ms … ≥128K 字 2s），新行快速路径；thinking delta 自适应节流。Markdown 解析在后台线程完成，仅赋值在 MainActor。

  • 空响应恢复：工具调用后若 LLM 返回空内容，注入 system-reminder 重试一次；可重试错误（5xx/network）自动重试；重试耗尽则在模型组内循环切换 entry 直到获得非空内容（fallback 时重新组装系统提示）。

  • 上下文管理：ContextPolicy 按模型窗口分 4 层（<32K / 32–64K / 64–128K / ≥128K），触发 offload（旧工具输出替换为文件路径）、compact（旧消息摘要化）、trim（保留最近 20 张图，旧图替换为文本占位）；全请求图片字节总量上限 25MB。

  • 流式 TTS：从 textDelta 按句末标记（。！？.!?; + 换行）切句送 TTS，跳过代码块，数字内部分隔符不切割。

4.1.4 会话与持久化

  • 存储引擎：iOS ChatStore（actor，原生 SQLite3 C API，WAL，Library/MinisChat/minis.db）；Android Room（AppDatabase）。

  • 数据模型：ChatSession（会话元信息）、RawMessage（parts_json 序列化 AgentContentPart：text/toolUse/toolResult/imageData）、ToolSnapshot（工具执行快照）、MediaRef（媒体引用，存于 Library/MinisChat/minis/<sessionId>/）。

  • 持久化时机：用户消息即时落库；每轮工具执行完成后批量持久化 assistant + tool_result（单事务）；首轮后异步生成会话标题。

4.2 Linux 沙箱（iSH / PRoot + Alpine）

沙箱是产品的心脏：在 App 进程内跑一个完整的 Alpine Linux，让模型获得 apk/pip/node 等真实工具链。iOS 与 Android 用不同的用户态技术实现同一语义。

4.2.1 双平台沙箱对比
维度 iOS（iSH） Android（PRoot）
技术 用户态 Linux 内核模拟（Asbestos JIT 翻译 ARM64） PRoot（ptrace 系统调用拦截 + bind mount）
Guest Alpine Linux aarch64 Alpine Linux aarch64
持久内核 是（ISHKernel 持续运行于独立 pthread） 否（PRoot 进程级，每会话一个持久 /bin/sh）
文件系统 fakefs（SQLite 元数据 meta.db + data/ 目录） 直接 bind mount 到 host 目录
设备集成 apple-* offload（execve 拦截 → Obj-C handler） android-* offload（--native-offload 扩展 → Unix socket）
交叉编译 Meson 交叉编译 iOS arm64 NDK r28+ 交叉编译
4.2.2 iOS iSH 集成层

  • ISHKernel（src/ios/iSH/ISHKernel.m，Obj-C 单例）：包装 C 内核。启动序列：挂载 rootfs → init PID 1 → 创建设备节点 → 挂 procfs/devpts → 配 DNS → 注册 TTY 驱动 → 注册原生卸载 handler。对外暴露 executeCommand（PTY 交互）、executeCommandAndWait（跑到完成）、sendInput、setTerminalSize、bindMountPath、refreshDns。

  • RootfsManager（src/ios/iSH/RootfsManager.swift）：Alpine rootfs 生命周期——解压到 ~/Documents/alpine-rootfs/、架构标签跟踪、重置（可选用户数据备份）、预建 /var/minis/ 子目录、在 fakefs meta.db 注册元数据使 bind mount 可见。

  • ISHShellExecutor（.m）：进程级执行——逐行输出回调、退出码与耗时、超时与 SIGKILL、同步/异步模式、自定义环境变量注入。

  • ISHExecutionCoordinator（Agent/ISH/，actor）：串行化、session 感知的命令调度器——per-session 完全并发、按 session 挂载/重挂 /var/minis/、正则检测 prompt（$ 、# 、user@host:path$ 等）、超 10 分钟且有等待者时抢占、100KB 输出缓冲上限、echo 去除。

内核能力：100+ Linux 系统调用（mmap/brk/poll/epoll/pipes/eventfd/inotify）、AF_INET/AF_INET6/AF_LOCAL 全栈网络、TTY/PTY 设备、SIGSEGV/SIGBUS JIT 崩溃恢复。

4.2.3 挂载系统与 per-session 隔离（fs_context 路径翻译）

agent 与 shell 永远只看到 /var/minis/，URL 与路径中不含 session ID。但”同一时刻只有一个 session 可见”是早期 spec 的说法——实现实际支持跨会话并发，隔离靠 MinisFsRouter 的 fs_context 路径翻译，而非 per-session 换挂载：

Guest 路径 Host 路径 路由方式
/var/minis/attachments/ minis/<sessionId>/attachments/ fs_context 翻译（per-session）
/var/minis/offloads/ minis/<sessionId>/offloads/ fs_context 翻译（per-session）
/var/minis/workspace/ minis/<sessionId>/workspace/ fs_context 翻译（per-session）
/var/minis/browser/ minis/<sessionId>/browser/ fs_context 翻译（per-session）
/var/minis/memory/ minis/memory/ （全局） 静态 bind mount（首次启动注册 meta.db）
/var/minis/skills/ minis/skills/ （全局） 静态 bind mount

机制（MinisFsRouter.swift + ISHExecutionCoordinator.swift）：

  1. MinisFsRouter.context(for: sid) 为每个 session 分配一个 u64 fs_context token；

  2. ISHShellExecutor.executeExecutable(..., fsContext:) 把 token 盖到 iSH 任务组（task->group->fs_context）；

  3. iSH 内核翻译 fakefs 路径时回调 MinisFsRouter.translate(guestPath, fsContext)，把 /var/minis/offloads/foo 重写到 ~/Library/.../minis/<sid>/offloads/foo。

会话切换 = 换 token，不搬数据：切换只设 mountedSessionId + 分配新 token，per-session 目录不重新挂载、不清空、不在 meta.db 注册（ISHExecutionCoordinator.swift:419-423 注释明确）。后果：

  • 崩溃天然安全——无数据搬运，各 session 数据本就在各自 host 目录，进程死于任意时刻，下次启动重新分配 token 即可恢复；

  • 跨会话并发——不同 session 的 shell 各自盖自己的 token，内核按 token 路由到各自目录，互不可见；

  • meta.db 注册只在首次启动对 4 个全局静态目录做一次（batchEnsureFakefsMetadata，单事务批量，ISHExecutionCoordinator.swift:784-851）；per-session 目录不经 meta.db。

⚠️ 早期 spec（docs/specs/ios-sandbox-ish-summary.md）描述的 “Harvest→Clear→Mount→Register” 生命周期在当前实现中不存在；本文档此前版本沿用了该 spec 的说法，现按源码更正。

4.2.4 Android PRoot 集成层

  • PRootKernel（sandbox/PRootKernel.kt）：boot() 解压 Alpine rootfs + PRoot 二进制、应用 default_mount/ overlay、注册全局 bind mount（/var/minis/{memory,skills,shared,mcp-servers}）、启动 NativeOffloadServer、安装 handler stub 到 /usr/local/bin/。buildProotCommand() 构建命令行：proot -0 --link2symlink -r <rootfs> -b /dev -b /proc -b /sys ... --native-offload=<socket>:<handlers> /bin/sh -c "<cmd>"。-0 fake root；--link2symlink 把 hardlink 转 symlink（Android 文件系统拒绝跨目录硬链接）；--native-offload 是 PRoot fork 扩展，拦截 execve 路由到 NativeOffloadServer。

  • ExecutionCoordinator（sandbox/）：每会话一个 PersistentShell（长期 PRoot /bin/sh），ConcurrentHashMap 管理；每会话一个 Mutex，同 session 串行、跨 session 并行。execute() 自动 boot → 取/建 shell → 注入环境变量快照 → 执行。

  • PersistentShell：长期 PRoot /bin/sh 进程，stdin 发命令，用唯一 marker（__MINIS_DONE_<uuid>_EXIT_<code>__）检测命令边界，后台 reader 解析 exit code；环境变量全量快照注入（新增 export、删除 unset）模拟每命令独立进程隔离。

  • NativeOffloadServer（sandbox/NativeOffload.kt）：PRoot 的 --native-offload 拦截 guest 的 execve("<handler>", argv, envp)，经 abstract Unix socket（native-offload）发到 host 端 server。协议为小端二进制（magic NOFF/NORF），handler 输出写入 rootfs /tmp/.native-offload-<pid>-<seq>，回复 (exit_code, guest_tmpfile_path)，PRoot 把 execve 重写为 /bin cat <tmpfile>。每个 handler 在 /usr/local/bin/ 装一个 #!/bin/sh\nexit 0 stub 让 PATH 搜索触发拦截。

  • PtyBridge（cpp/pty_bridge.c + PtyBridge.kt）：JNI 包装 bionic forkpty()，为 PRoot 进程提供真实 TTY（支持 Ctrl-C/D/Z），供交互式终端使用。

4.2.5 安全与隔离

  • iSH 跑在独立 pthread，线程局部 current 任务指针做进程隔离；JIT 异常 handler 防 guest 崩溃拖垮 App。

  • fakefs 提供与 host 的文件系统隔离；bind mount 显式且限于 /var/minis/。

  • 环境变量存 Keychain（iOS SecureEnclave / Android EncryptedSharedPreferences）。

  • guest 进程不能访问任意 host 路径，仅 bind 挂载目录。

  • 100KB 输出缓冲 + 10 分钟命令超时（有等待者时抢占）防内存耗尽。

4.3 原生卸载系统（Native Offloads）

沙箱里的 guest 进程是纯 Linux，无法直接访问 iOS/Android 的 HealthKit、相册、日历等硬件/系统能力。原生卸载机制在 guest 调用 /usr/local/bin/apple-*（或 android-*）时拦截 execve，路由到原生框架。传输分两套：iOS 进程内钩子（无 IPC），Android 经 abstract Unix socket。

4.3.1 拦截机制对比

  • iOS：iSH 内核在 execve 时检查 native_offload_add_handler 注册的命令路径，命中则进程内派发到 Obj-C handler（iSH 是嵌入 App 的模拟器，非独立进程），handler 调 iOS Framework，结果经 noff_emit_json 直接写 guest 的 stdout fd——无 pipe/socket IPC。需主线程的 Framework 用 noff_dispatch_main_sync 同步派发（阻塞 guest 线程直至完成）。

  • Android：PRoot 的 --native-offload=<socket>:<handlers> 扩展拦截 execve，经 abstract Unix socket（小端二进制协议 magic NOFF/NORF）发到 host 端 NativeOffloadServer；handler 输出写入 rootfs /tmp/.native-offload-<pid>-<seq>，PRoot 把 execve 重写为 /bin/cat <tmpfile>。每个 handler 在 /usr/local/bin/ 装 #!/bin/sh\nexit 0 stub 让 PATH 搜索触发拦截。

  • VoiceCorrectionEngine.swift（actor 单例）：LLM 语音转写纠错——分词→语音键归一化→并发多源检索（ConfusionDictionary + TypedVocabulary）→加权融合→LLM 纠错→结果验证。短 TTL memo cache（300s），所有失败路径 fallback 到原始转写。warmUp() 预加载 jieba 词典。

  • Android：speech/ 包，系统 + Provider，SpeechOffloadHandler 暴露 android-speech CLI。

4.8.2 TTS（文字转语音）

  • 流式 TTS：从 Agent 流式响应的 textDelta 中按句末标记（。！？.!?; + 换行）切句送 TTS，累积到动态窗口后送；首次 textDelta 清除前一轮 TTS 队列（per-session scoped）；跳过代码块；数字内部分隔符（如 28.98 的 .）不切割。

  • VoiceOutputPlayer.swift（Providers/Voice/，单例）：有序流式 TTS 队列——文本按序入队，音频预生成（pipeline 并发 synthesize）但严格按入队顺序播放。支持 fail-over 候选轮换、速度倍率（1.0/1.25/1.5/2.0）、浮动胶囊 UI 位置持久化。

  • VoiceProvider.swift：OpenAI 兼容的 STT（/v1/audio/transcriptions）和 TTS（/v1/audio/speech）基类，Vendor 子类覆盖 hook 适配不同 API，支持 chat-based ASR（多模态模型）。

  • shell 内 TTS/STT：iOS SpeakOffload（apple-speak，AVSpeechSynthesizer）+ SpeechOffload（apple-speech，SFSpeechRecognizer）；Android SpeakOffloadHandler/SpeechOffloadHandler。

4.9 minis:// URL 方案

minis:// 是会话作用域的统一资源定位符，桥接三层——Agent、iSH shell、host app——同一 URL 在工具结果、Markdown 渲染、组件间引用中都可用。

4.9.1 设计原则

  1. 会话作用域：所有资源访问绑定当前 session。URL 不含 session ID——始终对活跃 session 的存储解析，无跨 session 可见性。

  2. Agent 优先：每个工具产生的持久资源必须以 minis:// URL 回传模型。

  3. 可渲染：聊天 UI 内联解析 minis://——图片/音频/视频原生渲染。

  4. 双向：shell 与 host app 写入的文件都可用同一 URL 寻址。

  5. 会话内持久：资源在 app 重启后存活，session 隔离在持久存储，session 加载时挂载到 /var/minis/。

4.9.2 URL 格式与命名空间
minis://<namespace>/<path>
命名空间 Linux 路径 用途 内联渲染
attachments /var/minis/attachments/<path> 图片/音频/视频等媒体 是（图片 .png/.jpg/.gif/.webp、音频 .mp3/.m4a/.wav、视频 .mp4/.mov/.m4v）
workspace /var/minis/workspace/<path> 脚本/数据/配置/项目文件 否（文本链接）

4.9.3 路径解析与工具结果契约

  • minis:// → Linux 路径：minis://<namespace>/<path> → /var/minis/<namespace>/<path>。

  • Linux 路径 → host：/var/minis/<n>/<path> → <dataPath>/var/minis/<n>/<path>（dataPath=~/Documents/alpine-rootfs/data/）。resolveHostPath 拒绝含 .. 的路径防穿越。

  • 路径路由：per-session 目录（attachments/offloads/workspace/browser）由 MinisFsRouter 的 fs_context 路径翻译 hook 路由，不经 meta.db；仅 4 个全局静态目录（memory/skills/shared/mcp-servers）在首次启动经 batchEnsureFakefsMetadata 批量注册进 meta.db（单事务）。

  • 工具结果契约：file_write 写 /var/minis/ 下文件时附 minis_url:；shell_execute 执行后扫描 /var/minis/ 新增/修改文件附其 URL；browser_use 截图存 /var/minis/browser/ 并附 URL；用户附件经 saveAttachment() 返回 minis://attachments/<filename> 注入用户消息上下文。

4.9.4 渲染（iOS）

  • MinisImageProvider（AIChatView.swift）处理 Markdown 图片语法 ![](minis://...)，按扩展名分派：图片→UIImage（点击全屏，6 次重试）、音频→MinisAudioPlayerView（播放/暂停/进度）、视频→MinisVideoPlayerView（缩略图+全屏播放器）。

  • MinisURLSchemeHandler（BrowserUseManager.swift）：实现 WKURLSchemeHandler，让浏览器 tab 内的 minis:// 请求映射到本地文件。

  • MinisURLPathDecoding.swift：处理双重百分号编码的 minis:// 路径解码，以磁盘存在性为判别依据。

4.9.5 安全

会话隔离（fs_context 路径翻译在文件系统层强制——每进程只路由到自己 session 的 host 目录，无 mount/unmount 搬运）、路径穿越拒绝（resolveHostPath 拒绝 ..）、URL 中永不暴露 session ID。注意：resolveMinisURL（+RequestBudget.swift:293-337）未对命名空间做白名单校验——未知 host 被当作目录名尝试解析，最终以 file-not-found 软拒绝；不能逃逸 session 沙箱（host 始终是 minisPersistentBase/<sid>/<host>/ 下的单段路径），但缺纵深防御，建议补白名单。

10.1 结构性代价（非缺陷）

双沙箱：iOS iSH（用户态 ARM64 内核模拟 + fakefs）/ Android PRoot（ptrace 拦截 + bind mount）——两套完全不同的虚拟化栈，语义不同，连原生卸载传输都分两套（进程内钩子 vs socket+tmpfile）。平台强制：iOS 禁 ptrace 用不了 PRoot，Android 上 iSH 全模拟太重。无法消除，是本项目最大的长期维护负担，新增功能常需双平台各写一遍。

10.2 设计亮点（实测后确认优于预期）

  • fs_context 路径翻译做会话隔离——零数据搬运、崩溃天然安全、支持跨会话并发，比早期 spec 的”换挂载”模型更优雅（MinisFsRouter.swift:83-110）。

  • LLM Provider 用行为 flag 注入而非类型 switch——xAI/Kimi/OpenRouter/OpenAIResponses 复用同一 OpenAIProvider 类，12+ 行为 flag 在构造时注入，零 if provider=="kimi" 型判断（LLMProviderFactory.swift:20-39、OpenAIProvider.swift）。

  • iCloud 同步冲突显式策略——ConflictPolicy 枚举 + 按类型 LWW（updatedAt/serverEtag），冲突时合并 server record + 本地重入队，不静默丢（Syncable.swift:25-41、ICloudSharedZoneTransport.swift:1562-1581）。

  • iOS 原生卸载进程内钩子——handler 直接函数调用，近零 IPC 开销（ISHKernel.m:414-445）。

  • Memory 日注入有界——最近 3 篇、每篇前 200 行、30 天回溯（AIChatViewModel+MemoryTools.swift:20-53）。
